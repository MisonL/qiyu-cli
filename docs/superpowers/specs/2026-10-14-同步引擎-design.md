# 同步引擎（sync run）设计

> 状态：v1 草案（2026-10-14）
> 依据：`docs/qiyu-cli-design.md` §6（存储/类型/PII）、§7（同步引擎）、§9（输出契约）、§10.1（工单增量）、§10.5（知识库）；`docs/superpowers/specs/2026-10-09-后续交付路线图-design.md` §四.D 与 §四.G2；C1 存储层已交付能力（PR #4）。
> 前置：A（注册表）✅、C1（存储层）✅。本 spec 是 E（查询）的数据前提。

## 一、目标与非目标

**目标**：把七鱼 API 的数据可重复地同步进本地 DuckDB 库——增量/全量/断点续传/缺口记录/限流调度。**可重复的全量同步是一等公民**：只有第一次快不叫生产力，随时能重建才叫。

**非目标**（沿路线图 §九）：
- 不做 `messages` 表（设计稿 §6 明确本阶段不实现、不预留列）
- 不做守护进程；`sync install` 只生成系统调度器条目（默认 dry-run）
- 不做数据加密存储（设计稿 §6.5 明确范围之外）
- 不做 C2 外部后端的行为一致性验收（Kysely 后端另行）

**验收总纲**：`sync run` 幂等；中断后自动续跑；失败范围落 `sync_gaps`；`sync_state` 用 `pending/complete` 区分「未同步」与「空数据」；水位线与数据落库同事务；`sync verify` 能核对本地与远端一致性。

## 二、同步引擎的三条设计红线（传承教训，违反即架构错误）

以下三条来自更早一代同步实现的失败复盘（已拆除的旧数仓项目），是**本 spec 的宪法级约束**，每一节的机制设计都回指这里：

### 红线 1：主键只能是上游业务键

同步表的主键**只能**是上游 API 返回的天然业务键（如 `session.id`、`stat_date + staff_id`、`ticket_id`），**绝不含**：
- 派生值/富化产物字段（同步过程中计算出来的列）
- 会随重跑变化的字段（进程时间、导入批次号）
- 复合键中的非业务维度

**为什么**：历史上把富化字段放进排序键，导致「世代分裂」——重跑同步不修复旧行而是追加新行，读路径取到写入时刻最新的错误世代，重跑同步从「自愈手段」变成「污染源」。主键若含会变的东西，重跑就永远无法收敛。

**推论**：本地派生列（如 `session_type` 是从 `staffId` 推导的判别值）**不进主键**，作为普通列落库且必须**确定性派生**（同一输入行永远得到同一输出）。

### 红线 2：「任务成功」≠ 数据正确 —— 三方配对核对

只看「API 调用成功、事务提交」不构成正确性证据。历史教训：run 计数与落地行数长期不一致而无人发现，直到与上游合计对账才暴露缺数。

**机制**：引擎在每个窗口落库后做**配对核对**（API 返回行数 ↔ 实际写入行数）；`sync verify` 做**三方核对**（本地表行数/范围 ↔ 上游 API 合计 ↔ `sync_state` 记录的成功窗口集）。核对不符 ≠ 失败即中断——差异记录进 `sync_gaps`（reason=`count_mismatch`）并在 run 结束的 stderr 汇总中列出。

### 红线 3：水位推进与数据落库同事务

「水位已推进、数据未落库」的状态比「两者都没发生」危险得多——它制造一个永远跳过的静默空洞。C1 的 `Store.transaction` 闭包是为此准备的：**每个窗口的「写数据 + 推水位 + 删缺口」在一个事务内提交**。

## 三、命令面

```
qiyu sync run [task]              # 增量同步（task 缺省 = 注册表全部任务）
qiyu sync run --full [task]       # 全量重刷（重新冲刷区间，幂等）
qiyu sync run --since T --until T # 指定区间（--until 可单独用于分段）
qiyu sync status [task]           # 水位、区间状态、缺口、锁
qiyu sync tasks                   # 列出可用任务与不支持的数据集
qiyu sync verify [task]           # 三方配对核对（红线 2）
qiyu sync install --schedule CRON # 生成系统调度条目（默认 dry-run，--yes 才真装）
qiyu sync uninstall
```

> **修订（修复批 2）：本阶段无启用/停用机制** —— 注册表里的任务**总是全部执行**（选定
> 任务只能靠命令行显式列任务 id）。早前版本的「启用/停用」措辞与 `enabled` 输出字段
> 已从本 spec 移除（承诺了但不存在的能力 = 契约不诚实）；若未来引入启用开关，再走
> 迁移 + 输出字段的完整流程。

命令行为契约（沿 C1 命令层惯例）：
- `--help` / 未知子命令 / 未知参数 / 值位守卫 → `usageFail`（退出码 2）；`--pretty` 豁免
- `store_not_initialized` 的 hint 一律指 `qiyu store init`（**修订**：C1 与 D 阶段同口径；
  `sync run` 首跑虽会自动建库，但「初始化存储」的最小命令是 store init —— 此前设计稿
  §9.5 的「D 交付后改指 sync run」不再采纳，见 §九）
- JSON 结果走 stdout；**进度走 stderr**（人读：任务名、窗口序号/总数、耗时）——Agent 不被进度噪声污染，`--quiet` 关进度
- 相对时间（`--since 30d`、`yesterday`）按 `Asia/Shanghai` 解析（G2/§9.3），并在输出回显 `resolved_range`
- 中断（SIGINT/SIGTERM）：当前窗口事务回滚或完成提交后退出，水位不推；下次 `run` 自动续跑。**绝不阻塞 Agent**——`sync run` 总是前台可中断执行，不提供后台化

## 四、任务声明模型（代码内任务目录）

### 4.1 SyncTask 接口

```ts
interface SyncTask {
  id: string                    // 'reports.overview'、'sessions.export'、'knowledge.items'…
  table: string                 // 目标表（schema.ts TABLES 中的名字）
  kind: 'windowed' | 'snapshot' // 窗口型（时间切片）| 快照型（全量拉取）
  watermark: WatermarkSpec      // 水位字段与初始值
  maxWindowDays?: number        // 窗口切分上限（windowed 必填；预校验依据）
  overlapDays?: number          // 相邻窗口重叠（去重依赖 upsert/删除范围语义）
  primaryKey: string[]          // 红线 1：上游业务键
  fetch: (w: WindowRef, ctx: FetchCtx) => Promise<FetchResult>
  write: WriteStrategy          // deleteRangeInsert | upsertRows
  enrich?: (row: Record<string, unknown>) => Record<string, unknown>  // 确定性派生列
}
```

- **任务目录是代码**（`src/sync/tasks/*.ts`）：实测事实（窗口上限、水位字段、陷阱规避）本就是代码级知识，类型检查天然守护；不引入 JSON 任务文件的解析层与「声明了但没人读」风险
- `fetch` 内部经 `http.call(spec, body)` + `normalize()`——sync 不绕过信封层
- `enrich` 必须确定性（红线 1 推论）；`session_type` 判别（`staffId < -1 → robot`、`== -1 → internal`、`> 0 → human`）是典型用例

### 4.2 写策略

| 策略 | 适用 | 机制 |
|---|---|---|
| `deleteRangeInsert` | 报表 10 张（窗口聚合） | 事务内 `DELETE WHERE 范围` + 插入。**纯 upsert 不会删行**——坐席离职/某日无数据时陈旧行残留（实测 3 行→仍 3 行），按范围删除是必须的 |
| `upsertRows` | 维度表、sessions、知识库、工单 | `Store.upsert`（ON CONFLICT DO UPDATE），按主键幂等 |

`--full` 的先删后插**必须整段在一个事务内**（红线 3）；`sync_state.range_status = 'pending'` 在事务开始前置位、成功后推 `'complete'`——Agent 因此能区分「没有数据」和「没有同步」。

### 5.2 报表（9 + tickets 归 §5.5，kind=windowed，deleteRangeInsert，按天轮转）

全部**日期由调用方按窗口填写**（响应内 `date` 字段逐接口语义不同：恒 0 / 小时戳 / 窗口起点 / 无日期字段——统一不信响应日期）：

**聚合报表按天切片（窗口 1 天）**：这些接口返回的是**窗口聚合值**（`overview` = 一行全局汇总 69 字段；`staffworklod` = 每客服一行；`transferHuman` = 永远 1 行），响应 `date` 原文是 "this date has no specific meaning, it only indicates the start time of the current query"。多天窗口 = 一条多天聚合被标成某一天（`daily_overview` 会把 31 天汇总写成第 1 天，E 的「每日概览」读到 31 天累计值），且 `deleteRangeInsert` 按 `stat_date` 删范围时下一次不同起点的窗口删不到旧行（陈旧行残留）。水位字段是 `query_start` —— 按天窗口才能每日推进。**窗口数 = 天数**（`--full` 从 1970 起会切出上万窗，见下「量级提醒」）。唯一例外：`staff_attendance` 的响应**有逐行可信时间戳**（`date` 按小时对齐，落 `hour_ts`）→ 保持 31 天窗口（一行一小时 ≈ 1.7 万行/窗），但 `stat_date` 由该行的 `hour_ts` 推导上海日（不是窗口起点）。

| 表 | 接口 | 窗口上限 | 水位 | 特殊规则 |
|---|---|---|---|---|
| `daily_overview` | `statistic.overview` | **1**（按天切片） | `query_start` | — |
| `staff_workload` | `statistic.staffworklod` | **1**（按天切片） | `query_start` | `date` 恒 0，写入请求窗口日 |
| `staff_quality` | `statistic.staffquality` | **1**（按天切片） | `query_start` | `sum` 与分页无关、覆盖全集 → 全局汇总行单独 upsert |
| `staff_satisfaction` | `statistic.satisfaction.report` | **1**（按天切片） | `query_start` | — |
| `staff_attendance` | `statistic.staffAttendance` | 31 | `query_start` | **必须传 `startTime`**（省略则静默降级为天粒度、少抓 ~10 倍）；`endTime` 不得晚于今天 0:00（贴边不稳定，留一天安全余量）；主键 `staff_id + hour_ts`；`stat_date` 由本行 `hour_ts` 推导 |
| `order_performance` | `statistic.performance` | **1**（按天切片；365 只是接口跨度上限） | `query_start` | `orders:null` = 筛选失败非空窗口 → 记 gap reason=`filter_matched_no_staff`；空结果 `page>1` 报 14500；`Radio` 拼写按线上 |

| `transfer_human` | `ai.statistic.transferHuman` | **1**（按天切片；360 天曾是接口跨度上限） | `query_start` | 忽略 `type` |
| `tickets` | `v2/ticket/search` | **op 窗口 ≤31**（`opStart` 被钳制到当前时刻前 ~31 天，90 天上限在诱导切 89 天窗——每个切片会静默少取 ~58 天） | `opStart/opEnd` + 3 天回看重叠 | **水位必须用操作时间**（按创建时间增量永远拿不到状态变更）；op 参数必须成对（缺 `opEnd`/`=0`/只传一个 → 静默返回全量）；`limit=500`；`search` 只识别 8 个参数 |

**轮转调度**（实测：限频按路径独立 30 秒）：同一天内不同报表接口背靠背，天与天之间按同路径冷却等待——31 天 × 10 接口 ≈ 16 分钟，而非接口串行的 2.6 小时。轮转是 `kind:'windowed'` 批量任务的内建调度策略，不逐任务配置。按天切片后同一天内 10 个接口仍背靠背，只是「一轮」= 一天。

**量级提醒（按天切片的代价，如实写在明处）**：窗口数 = 天数。`--full`（起点 0 = 1970）对 8 个按天切片任务会切出**上万窗**（≈ 56 年 × 每天 1 窗），每窗至少一次调用（考勤 2 页、salaryDetail 每客服一次），几十小时量级——首跑/回补历史请用 `--since/--until` 限定区间（例如 `--since 30d` = 30 窗/任务）。行为不因该提示改变，只是把代价写在明处。

**删除边界与半开窗口**：窗口是半开 `[start, end)`，`deleteRangeInsert` 的天对齐上界取 `dayOf(end − 1ms)`（窗口内最后一个瞬时所在的自然日）——否则 `--until` 指定日期 / `windowEndClamp` 钳到昨天 0:00 这类「end 恰在日界」的窗口会多删**下一天**的行（`--since D0 --until D2` 的第二窗会删掉 D2 日已同步的行，而本轮不重拉）。`resolved_range` 的末端仍是**水位**（「上次成功推进到的时刻」），不是删除边界。

**窗口按上海日界对齐（`windowAlign: 'shanghaiDay'`，8 个 `stat_date` 主键报表任务）**：按天切片只约束窗宽，窗口**起点**仍来自水位续跑（`watermark+1ms`）或任意时刻的 `--since` —— 错相位窗（如 `[今天18:23, 明天18:23)`）只写一行 `stat_date=dayOf(start)`，拉到的却是跨两天的聚合值，且删除范围是两天 → 「明天」日的行被删掉而不重写，「每日概览」只在日对齐 run 下才是精确全天值。声明后：切片按上海日界网格推进（首窗 start 允许被钳到 range.start、末窗 end 钳到 range.end），水位续跑起点落到日界（水位所在日整体重拉）；单任务与轮转两条执行路径同一切片函数。`staff_attendance` 不声明——主键 `staff_id + hour_ts` 行集本身幂等，`stat_date` 只是辅助列，窗内小时行跨日无害；工单（3 天回看、任意起点）走原切片路径。`--full` 量级不变：起点 0（= 上海 1969-12-31 16:00）使首窗成为 16 小时残段（被钳到 range.start）、此后整日推进——窗数 = 起始上海日至今天数（与按天切片同量级，至多 +1）。

**空结果必须重试一次**（`staffAttendance` 实测偶发假空：同一 body 先返回空、重试恢复出全量）→ 引擎对空窗口先重试一次再判空，判空推进 `complete` 状态（空数据 ≠ 未同步）。

**实时快照不进报表同步**：`realtime_session` / `realtime_ipcc` 是快照接口，无历史回补能力，本阶段**不建同步任务**（`sync tasks` 输出中显式列出并注明 `unsupported: realtime`，而非沉默缺席——契约诚实性）。

### 5.3 会话导出（1，kind=windowed，四步流水线）

`sessions` 表 ← `export.session` 流水线，窗口 ≤6 天、水位用 **`endTime`**（导出按 endTime 过滤，判定式 `window.start <= endTime <= window.end`）：

1. **create**：`POST /openapi/export/session`，10 秒 6 次限频（唯一可靠流控；并发上限测不出）
2. **poll**：`export.session.check`（无限频）直到完成或 `14403` → 下载链接
3. **download+unzip**：解压密码 = appKey 前 12 字符
4. **parse**：JSONL 逐行解析，**跳过末尾非 JSON 尾行**（`startTime=...,endTime=...` 标记行）

正确性规则：
- 相邻窗口**重叠**（默认 1 天）——跨窗口长会话会被漏掉（实测 5 会话/16 消息）；重叠行由按 `session.id` 的 upsert 幂等吸收。**去重按 `session.id`，绝不能按导出任务 key**（服务端按（企业，窗口）复用结果，同参数重复创建返回不同 key 相同数据）
- 落库字段按导出 payload 实测全集（`private/raw/session.txt` 为验证样本，不入仓库）；`enrich` 派生 `session_type`（`staffId` 判别：`< -1` robot / `== -1` internal / `> 0` human——不用 `sType`）；`categoryDetail` 归一化（导出是 `" / "` 带空格，`/one` 无空格——本阶段只吃导出，归一化仍做，为 E 的 JOIN 铺路）
- **PII 列打 `sensitive: true`**（`userPhone`/`userName`/`userEmail`/`userAddress`/`fromIp`/`userIpCity`/`userCrmInfo`——blob 整体视为敏感）；脱敏是 CLI 输出层的事（E），存储层只负责标注
- 创建任务返回的 key 仅用于 poll/download，不落库

### 5.4 知识库（3，kind=snapshot + 本地增量）

| 表 | 接口 | 模式 |
|---|---|---|
| `knowledge_items` | `robot.data.knowledge` | **全量快照**（接口不接受时间参数）→ 落库后本地按 `updateTime` 维护增量视图字段；游标分页（`mid` 严格大于 + `size`≤1000，`isEnd=1` 终止；实测 12778 行/13 页） |
| `knowledge_points` | `robot.data.knowledge.point` | 全量快照，一次拉完 |
| `knowledge_categories` | `getCategoryTree` | 按 robotId 隔离（与 items 的全量并集语义不同，任务声明里分别标注） |

规则：
- 快照型任务的幂等来自「全量删除 + 重插」（事务内）——知识库是只读镜像，不是累积增量
- 计数会漂移：**测试断言不变量，不硬编码行数**
- `robotId` 被静默忽略的接口（items），任务声明里显式标注并校验调用参数不含 robotId（不透传误导性参数）
- `message` 是 JSON 字符串（信封 shape C）——`normalize()` 已处理，任务代码不再二次猜测
- 快照不会**静默丢行**：`projectRows` 丢弃缺键行时记 gap reason=`knowledge_row_malformed`（detail 含丢弃行数与任务 id）——全删重插下这些行已从表里消失，必须可查；会话导出（§5.3）两会话端窗口核对的两条 reason `export_fixture_unreported`（导出流未上报尾部标记行）与 `export_window_mismatch`（标记声明的窗口宽于请求窗口）同属这一体系，缺口 reason 在 `sync_gaps` 里可分派

### 5.5 工单域补充表（1）

`ticket_logs` ← `ticket.logs`（按工单拉日志；工单明细 `tickets` 的同步规则在 §5.2 末行，同为 windowed）——`ticket.search` 无日志时间，没有 logs 表就回答不了「张三昨天处理了多少工单」。水位沿用 tickets 的 op 窗口推进，日志按 `ticket_id + log_id` upsert。

## 六、引擎机制

### 6.1 窗口切分与调度

```
run(task):
  state = readSyncState(task)            # sync_state
  range = args.full ? 全历史 : (args.since/until 或 state.watermark+1 → now−安全余量)
  windows = sliceByMaxWindow(range, task.maxWindowDays, overlap)
  for window of windows:                 # 按天轮转（5.2 的调度内建于此层）
    await rateGate(task)                 # 持久化限频闸门（6.2）
    result = await task.fetch(window)    # http.call + normalize；写者重试在引擎层
    pairCheck(result.fetched, rows)      # 红线 2：行数配对
    await store.transaction(tx =>        # 红线 3：同事务
      task.write(tx, rows)
      advanceWatermark(tx, window.end)
      clearGap(tx, task, window))
  finish: range_status='complete'（全窗口成功）
```

- 每窗口独立 try/catch：失败记 `sync_gaps`（reason、range、error kind）后**继续下一窗口**（故障隔离——一个任务/窗口失败不影响其他）
- 断点续跑：`run` 启动时读 `sync_state`，pending 范围从水位续；`sync_gaps` 中记录的失败窗口可被 `sync run --full` 或自动重试覆盖
- 假空重试（5.2）在引擎层实现，任务不用各自写

### 6.2 限频持久化（rate gate）

现状：`core/ratelimit.ts` 的 `TokenBucket` 是进程内的；http 层撞桶抛 `local_rate_limit`。D 的增量：

- `src/sync/rate-limit-state.ts`：持久化「下次可调用时间」到本地库（`sync_state` 扩列或独立键值表，走 MIGRATIONS v2）——**命中限频（任何 `rate_limit` 类错误）后写入冷却截止时间；同路径后续调用先查库，未到点直接快速失败（不碰网络），`retry_after` 永远准确**（设计稿 §7.4 义务）
- `TokenBucket` 本体不动（core 层复用），D 在其外包装持久化读写
- 跨进程一致性以「读库判断」为准——毫秒级竞态可接受（保守方向：宁可多等一次冷却）

### 6.3 与 Store 的契约（C1 交付面）

- 单写者：`sync run` 以 rw 打开，进程退出释放（C1 `close()` 双 closeSync 已钉）；`sync status`/`verify` 以 ro 打开 + C1 读者退避
- **双轨契约**：数据语句经 `Store.upsert`/`execSql`，事务控制经 `transaction` 闭包直调；SQL 只允许代码内常量，字面调用点计数随 D 新增更新
- Store 方法**不得并发调用**（C1 契约）：引擎内所有落库串行 await
- 写者重试：C1 写者无内置重试——引擎对 `store_locked` 类错误自建重试（固定间隔，沿 C1 retry 模块），写者撞锁不无限等待（有界，超限记 gap）
- schema：D 新增全部数据表走 **MIGRATIONS v2+**（函数式迁移，C1 机制）；`sync_state` 加列（G2 字段，§八）同批迁移；表定义进 `TABLES`，PII 列 `sensitive: true`

### 6.4 中断与调度器

- 中断：事务边界即安全点；SIGINT 后当前窗口提交或回滚，进程干净退出（exit code 130 语义留给 errors 分派决定）
- `sync install`：按平台生成 launchd/systemd/schtasks/crontab 条目，**默认 dry-run 打印将写入的内容**，`--yes` 才执行；安装前必须先跑通一次 `sync run`（hint 指引）；跨平台矩阵沿设计稿 §7.6

## 七、命令输出契约（对 Agent）

`sync run` 成功（stdout JSON，`--pretty` 人读）：

```json
{
  "tasks": [{
    "task": "reports.overview", "status": "complete",
    "windows": { "total": 31, "succeeded": 31, "failed": 0 },
    "rows": { "fetched": 48695, "written": 48695 },
    "resolved_range": ["2026-09-14T00:00:00+08:00", "2026-10-14T00:00:00+08:00"],
    "watermark": "2026-10-13", "gaps": [], "notes": []
  }],
  "truncated": false
}
```

- 行数配对不符 → `"gaps": [{"range": [...], "reason": "count_mismatch", "detail": ...}]`，任务 `status: "partial"`，退出码仍 0（部分成功是成功完成的 run；全失败 → 1）
- **`gaps[].range` 与 `resolved_range` 同形态**（Asia/Shanghai 的 +08:00 ISO）——修复批 2 前 gap 输出 epoch 毫秒字符串，同一字段族两套形态
- **`notes`（修复批 2 新增）**：按任务的中文说明数组（恒在，常为空）。当前唯一生产者是「请求区间早于接口可得下界」（如 `tickets.search` 的 `opStart` 被服务端静默钳到 now−31 天）：这段历史上游物理上给不出，notes 把「区间不可得」与「同步故障」在输出里分开，绝不静默
- **`ok:true` 与退出码 1 的双轨语义（裁定）**：`ok` 表示「命令已产出结果」（stdout 是合法 JSON 的结果体），**退出码才是成败的权威判据**。因此全失败（退出码 1）与 `verify` 的 drift 非空（退出码 1）时 stdout 仍是 `{ok:true,data:...}` —— 结果体是**成功的输出**（缺口/漂移就是它要报告的内容），不是命令失败。Agent 一律先看退出码、再看 `data`；`{ok:false,error}` 只在命令无法产出结果时出现（usage/环境/内部错误）
- `sync status`：每任务一行 `{task, watermark, range_status, last_synced_at, resolved_range, gaps, gaps_count, locked}`
  - `resolved_range`（修复批 2 新增，G2）：上次成功推进覆盖的区间，形态与 run 的 `resolved_range` 一致（+08:00 ISO 二元组；从未成功推进/旧库为 null）
  - `gaps`（修复批 2 新增）：历史缺口逐条输出 `{range, reason, detail, recorded_at}`（`range` 原样回显 sync_gaps 的存储值）；`gaps_count` 保留为计数快照（既有消费者不破坏）
- `sync verify`：三方核对结果 `{task, local_rows, expected_from_api, state_windows_consistent, drift: [...]}`，drift 非空退出码 1。**`expected_from_api` 仅对快照任务有意义**（上游 fetch 的行数）；windowed 任务不做上游全量重拉（成本高），该字段恒为 `null`，核对方式为「本地行数 ↔ sync_state 成功状态」的一致性（`state_windows_consistent`）
- `sync tasks`：全部任务 + `{kind, table, watermark, maxWindowDays, overlapDays, primaryKey, sensitive_columns}`（含实时快照的 `unsupported` 标注）
  - **`enabled` 字段已移除（修复批 2 裁定）**：本阶段无启用/停用机制，全部任务总是执行 —— 输出一个恒为 `true` 的字段是「声明了但没人读」的契约噪声
  - `sensitive_columns`（修复批 2 新增）：该表标注 `sensitive: true` 的列名清单（来自 schema.ts 的列声明闭集）——这是 `sensitive` 标记在 D 阶段的运行时出口，Agent 据此知道哪些列不该 `SELECT *`

## 十一、验收清单
