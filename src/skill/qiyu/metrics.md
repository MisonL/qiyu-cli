# 指标语义协议

原始行数不等于业务实体数。以下三处如果直接把行数当答案，结果会**系统性偏高**，
而且不会报任何错。回答前先声明你用的是哪种语义；两种都要时分开报。

具体计数不要凭记忆——交给运行时：

```
qiyu db tables
qiyu sync tasks
qiyu query --table <表>
```

## 1. 知识库条目：知识点 vs 相似问

知识库条目数据集里混着两类行：

- **知识点行**：一个标准问题加一个答案，是「一个知识点」。
- **相似问行**：挂在某个知识点下的近似问法，**不携带答案**，只是同一知识点的另一种说法。
  它们与所属知识点共享同一个分组标识。

所以「有多少个知识点？」不能答条目数据集的原始行数——那会把相似问全算成独立知识点。
正确语义是**按分组标识去重后的数量**（等价于知识点行的数量）。如果人类确实要把相似问也算进去，
在结论里显式写明「含相似问，共 N 条问法」。

先跑一次按分组计数的查询确认口径，再回答；不要用「总行数 ÷ 2」之类的经验值。

## 2. 会话：人工会话 vs 机器人会话

会话数据集包含**机器人会话**，且机器人侧的很多字段恒为空（没有人工处理人、没有人工类目等）。
直接对全部会话聚合，会把机器人的量混进「人工客服工作量」，并且稀释类目分布。

- 会话类型是本地同步时按处理人编号派生出来的确定性列，不是上游字段。
- **报告人工客服工作量前必须按会话类型过滤**，排除机器人会话；报告「总咨询量」时可以说全量，
  但要写明含机器人。
- 机器人会话里处理人编号与机器人编号之间存在固定的符号关系（负数），可用于反推机器人编号，
  见 setup.md。
- 无效会话是哨兵值，不是类目：计算任何问题分布前必须排除，且哨兵的字面量是中文——按英文匹配
  一个都排除不掉。

## 3. 工单工作量：工单数 vs 日志条数

工单的操作日志按「动作」逐条记录：一个人连续改 8 个字段就是 8 条日志，关一次单可能产生多条
关闭记录。所以「张三昨天处理了多少工单」的正确语义是**不同的工单数**，不是日志条数。

另外两件事会扭曲这个指标：

- **系统操作会混进来**：自动流转、自动关闭以系统账号身份记日志；不排除系统账号，
  它会在排行榜上常年霸榜。
- **自然日按上海时区算**：UTC 容器里的「昨天」会差 8 小时，且不会报错。

## 4. 知识库还有一处语义分叉：并集 vs 隔离

条目数据集是**跨全部机器人的并集**，而分类树是**按机器人隔离**的。因此：

- 「某个机器人有哪些知识分类」——查该机器人的分类树，**不要**从条目数据集的分类字段反推
  （那会把别的机器人的分类混进来）。
- 条目数据集里机器人编号是承重字段：按机器人切片先按它过滤。

## 5. 通用做法

1. 先声明语义：「按知识点去重」还是「原始行数」、「人工会话」还是「含机器人」。
2. 用 `qiyu query --table <表>` 的 `--group-by` 做分组计数，让命令给出分组后的数，而不是自己拿
   行数做除法。
3. 结论里同时写出语义、时间窗口与数据覆盖区间——三者缺一，数字就不可复核。
