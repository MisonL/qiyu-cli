# 查询接口与沙箱（db / query / stats）设计

> 状态：v1 草案（2026-10-17）
> 依据：`docs/qiyu-cli-design.md` §8（查询接口与沙箱，含 §8.2 攻击表与三层防护）、§6.5（PII 实测清单与脱敏决策）、§9.1（输出信封）、§9.2（静默失败防护）、§9.3（时区）、§11（Skill 不硬编码事实）；`docs/superpowers/specs/2026-10-09-后续交付路线图-design.md` §四.E（验收判据「沙箱三层缺一不可」）、§五.2（`describe(table)` 归 E）、§八.6（`category` 字段归 G1）；C1 存储层 spec §十二.3（沙箱落点与 `TABLES` 扩展的开放问题）；D 同步引擎 spec §七（输出契约形态）。
> 前置：C1（存储层）✅、D（同步引擎）✅。本 spec 是 F（Skill）与 G2（剩余静默失败防护）的前置。
> 实测环境：node v24.19.0 / macOS 26.6.1（Darwin 25.6.0）/ @duckdb/node-api 1.5.6-r.1。本 spec 的「已实测」均出自 2026-10-17 的 10 组探针（脚本不入仓库），逐条注明探针编号；「推断」与「未覆盖」单独标注。

## 一、目标与非目标

**目标**：让 Agent 不靠猜就能用本地数据仓库——`db tables` / `db describe` 回答「有哪些表、哪些列、哪些是 PII」；`query --sql` / `query --table` 回答数据问题，且**三层只读沙箱缺一不可**；`stats fields` 回答「这个指标的单位与哨兵值」。**默认脱敏，原始值必须显式请求**。

**非目标**（沿路线图 §九与设计稿范围）：
- 不做写通道：查询命令一律只读；`--sql` 不接受任何非 SELECT/EXPLAIN 语句，也不提供 `--allow-write` 之类的逃生门
- 不做加密存储（设计稿 §6.5 明确范围之外）
- 不做 `--pretty`（归 G1；本 spec 的查询命令与既有命令同答：显式拒绝）
- 不做查询缓存、不做 SQL 方言适配层（DuckDB 即方言）
- 不替 Agent 猜指标语义：`stats fields` 只输出有出处的声明，其余如实置 null（§九）

**验收总纲**：设计稿 §8.2 攻击表的每一行在 CLI 上被拦；三层中任意一层单独失效时其余层仍兜底（测试用对照实例钉死「缺一不可」）；默认输出中 PII 已被脱敏；0 行结果附带可操作警告；表/列不存在给出候选而非 DuckDB 英文原文。

## 二、三条设计红线（E 版本，违反即架构错误）

### 红线 1：沙箱三层缺一不可——每层单独都有实测穿透

设计稿 §8.2 的攻击表不是理论推演：在**无防护**的 DuckDB 上九类攻击全部成功（设计稿实测）。本 spec 的探针进一步证明**任意单层都不够**：

- **仅 layer3（`access_mode=READ_ONLY`）**：`read_csv` 成功读取、`COPY TO` 成功**且文件真的被创建**（探针 2 复证）——只读模式只拦库内 DML/DDL，拦不住文件系统与网络
- **仅 layer1（语句白名单）**：`PRAGMA database_list`、`PRAGMA table_info`、`DESCRIBE`、`SHOW` 都被报告为 `statementType=1`（SELECT）（探针 8/10）——白名单会放行它们；`PRAGMA enable_external_access=true` 被报告为 20（SET）可拦，但 PRAGMA 面太宽，不能指望枚举
- **仅 layer2（`enable_external_access=false` + `lock_configuration=true`）**：库内写操作不受它约束（它管文件/网络，不管 DML）

三层各管一个面：layer1 管「语句类型」、layer2 管「文件与网络」、layer3 管「库内写」。**任何一层被删掉，攻击表里就有一行重新穿透**。测试必须用对照实例逐层验证（§十三）。

### 红线 2：默认脱敏——原始值必须显式请求，脱敏缺口必须写在明处

设计稿 §6.5 的决策是「默认脱敏；只有 `--no-mask` 才输出原始值」，理由是该数据会被 Agent 写入日志、报表与对话上下文。本 spec 追加一条：**脱敏不是尽力而为，是默认契约；凡静态无法判定的场景，必须在输出里声明缺口**，不得静默放行。

`query --table` 通道的脱敏是**精确的**（结果列来自 `TABLES` 声明，逐列命中 `sensitive: true`）；`query --sql` 通道是**有边界的**（任意 SQL 无法静态判定列血缘，别名 `SELECT userPhone AS p` 会绕过列名匹配）——边界与兜底见 §七，**不假装完美**。

### 红线 3：0 行 ≠ 没有数据；未知 ≠ 猜

设计稿 §9.2：0 行是比报错危险得多的失败模式——Agent 的错误处理不会触发，它会向人类汇报「上周没有满意度数据」。E 的每个出口都必须能自证：

- 时间过滤 0 行 → `meta.warnings` 附可操作提示（查 `sync status` 的覆盖区间）
- 表/列不存在 → 中文消息 + 候选列表（解析 DuckDB 原生报错的候选，或从 `TABLES` 计算）
- 单位不确定 → `stats fields` 的 `declared.unit` 带 `source` 标明「实测/文档/命名推断」，**推断要标明是推断**；无出处的一律 null
- 声明与实况不一致（`TABLES` vs `information_schema`）→ `meta.warnings` 显式暴露（§八）

## 三、命令面

```
qiyu db tables                    # 表清单 + 粒度 + 行数 + 数据时间范围 + PII 列
qiyu db describe <table>          # 列名、类型、可空、敏感标记、观测枚举、时间列、单位
qiyu query --sql "SELECT ..."     # 任意只读 SQL（三层沙箱 + 默认脱敏 + 行数上限 + 超时）
qiyu query --table <t> [--since T] [--until T] [--group-by COL ...]
                                  # 受约束查询通道（列白名单、时间列语义化、精确脱敏）
qiyu stats fields <table>         # 指标自描述（声明 + 本地观测分布 + -1 哨兵）
```

通用约定（沿 C1/D 命令层惯例，`src/commands/store.ts` 形态）：
- `--help` / `-h` → stdout 用法、退出码 0；`--pretty` → `usageFail('--pretty 尚未实现…')`（与既有命令同答，归 G1）
- 未知子命令/未知参数/值位守卫 → `usageFail`（退出码 2）
- 存储定位：`--db <path>` / `--profile <name>` / `--backend <name>`，环境变量 `QIYU_DB_PATH` / `QIYU_PROFILE` / `QIYU_STORE_BACKEND`（复用 `resolveStoreConfig`，`src/store/config.ts`）
- 库不存在 / 缺 `schema_version` / 被写进程持锁 → 沿 C1/D 的 `store_not_initialized` / `store_locked`，hint 一律指 `qiyu store init`
- 时间参数（`--since` / `--until`）复用 `parseTimeArg`（`src/commands/sync-run.ts:86`）：`Nd` / `yesterday` / `YYYY-MM-DD` / ISO 8601，按 `Asia/Shanghai` 解析，输出回显 `resolved_range`

## 四、元数据扩展（`TABLES` 是唯一权威）

C1 spec §十二.3 的开放问题裁决：**`db describe` 消费 `TABLES` 并扩展 `ColumnDef`，不重复定义表结构**。本 spec 在 `src/store/schema.ts` 上做**纯 TypeScript 侧**扩展（不产生 DDL、不新增迁移，见 §十二）：

```ts
// ColumnDef 追加（全部可选）
observed_enum?: string[]   // 实测观测到的取值集合——命名刻意不叫 enum：设计稿多次证明观测集不完整
unit?: string              // 列级单位（本期仅极少数列有意义；payload 内的字段级单位归 stats fields）
note?: string              // 一句话语义（如「派生列：staffId 数字判别」）

// TableDef 追加（全部可选）
grain?: string             // 粒度描述（如「每个会话一行」「每客服每小时一行」）
timeColumn?: { name: string; kind: TimeColumnKind }
// TimeColumnKind = 'iso-day' | 'iso-instant' | 'epoch-ms'
```

`timeColumn` 的三种形态来自 D 的存储实况（**已实测/已读代码**）：

| kind | 存储形态 | 用它的表 | 比较方式 |
|---|---|---|---|
| `iso-day` | `shanghaiDayIso()` 产出的上海日零点 ISO（如 `"2026-09-14T16:00:00.000Z"` = 上海 9/15 零点），字典序即时序 | 9 张报表表的 `stat_date`（`daily_overview` / `staff_workload` / `staff_quality` / `staff_satisfaction` / `staff_attendance` / `order_performance` / `staff_salary_detail` / `robot_summary` / `transfer_human`）；`staff_salary_detail` 另有 `work_date`（同为 iso-day，本期 `timeColumn` 取 `stat_date`） | `--since` **向下取整到上海自然日**（`shanghaiDayIso(sinceMs)`）——若直接用 `sinceMs.toISOString()`，一个 9/15 12:00 的 since 会把 9/15 全天的行（`stat_date` = 9/14T16:00Z）排除在外 |
| `iso-instant` | `new Date(n).toISOString()` 的整点 ISO | `staff_attendance.hour_ts` | 直接字符串比较（同格式 ISO 字典序即时序） |
| `epoch-ms` | 上游原值经 `strOrNull` 落库：数字被 `JSON.stringify` 成毫秒数字串（`src/sync/tasks/sessions.ts:22`） | `sessions.startTime`（查询语义 = 会话开始时间；**与同步水位的 `endTime` 不同**，水位用 endTime 是因为导出按 endTime 过滤） | `TRY_CAST("startTime" AS BIGINT) >= ?`——非数字行被排除，不静默参与比较 |

没有 `timeColumn` 的表（维度表、工单、知识库、元数据表）不支持 `--since`/`--until`，给出可用表清单（§十一）。`db tables` 的「数据时间范围」= 对 `timeColumn` 跑 `MIN`/`MAX`；`epoch-ms` 列在 JS 侧转上海 ISO 输出。

`grain` 为 25 张表逐一声明（内容来自设计稿 §6.2/§7.5/§10 的实测粒度，plan 阶段落文本）。

## 五、`query --sql`：三层只读沙箱

### 5.1 沙箱落点（C1 开放问题裁决）

落在**新目录 `src/query/`**（`query/sandbox.ts`），不经 `Store` 接口。理由：C1 的 `Store` 是后端无关抽象（`src/store/types.ts:2` 明文「不得出现任何 DuckDB 类型」），而三层沙箱需要 `extractStatements` / `prepare().statementType` / `interrupt` / 每连接 `SET` —— 这些都是 DuckDB 专属原语。把它们加进 `Store` 会污染 C2 的外部后端契约；放进 `store/` 又会让「store 层只管存储」的边界变形。

`query/` 可以 import 的 store 侧模块：`store/schema.ts`（元数据，纯数据）、`store/config.ts`（配置解析，纯函数）、`store/retry.ts`（ro 锁退避，纯函数）。**不 import `store/duckdb.ts` 的 `Store` 实现、不 import `sync/`、不 import `commands/`**（分层规则进 `tests/store/layering.test.ts`，§十三）。`@duckdb/node-api` 在 `query/sandbox.ts` 内 **dynamic import**（与 `store/duckdb.ts:20` 同款惰性边界），依赖缺失时给出与 store 相同的安装指引。

### 5.2 打开与加固（顺序敏感，已实测）

**只有一个执行入口**：`query/` 暴露的沙箱会话只有 `run(sql, { params?, limit })` 一个方法，`db tables` / `db describe` / `stats fields` 的代码内 SQL 也走它——**不存在「可信 SQL 绕过白名单」的旁路**。这些 SQL 全是单条 SELECT，白名单自然放行；旁路 API 本身就是攻击面，不提供。

```
1. DuckDBInstance.create(path, { access_mode: 'READ_ONLY' })   // layer3
2. connect()
3. SET TimeZone='Asia/Shanghai'
4. SET memory_limit='1GB'
5. SET enable_external_access=false                            // layer2
6. SET lock_configuration=true                                 // layer2 锁死
7. 自检：SELECT current_setting('enable_external_access'), current_setting('lock_configuration')
   —— 任一不符即拒绝服务（防 DuckDB 未来改名导致静默失效）
```

实测约束（探针 3/6/10）：
- **顺序敏感**：`TimeZone`/`memory_limit` 必须在 `lock_configuration` 之前设；lock 之后连 `SET TimeZone='UTC'` 都报 `Cannot change configuration option "TimeZone" - the configuration has been locked`（探针 6）
- **配置是实例级而非连接级**：同实例新连接继承 layer2 设置与锁；**不同实例（同一文件）不受影响**（探针 3）。因此设计稿 §8.2 坑 1「必须在每个连接上设置」的准确表述是「**每个进程/实例首次连接时设置并锁定**」——本 spec 修正该措辞
- 自检输出实测：`ea=false, lc=true, ml="953.6 MiB"（1GB 的显示值）, tz="Asia/Shanghai"`（探针 10）
- ro 打开撞写锁的退避复用 `store/retry.ts` 的 `retryWithBackoff` / `isLockError`（`readOnlyRetryMs` 默认 30000），超限 → `store_locked`，与 C1/D 同口径

`memory_limit='1GB'` 为硬编码常量（YAGNI，不设配置项）：实测 128MB 下大排序报 `Out of Memory Error`、1GB 下 `range(1e8)` 聚合可完成（探针 8/9）——1GB 足以覆盖本库任何表（最大表 31 天考勤约 1.7 万行），同时防跑飞。

### 5.3 执行管线（layer1）

对每条用户 SQL：

```
1. extractStatements(sql)
   · count === 0 或 extractStatements 抛异常（空串/纯空白/纯注释/';' 均实测抛
     "Error in native callback"）→ usage「SQL 为空或无有效语句」
   · count > 1 → usage，code=sandbox_blocked（多语句：'SELECT 1; DROP TABLE t' 实测每条都执行）
   · 'SELECT 1;;' / 尾分号 / 尾注释 → count=1，放行（探针 10）
2. prepare(0)
3. statementType ∈ { 1 (SELECT), 4 (EXPLAIN) } → 放行；其余一律 usage + code=sandbox_blocked
   · DESCRIBE / SHOW / PRAGMA table_info / PRAGMA database_list 也被报告为 1（探针 8/10）——
     它们是只读形态，放行；真正危险的是 17（PRAGMA force_checkpoint 等）与 20
     （PRAGMA enable_external_access=true 也报告为 20）——被拦
   · **type=4 追加内层闸门：拒绝一切带 ANALYZE 的 EXPLAIN**（`EXPLAIN ANALYZE …`、
     `EXPLAIN (ANALYZE …) …`，含 `ANALYZE false` 形态——实测同样执行内层）。理由（探针 16）：
     EXPLAIN ANALYZE **会真正执行内层语句**，而内层 `CALL enable_profiling()` 修改的是
     实例级配置——不碰文件（layer2 不管）、不是库写（layer3 不管），实测把后续每条查询的
     profile 树打到 stdout，直接破坏「stdout 只出 JSON」的契约。**纯 EXPLAIN（无 ANALYZE）
     不执行内层**（实测 `EXPLAIN CALL enable_profiling()` 前后配置不变），放行
   · 检测方式：剥掉注释与字符串字面量后，对 type=4 的语句文本查 `\bANALYZE\b` 记号。
     字符串字面量里的 "ANALYZE" 不会误报；列名恰叫 analyze 且被 EXPLAIN 的极端情形会
     误拒（fail closed，可接受，hint 说明去掉 ANALYZE 即可）
   · 其余内层写操作（INSERT/COPY 等）仍由 layer2/3 兜底——这正是「三层缺一不可」的
     实证场景，验收用例单列
4. runAndReadUntil(limit + 1) → 行数 > limit 即 truncated，输出 slice(0, limit)
   · 实测 runAndReadUntil **不精确限行**：请求 10 行返回 2048 行、请求 5000 返回 6144
     （按 chunk 倍数读）；请求数超过结果总数时返回真实行数（请求 4 行、表 3 行 → 返回 3）
   · 因此**不用 SQL LIMIT 包装**（包装需剥尾分号/尾注释，`SELECT 1; -- x` 会炸），
     用 reader 多读一行 + JS 截断：返回行数 > limit 当且仅当结果确实多于 limit
5. 序列化走 getRowObjectsJson()（JSON 安全值，实测 DATE→"2024-01-02"、
   TIMESTAMP→"2024-01-02 03:04:05"、INTERVAL→{months,days,micros}、DECIMAL→"1.50"、
   HUGEINT→字符串、LIST→数组、STRUCT→对象；重名列去重为 "a" 与 "a:1"，探针 6/9）
```

`--limit`：默认 1000，取值 1–10000，`--limit 0` / 负数 / 非整数 → usage。`--timeout <秒>`：默认 30，0 = 无超时；超时调 `conn.interrupt()`（实测约 300ms 生效，中断后连接仍可用，探针 6/9），映射 `query_timeout`（§十一）。

## 六、`query --table`：受约束通道

参数：`--table <t>`（必填）、`--since T` / `--until T`（可选，复用 `parseTimeArg`）、`--group-by <col>`（可重复，可选）、`--limit` / `--timeout`（同 §五）。`--sql` 与 `--table` 互斥且至少给一个，否则 usage。

SQL 构造**全部由代码常量 + 白名单标识符拼接**（外部字符串只进 `?` 参数位）：

```sql
SELECT * FROM "t"                                              -- 无 --group-by
SELECT "g1", "g2", COUNT(*) AS count FROM "t"                  -- --group-by
  WHERE <timeColumn> >= ? AND <timeColumn> <= ?                -- --since/--until（见 §四 kind 规则）
  GROUP BY "g1", "g2"
```

- `--group-by` 的列必须在该表 `TABLES` 列集内（未知列 → usage + 该表列清单）；列名加双引号拼接前先经闭集校验，**不存在注入面**
- `--since` 无 `--until` → 上界 = 当前时刻；`--until` 无 `--since` → 下界 = 该表数据最早时刻（MIN）—— 两者都回显 `resolved_range`
- `iso-day` 列的上界：`--until` 所在上海日的日零点 ISO（含当天）；下界：`--since` 所在上海日的日零点 ISO（含当天，见 §四）
- 结果脱敏**精确**：输出列 ⊆ 该表列，逐列按 `TABLES.sensitive` 命中（§七）
- `meta` 携带 `resolved_range`（给了 --since/--until 时）与 `data_coverage`（该表 `timeColumn` 在过滤范围内的 MIN/MAX；无 timeColumn 的表为 null）

## 七、脱敏（默认开启）

### 7.1 规则

`sensitive: true` 的列在输出时按以下规则转换（设计稿 §6.5 的三条 + 本 spec 补齐无格式列）：

| 值的形态 | 转换 | 示例 |
|---|---|---|
| 手机号（`^1\d{10}$`） | 前 3 后 4，中间 `****` | `138****1234` |
| 邮箱（`^[^@\s]+@[^@\s]+$`） | 首字符 + `***` + 完整域名 | `a***@x.com` |
| IPv4（`^\d{1,3}(\.\d{1,3}){3}$`） | 末段打码 | `10.2.3.*` |
| 其余（姓名/地址/`userCrmInfo`/`payload` 等） | **整值替换为 `<已脱敏>`** | — |

`payload` 列是整行 JSON 副本（含全部 PII，C1/D 已标注），逐字段脱敏需要按表枚举 JSON 键——不可维护且随上游字段漂移失效；**整值替换是唯一不会漏的规则**。需要 payload 内字段时用 `stats fields`（聚合统计，不输出单值）或 `--no-mask` 显式承担风险。

### 7.2 两条通道的覆盖与缺口（写在明处）

- `--table` 通道：**精确**。结果列名来自 `TABLES`，与 `sensitive` 标记一一对应，无别名
- `--sql` 通道：**两层**
  1. **列名级**（主防线）：输出列名 ∩ 全部表 `sensitive` 列的**列名并集**（`userPhone`/`userName`/`userEmail`/`userAddress`/`fromIp`/`userIpCity`/`userCrmInfo`/`crmUserName`/`crmUserPhone`/`crmUserEmail`/`userMobile`）→ 命中即按 §7.1 脱敏。**`payload` 刻意不在并集内**：报表表的 payload 是聚合数字 JSON，列名级会把它们整列误杀；会话/工单的 payload 含 PII 则靠第 2 层 JSON 值级检测兜底（实测手机号 99% 行存在，足以命中）。这是显式取舍，不是遗漏
  2. **值级兜底**（只对未被列名命中的列做）：字符串值匹配手机号/邮箱/IPv4 模式 → 按 §7.1 转换。覆盖 `SELECT userPhone AS p` 这类别名绕过；**姓名/地址无法值级检测，别名场景仍会漏**——这是静态无法消除的缺口

**缺口声明**：当 SQL 文本中出现敏感列名、但该名字不在输出列名中时（典型：`SELECT userPhone AS p`、`concat(userName,'x') AS n`），`meta.mask_warnings` 附一条：「SQL 引用了敏感列 X，但输出列名不匹配；脱敏可能不完整，建议用 `qiyu query --table` 或保持列名原样」。这是警告不是防护——README 与 Skill（F）必须写明 `--sql` 的脱敏边界。

`--no-mask`：关闭两条通道的全部脱敏，`meta.masked=false` + `meta.warnings` 追加「输出包含未脱敏的客户 PII；不要写入日志或对外报表」。`db tables` / `db describe` 不输出行数据，无 `--no-mask`。

`meta.masked_columns` 恒在（本次实际脱敏的列名清单，可为空数组）——Agent 可据此判断输出是否被改写。

## 八、`db tables` / `db describe`

### 8.1 `db tables`

```json
{
  "ok": true,
  "data": { "tables": [
    { "name": "sessions", "rows": 4687, "grain": "每个会话一行（含机器人/人工/内部）",
      "time_range": { "min": "2026-08-15T00:00:00+08:00", "max": "2026-10-14T00:00:00+08:00" },
      "pii_columns": ["payload", "userPhone", "userName", "userEmail", "userAddress", "fromIp", "userIpCity", "userCrmInfo"] },
    { "name": "schema_version", "rows": 9, "grain": "迁移版本记录（每版本一行）", "time_range": null, "pii_columns": [] }
  ] },
  "meta": { "notice": "本数据库包含客户 PII；不要将其写入日志或对外报表", "warnings": [] }
}
```

- 清单以 `TABLES` 为权威（含 25 张：元数据表 3 + 维度 6 + 报表 9 + 工单 2 + 会话 1 + 知识库 3 + tags）
- `rows` 逐表 `COUNT(*)`；`time_range` 按 §四的 `timeColumn` 计算（无时间列 → null）；`epoch-ms` 列在 JS 侧转上海 ISO
- `meta.notice` 恒在（设计稿 §6.5 要求 `db tables` 必须带 PII 提示）
- **一致性核对**：把 `TABLES` 声明与实际库表集（`information_schema.tables`）比对，不一致 → `meta.warnings` 逐条列出「声明有而库中无 / 库中有而声明无」——声明与实况的差异不得静默

### 8.2 `db describe <table>`

```json
{
  "ok": true,
  "data": {
    "table": "sessions",
    "grain": "每个会话一行（含机器人/人工/内部）",
    "primary_key": ["session_id"],
    "time_column": { "name": "startTime", "kind": "epoch-ms" },
    "row_count": 4687,
    "time_range": { "min": "...", "max": "..." },
    "columns": [
      { "name": "session_type", "type": "VARCHAR", "nullable": true, "sensitive": false,
        "unit": null, "observed_enum": ["robot", "internal", "human"],
        "note": "派生列：staffId 数字判别；null = 未知形态（staffId=0 或非数字）" },
      { "name": "userPhone", "type": "VARCHAR", "nullable": true, "sensitive": true,
        "unit": null, "observed_enum": null, "note": null }
    ],
    "pii_columns": ["payload", "userPhone", "userName", "userEmail", "userAddress", "fromIp", "userIpCity", "userCrmInfo"]
  },
  "meta": { "notice": "本数据库包含客户 PII；不要将其写入日志或对外报表", "warnings": [] }
}
```

- 列清单以 `TABLES` 为权威（`sensitive`/`observed_enum`/`unit`/`note` 只在那里）；实际列集经 `information_schema.columns` 核对，不一致 → `meta.warnings`（如「表 X 实际多列 a、少列 b——可能来自旧版 CLI 或库损坏」）
- `<table>` 未知 → usage + 候选列表（前缀/编辑距离匹配 `TABLES` 表名）
- `observed_enum` 只填**有实测出处**的列（如 `sessions.session_type`、`sync_state.range_status`、`staff.role`/`status`、`knowledge_items.type`）；命名刻意用 `observed_enum` 而非 `enum`——设计稿 §10.5 明确「所观察到的枚举取值集合是不完整的，不要基于它们做校验」

## 九、`stats fields <table>`

### 9.1 输入约束

`<table>` 必须是**报表域表**（`daily_overview` / `staff_workload` / `staff_quality` / `staff_satisfaction` / `staff_attendance` / `order_performance` / `staff_salary_detail` / `robot_summary` / `transfer_human` 之一，均有 `payload` 列）。其它表 → usage + 可用表清单。理由：字段自描述只对「业务字段收敛进 payload」的报表域有意义；会话/工单的 payload 是 PII 副本，统计它没有价值且扩大暴露面。

### 9.2 输出：声明与观测分离

```json
{
  "ok": true,
  "data": {
    "table": "daily_overview",
    "sentinel": { "value": -1, "meaning": "该窗口或筛选条件没有匹配到数据（设计稿 §6.2 实测：报表面族统一哨兵，厂商未文档化）" },
    "declared": {
      "assignedRatio": { "unit": "ratio", "higher_is_better": null, "source": "name-suffix", "note": null },
      "sessions":      { "unit": "count", "higher_is_better": null, "source": "name-suffix", "note": null }
    },
    "observed": [
      { "field": "assignedRatio", "rows_present": 31, "minus_one": 0, "nulls": 0, "min": 0.912, "max": 0.987 },
      { "field": "sessionInviteRatio", "rows_present": 31, "minus_one": 31, "nulls": 0, "min": null, "max": null }
    ],
    "unknown_fields": ["carrier", "nameSpell", "…"]
  },
  "meta": { "warnings": [] }
}
```

- **`declared`**：来自代码内受控目录 `src/query/metric-catalog.ts`。每条声明**必须带 `source`**：
  - `'design-doc'` = 设计稿实测明说（如 `-1` 哨兵、`loginDuration` 毫秒）
  - `'name-suffix'` = 按字段名后缀推断（`*Ratio`/`*Radio`→`ratio`、`*Count`/`sessions`→`count`、`*Duration`/`*Time`→`ms`）——**标明这是命名推断，不是实测**
  - `higher_is_better` **没有任何上游来源**（设计稿从未给出）→ 一律 `null`，除非未来有实测依据；不猜
- **`observed`**：从本地库的 `payload` 派生（原型 SQL 已实测，探针 6）：`json_keys + unnest + TRY_CAST(json_extract_string(payload, '$."'||k||'"') AS DOUBLE)`，逐字段输出 `rows_present / minus_one / nulls / min / max`。这是**数据分布**，不是语义
- **`unknown_fields`**：目录未声明但观测到的字段，如实列出——Agent 知道「哪些字段没有单位信息」
- 空表 → `observed: []` + `meta.warnings`「该表无数据；先运行 `qiyu sync run`」
- 字段名含特殊字符时 JSON 路径加引号（`$."a b"`，探针 6 验证）

## 十、输出契约（对 Agent）

- 信封：成功 `{ok:true,data,meta}`（`data` 恒在）；失败 `{ok:false,error}`；stdout 只出 JSON、stderr 镜像；退出码 0/1/2/3/4（沿 `src/output.ts`）
- `meta` 字段族（恒在或按条件）：

| 字段 | 出现条件 | 含义 |
|---|---|---|
| `rows` / `truncated` / `limit_applied` | query 两通道 | 实际返回行数（截断后）/ 是否被 limit 截断 / 生效的上限 |
| `resolved_range` | `--table` 给了 --since/--until | 上海 +08:00 ISO 二元组（与 sync 同形态）|
| `data_coverage` | `--table` 有 timeColumn | 该表时间列在过滤范围内的 MIN/MAX；`--sql` 通道恒为 null（任意 SQL 无法通用判定覆盖，不猜）|
| `masked` / `masked_columns` / `mask_warnings` | query 两通道 | 脱敏状态 / 实际脱敏列 / 静态缺口警告（§7.2）|
| `warnings` | 0 行 / 声明与实况不一致 / 空表等 | 可操作提示数组（恒在，可为空）|
| `notice` | `db tables` / `db describe` | PII 提示（设计稿 §6.5）|

- **0 行警告的触发**：`--table` 给了 `--since`/`--until` 且结果 0 行；`--sql` 文本匹配 `\b(stat_date|work_date|hour_ts|startTime|endTime)\b` 且结果 0 行。文案示例：「查询在区间 [A, B] 返回 0 行。这不代表没有数据：同步可能未覆盖该区间——用 `qiyu sync status` 查看覆盖范围，或放宽过滤条件」
- `ok:true` 与退出码的双轨语义沿 D spec §七：结果体是成功的输出，退出码才是成败权威

## 十一、错误处理与分派

| 场景 | kind | code | 退出码 | message/hint 要点 |
|---|---|---|---|---|
| SQL 空/纯注释/`;` | `usage` | `query_error` | 2 | 「SQL 为空或无有效语句」|
| 多语句（count>1） | `usage` | `sandbox_blocked` | 2 | 点明「一次只接受一条语句」（多语句实测每条都执行）|
| statementType 非 {1,4} | `usage` | `sandbox_blocked` | 2 | 点明类型名（COPY/ATTACH/SET/CALL/PRAGMA(17)…）|
| layer2 拦截（`Permission Error: … disabled by configuration`） | `usage` | `sandbox_blocked` | 2 | 「该语句尝试访问文件或网络，已被只读沙箱拦截」|
| 表/列不存在 | `usage` | `query_error` | 2 | 中文包装 + 候选（解析 `Did you mean "x"?` / `Candidate bindings: "y"`；无候选时从 `TABLES` 计算）|
| SQL 语法错 / 未绑参 | `usage` | `query_error` | 2 | 中文包装 + 底层原文（DuckDB 原生错误自带表/列候选，探针 7）|
| 超时 | `query_timeout`（**新增 kind**）| `query_timeout` | 1 | hint：缩小时间范围、加过滤条件或调 `--timeout` |
| `--table` 未知表 / `--group-by` 未知列 / 无时间列却给 `--since` | `usage` | `query_error` | 2 | 附候选清单 |
| 库不存在/缺表/被锁 | `store_not_initialized` / `store_locked` | 同 kind | 1 | hint 指 `qiyu store init`（C1/D 同口径）|
| 其它 DuckDB 执行期错误 | `internal` | `internal` | 1 | 中文包装 + 底层原文（沿 `thrownToExit`，不裸透英文）|

`src/core/errors.ts` 的 `ErrorKind` 闭集追加 `query_timeout` 一项（路线图 §五.4 要求扩展 kind 时同步更新）。`query_timeout` 不进 `exitCodeFor` 的特殊分支 → 退出码 1。

## 十二、schema 变更：无迁移

`ColumnDef` / `TableDef` 的扩展（§四）是**纯 TypeScript 元数据**，不进 `ddlFor()`、不产生 DDL、**不新增 MIGRATIONS 条目**。现有库无需任何操作即可被 E 读取。`ddlFor` 只读 `name/type/nullable`，扩展字段对它不可见——需在 plan 中加断言防回归（扩展字段若误入 DDL，会破坏 C1/D 的迁移幂等）。

`tests/store/schema.test.ts` 里 `toEqual({name,type,nullable,sensitive})` 形态的严格断言若因新增可选字段变红，按「测试为权威」修订为逐键断言（不削弱语义）。
