# 测试耗时优化 —— 方案

> 背景：用户要求「npm test 慢的问题要优化一下」。
> 基线（本机 16 核 / 64 GB，2026-10-20 实测，load avg 15-30 时）：
> - **单进程全量：111.6s**，峰值 RSS **456 MB**
> - **4 分片并行：51.5s**（2.2× 提速），每片内部仍 `--maxWorkers=1`
> - 53 个测试文件 / 1162 条用例

## 一、事故防护红线不动

`vitest.config.ts` 的 `maxWorkers: 1` + `fileParallelism: false` 是 2026-10-05 内存耗尽事故的防护：

> 一份变异扫描脚本**循环**调用 `npx vitest run`（未限 worker 数），vitest 按 16 核起满 worker，
> 某条变异让数组无界增长，三个 worker 各涨到约 16 GB，64 GB 内存耗尽 —— macOS Jetsam 杀掉 1414 个进程。

**根因是「无界循环 × 无界增长」，不是「并发」本身。** 本方案严格保留每片内部的单进程单 worker，
且**分片数是固定值**（不是循环调用 vitest），因此不构成同类风险。

## 二、方案：固定分片 runner

新增 `scripts/test-shards.mjs`：

- 扫描 `tests/**/*.test.ts`，按**文件大小降序**贪心装箱到 N 片（重量不均时自动平衡）
- 每片启动一个 `vitest run --maxWorkers=1 --no-file-parallelism <该片文件>` 子进程
- **N 由环境变量 `QIYU_TEST_SHARDS` 控制，默认 4**（固定上限，不随 CPU 数放大）
- 任一片非零退出 → 整体非零退出
- 全部跑完后打印每片耗时与合计

**为什么默认 4 而不是 16**：16 片会让 16 个 vitest 进程同时起（每进程带 Node + 转换缓存），
逼近事故那天的并发形态。4 片在 16 核机器上是 1/4 占用，内存实测每片峰值 < 500 MB。

## 三、命令行与 CI

```bash
npm test                      # 4 分片并行（约 51s）
QIYU_TEST_SHARDS=1 npm test   # 单片（等价于原行为，约 111s）
QIYU_TEST_SHARDS=8 npm test   # 更多分片
```

CI 保持 `npm test`（即 4 分片）。GitHub runner 是 2 核，分片反而更慢——
**故 CI 显式设 `QIYU_TEST_SHARDS=1`**，并把分片能力留给本地开发。

## 四、同时降低单文件耗时（可选收益）

剖析出的两个热点：

| 文件 | 单跑耗时 | 主因 |
|---|---|---|
| `tests/commands/sync.test.ts` | 33s | 45 条用例各建真 DuckDB 库（69-428ms/次）＋ 21 任务端到端 |
| `tests/commands/query.test.ts` | 11s | 1 条 `--timeout 0` 用例 4.3s（两条确定性 >1s 查询 + 3 次子进程锁探针 406ms/次） |

但**这两条都不动**：它们各自钉着真实行为（锁释放、timeout 语义、21 任务故障隔离），
改小断言会削弱覆盖。分片已经把它们分到不同片上（贪心装箱按文件大小，sync.test.ts 最大），
墙钟由最慢那片决定。

## 五、验收

1. `npm test` 墙钟 ≤ 70s（基线 111.6s）
2. `QIYU_TEST_SHARDS=1 npm test` 结果与基线**逐条一致**（1162 passed）
3. 峰值内存：4 片并行时单进程 < 500 MB，总量 < 2 GB
4. 任一片失败 → 整体退出码非 0（不能因为「其他片通过」就吞掉失败）
5. 变异验证：故意让一个分片内的用例失败 → 整体非 0

## 六、不做的事

- 不动 `vitest.config.ts` 的 `maxWorkers: 1` / `fileParallelism: false`
- 不把分片数做成随 CPU 数自适应（那正是事故的形态）
- 不删减现有测试断言换速度
