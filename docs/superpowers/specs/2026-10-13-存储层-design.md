## 一、目标与非目标

### 1.1 目标

建立**本地数据仓库抽象层**，使：

1. **D（同步引擎）可以开工** —— 它只需要 `Store` 接口与一个可用的 DuckDB 实现；
2. **E（查询/沙箱）/F（Skill）有稳定的读入口** —— 只读查询脱离七鱼限流；
3. **配置可自定义** —— 库路径、后端类型、行为参数可按 profile 设定，且后端类型在
   **接口层**为多后端预留（C2 接外部库时不改调用方）。

### 1.2 非目标（C1 明确不做）

| 不做 | 归属 | 理由 |
|---|---|---|
| Kysely 外部后端（Postgres/MySQL/SQLite）与连接串配置 | **C2** | 用户裁决「拆 C1/C2，先 DuckDB」：D 只需 DuckDB，外部后端不阻塞关键路径 |
| 三层只读查询沙箱（`--sql`） | **E** | 路线图 §四.E 明列沙箱为 E 的产出；C1 只提供 `query()` 原语且**不暴露任何命令**（见 §7.4） |
| 全部 ~20 张业务表的 DDL | **D 及各业务域** | 设计稿明说「完整 DDL 未给，只有表/主键/实测字段清单」；D2 决策「字段语义以实测为准」，空建 18 张表大概率被 D 推翻（先例：`staff_attendance` 粒度随参数切换、`tickets` 线上 27 键 vs 文档 16 键） |

## 三、配置体系

### 3.1 配置文件位置与形态

**位置**：`~/.config/qiyu/config.json`（设计稿 §4.2 既定；`chmod 600`）。

> **⚠️ 裁决 1（controller）：两个根目录并存是接受的，不统一。**
> 设计稿 §4.2 定配置在 `~/.config/qiyu/`，C1-D4 定数据库在 `~/.qiyu/duckdb/`。
> 二者语义不同（配置 = 设置；数据 = 仓库，且是百万行级 PII），且 §4.2 已写进设计稿与
> README，改口成本大于收益。**代价若判错**：用户需要记两个路径。缓解：`store init` 与
> `store status` 都回显实际配置文件路径（`config_path`）与库路径。

> **⚠️ 裁决 2（controller，v2 新增，回应契约诚实性审查）：C1 的配置文件 schema
> 只含 `store` 配置，不含 `appKey`/`appSecret`。**
> 理由：`resolveCredentials`（`src/core/credentials.ts:9-27`）虽支持 `fromFile` 参数，
> 但**没有任何调用方传入配置文件**（`src/commands/auth.ts:146-151` 只传 env）。若 C1 的
> 配置 schema 声明凭证字段却无人读取，就同时踩两个坑：违反 §3.3 的未知键 fail-closed
> （合法示例被拒）或制造「被接受但不生效」的静默无效键（本仓明令消灭的形态）。
> → **凭证字段留到 G1（`auth login`）落地时加入**；C1 的配置只有 `defaultProfile` 与
> `profiles.<p>.store`。
> **⚠️ 连带（v3，A 组）**：设计稿 §4.2 教用户把凭证写进该文件，C1 会报「未知键」——
> §8.3 第 6 处的 README 改文必须写明「凭证字段暂不支持，请用环境变量」，堵住组合陷阱。

**形态**（全部字段可选；缺省走内置默认）：

```json
{
  "defaultProfile": "default",
  "profiles": {
    "default": {
      "store": {
        "backend": "duckdb",
        "path": "~/.qiyu/duckdb/qiyu.duckdb",
        "readOnlyRetryMs": 30000,
        "batchSize": 1000
      }
    },
    "prod": { "store": { "path": "~/.qiyu/duckdb/prod.duckdb" } }
  }
}
```

### 3.2 优先级（与凭证既有三级一致）

**命令行 flag > 环境变量 > 配置文件 > 内置默认**。

| 项 | flag | 环境变量 | 配置文件键 | 默认 |
|---|---|---|---|---|
| 库路径 | `--db <path>` | `QIYU_DB_PATH` | `profiles.<p>.store.path` | `~/.qiyu/duckdb/qiyu.duckdb` |
| 后端 | `--backend <name>` | `QIYU_STORE_BACKEND` | `profiles.<p>.store.backend` | `duckdb` |
| profile | `--profile <name>` | `QIYU_PROFILE` | `defaultProfile` | `default` |
| 读锁重试上限 | — | — | `profiles.<p>.store.readOnlyRetryMs` | `30000` |
| 批量行数 | — | — | `profiles.<p>.store.batchSize` | `1000` |

- **取值校验（v3，B 组）**：`readOnlyRetryMs` 与 `batchSize` 必须为**正整数**；
  非法值（0/负数/非数字）→ 退出码 2、`kind: 'usage'`、消息点名键路径（§3.3 同族）。
- **点名的 profile 必须存在（v4，2026-10-27 实测修）**：`--profile`/`QIYU_PROFILE`/
  `defaultProfile` 给出的名字不在 `profiles` 里 → 退出码 2，消息点名来源与现有 profile
  列表。此前 `profiles[name] ?? {}` 让拼错的 profile **静默回落到默认库**：实测
  `--profile prodd` 时 `query` 返回 `ok:true` 与另一个库的数据，`store init` 在默认路径
  创建一个用户从未配置的库。判据是 **own property**（`Object.hasOwn`）—— `profiles`
  为 null 原型对象，`--profile constructor`/`toString` 不会命中 `Object.prototype` 的
  继承属性。刻意保留的回落有四种：配置文件不存在、`profiles` 为空、profile 存在但没写
  `store` 块、未点名任何 profile 时用内置 `default`（各有用例钉住）。空串口径与
  `auth login` 一致：`--profile ''` → usage「--profile 不能为空」；`QIYU_PROFILE=` 与
  `defaultProfile: ""` 视为未设置（与 core `fileProfile` 同一判据）。
- **复用边界（v2 澄清）**：`resolveCredentials` 只提供「命令行 > env > 文件」的**值合并**
  逻辑，它**不读文件、不选 profile**。C1 自行实现：读配置文件 → 选 profile → 取出
  `store` 块 → 与 flag/env 合并。凭证在 C1 完全不走配置文件（§3.1 裁决 2）。

### 3.3 未知键 fail-closed

配置文件出现**未知键** → 明确报错（退出码 2、`kind: 'usage'`），消息点名**完整键路径**
（如 `配置文件未知键：profiles.default.store.backendd`）。

- 检查**递归覆盖全部层级**（顶层键、`profiles` 键、profile 内键、`store` 内键）。
- **`store` 块缺键不报错**（走默认）—— 只有**多余的**键才报错。
- 理由：契约诚实性原则——「声明了但没人读」的字段是本仓要消灭的形态
  （路线图 §八 条目 6 的 `category` 先例）。拼错的配置键**静默无效**等于让用户以为设置生效了。

### 3.4 配置文件权限检查（v2 新增，v3 扩面）

C1 读取配置文件时，在 POSIX 平台检查：

- **文件**：`mode & 0o077` 非零（group/other 的**读或写**位）→ stderr 警告
  （v3：含写位——组/其他可写比可读更危险，可篡改 `store.path` 指向恶意库）。
- **父目录** `~/.config/qiyu/`：同款检查（v3：0777 目录可整体替换文件，文件自身 0600 形同虚设）。
- 警告文案：`配置文件 <path> 权限过宽（建议 chmod 600）`。**不阻断**。
- 非 POSIX 平台（Windows）：跳过检查，如实标注「等效策略待定」（§12.5）。
- **G1 交接（v3）**：凭证字段加入配置 schema 时，此检查**必须升级为拒绝**
  （退出码 1）——设计稿 §4.2 明确要求 chmod 600；机制上预留 severity 参数位。
- 文件不存在 → 不警告（走默认，正常路径）。

### 3.5 已知缺口：配置文件没有写入者

> **⚠️ 本节已整体过时（2026-10-30 状态注）**：`auth login` 已于 **2026-10-25（G1 第三批）实现**，
> 配置文件**已经有写入者**。实现口径：只从**环境变量**读凭证（不接受 `--app-key`/`--app-secret`，
> argv 会留在 shell 历史与 `ps` 里）、原子写（临时文件 + `rename` 换入）、合并保留该 profile 的
> 其它键、符号链接拒绝、绝不回显凭证；含凭证的文件 group/other 可读时**拒绝读取**
> （`kind: config_insecure`，退出码 1），无凭证时维持「警告不阻断」。
> 下面原文保留作历史记录 —— **它描述的是 C1 当时的事实，不是现在的**。

`auth login`（设计稿 §4.2 承诺的「写入 `~/.config/qiyu/config.json`」）**归 G1，尚未实现**
（`src/commands/auth.ts:57` 现状是显式报错）；于 C1 交付时，配置层是**只读**的：

- 用户需**手工创建/编辑** `~/.config/qiyu/config.json`（**已过时**：`auth login` 可写）；
- 或完全靠 flag/env（`--db` / `QIYU_DB_PATH`）指定库路径；
- `store init` **不写**配置文件（不越界实现 `auth login` 的职责）——**这条至今成立**。

**README 必须写明这一点**（§8.3 第 6 处给出逐字改文，含「凭证字段暂不支持写入该文件」），
不得暗示 CLI 会替你写配置。

## 四、`Store` 抽象（`src/store/types.ts`）

### 4.1 接口签名

```ts
export type BackendName = 'duckdb'   // C1 唯一实现；C2 新增 'postgres' | 'mysql' | 'sqlite'
export type StoreMode = 'ro' | 'rw'

export interface StoreConfig {
  backend: BackendName
  path: string
  readOnlyRetryMs: number   // 读者拿锁的退避上限，默认 30000；仅读者使用（§5.2）
  batchSize: number         // 多值 INSERT 每批行数，默认 1000；正整数
  /** 后端专属配置（C2 的 host/port/user/…）。C1 忽略；C2 读取。 */
  options?: Record<string, unknown>
}

export interface QueryResult {
  columns: string[]
  rows: Record<string, unknown>[]   // JSON 安全值：无 BigInt、无 Date 包装对象
}

/**
 * 只读事务/回调视图：不含 query/init/close —— 见 §4.2.6 的防线分层。
 */
export type WriteTx = Omit<Store, 'query' | 'init' | 'close'>

export interface Store {
  /** 幂等建表 + 推进迁移。**仅 rw 模式合法**（ro 上调用 → usage 错误）。 */
  init(): Promise<void>
  /** 表名清单（含元数据表），按名称排序。 */
  tables(): Promise<string[]>
  /** 单表行数（返回 number —— BIGINT 聚合经 getRowObjectsJson 是字符串，实现必须收敛，见 §5.4）。 */
  count(table: string): Promise<number>
  /**
   * 批量 upsert。**要求每行提供该表的完整列集**（缺列 → usage 错误），
   * 且同一批次内所有行的键集必须一致。内部构建多值 INSERT，绝不逐行循环。
   * **事务语义（v3 定死）**：处于活动事务内则加入该事务（零开销），否则自开单次事务
   * （整批原子）。返回实际写入行数（number，同 count 的收敛要求）。
   */
  upsert(table: string, rows: Record<string, unknown>[]): Promise<number>
  /**
   * 事务：回调内的所有写操作原子提交；抛异常则整体回滚。
   * 回调收到 `WriteTx`（无 query/init/close）。**不得**在回调内再调 store.transaction()
   * ——嵌套 → usage 错误（DuckDB 不支持嵌套事务）。
   */
  transaction<T>(fn: (tx: WriteTx) => Promise<T>): Promise<T>
  /**
   * 原始查询原语，位置参数用 `?` 占位。**不受 §4.2.5 白名单保护** —— 只接受可信代码的
   * 字面 SQL；E 的三层沙箱是唯一对外护栏（§7.4）。C1 不通过任何命令暴露它。
   */
  query(sql: string, params?: unknown[]): Promise<QueryResult>
  close(): Promise<void>
}

/** 工厂：按 cfg.backend 查后端注册表；未知后端 → usage 错误。 */
export function openStore(cfg: StoreConfig, mode: StoreMode): Promise<Store>
```

### 4.2 设计约束

1. **接口无 DuckDB 痕迹** —— 无 `DuckDBInstance`、无 `getRowObjectsJson` 等类型泄漏到
   `types.ts`。C2 接外部后端时**只新增 `kysely.ts` 与 `BackendName` 成员**，
   **不改 `Store` 接口的方法签名**（v2 修正：原表述「不改 `types.ts`」与「扩 `BackendName`」
   自相矛盾——`BackendName` 就在 `types.ts` 里）。
2. **后端专属配置经 `StoreConfig.options`** —— C1 不解释其内容；C2 用它承载连接串/认证。
   这样 C2 无需改 `StoreConfig` 的既有字段。
3. **`rows` 进出都是 JSON 安全值** —— BigInt/Date 的转换消灭在 `duckdb.ts` 边界内
   （实测：`getRowsJS()` 的 BigInt 会让 `JSON.stringify` 直接抛异常）。
4. **后端注册表**（`src/store/index.ts`）：
   `Record<BackendName, (cfg: StoreConfig, mode: StoreMode) => Promise<Store>>` ——
   **工厂必须接收 `cfg` 与 `mode`**（v2 修正：原为 `() => Promise<Store>`，后端拿不到
   `path`/`batchSize`/`mode`，无法实现）。惰性映射使 `openStore` 不必静态 import
   `duckdb.js` —— 这是 optionalDependency 惰性加载的落点。
5. **标识符白名单（v2 新增，回应安全审查）** —— `upsert`/`count` 的 `table` 参数必须在
   `TABLES` 中声明；`rows` 的键必须匹配该 `TableDef` 的列名；表名/列名进 SQL 时加双引号
   转义；**值一律走绑定参数**，不得拼进 SQL 文本。未知表/未知列 → usage 错误。
   （理由：`table` 可能受 D 的任务名影响，仅靠引号转义不足以替代白名单。）
6. **防线分层（v3 新增，A 组）**：`upsert`/`count` 受白名单保护（数据可能来自外部）；
   **`query()` 不受白名单保护**——它只接受**可信代码的字面 SQL**，E 的沙箱是对外唯一护栏，
   D 不得把外部派生字符串传入 `query()`（写入接口 JSDoc）。`transaction()` 回调收到
   `WriteTx`（**收窄视图**：无 `query`/`init`/`close`），使「事务内的写面」与「任意 SQL 面」
   在类型上分离。

### 4.3 分层约束

- `store/` **可以** import `core/`（用 `core/errors.ts` 的 `ErrorKind`）—— 方向单向，无环。
- `store/` **不得** import `sync/`（设计稿 §3.2 明文）。
- `core/` **不得** import `store/`。
- `commands/store.ts` import `store/`（命令层消费，合法）。
- **这三条由 `tests/store/layering.test.ts` 守护**（v3 统一落点——原 §4.3 写
  「扩展 tests/cli.test.ts 的既有扫描」与 §9.1 落点矛盾；形态沿用 `tests/cli.test.ts:163`
  的静态扫描先例，新建独立文件）。

## 五、DuckDB 实现（`src/store/duckdb.ts`）

### 5.1 惰性加载与依赖缺失

```ts
// 可注入边界（v2 新增）：单测 mock 此函数模拟 ERR_MODULE_NOT_FOUND
export type DuckDbImporter = () => Promise<unknown>
const defaultImporter: DuckDbImporter = () => import('@duckdb/node-api')
```

- `@duckdb/node-api` 进 **`optionalDependencies`**，**精确版本**（`1.5.6-r.1`，
  `npm view` 实测 latest，自带 `.d.ts`）。
  **⚠️ 实施任务（v3 修正，C 组）**：当前 `package-lock.json` **无** `@duckdb` 条目
  （96 包，grep 0 命中）——实施必须执行 `npm install @duckdb/node-api@1.5.6-r.1`
  并提交更新后的 lockfile（**联网步骤**；`npm ci` 消费者依赖 lockfile 同步）。
  tsc 严格模式下动态 import 需要包的类型存在，故安装先于编译。
- `api`/`auth` 等命令**完全不加载它**，保持轻量。
- **导入失败 → `kind: 'store_not_initialized'`，成因判定规则（v3 定死，B 组）**：
  - `ERR_MODULE_NOT_FOUND` 且缺失 specifier 以 **`@duckdb/node-api`** 开头 → **未安装**：
    `hint: '未安装 DuckDB 依赖。请运行：npm i @duckdb/node-api@1.5.6-r.1'`
  - `ERR_MODULE_NOT_FOUND` 且缺失 specifier 以 **`@duckdb/node-bindings-`** 开头 →
    **平台不支持**（`@duckdb/node-api` 依赖 `@duckdb/node-bindings`，后者按平台分包——
    平台包缺失时抛的同样是 `ERR_MODULE_NOT_FOUND`，v2 的二分法会把它误归「未安装」）：
    `hint: '当前平台无 DuckDB 预编译包（无 node-gyp 回退）。请改用外部后端（C2）或受支持的平台'`
- **裁决（controller）**：不为「依赖缺失」新增第三个 kind。两种成因的处置动作都是
  「解决环境后重试」，`retryable: false` + 明确 hint 已足够；新增 kind 会稀释语义密度
  （本仓错误层以 message 承载细分，不以 code/kind 堆叠）。

### 5.2 并发模型（实测约束）

实测矩阵（`@duckdb/node-api@1.5.6-r.1` + Node 24）：`rw→rw` 阻塞、`rw→ro` 阻塞、
`ro→rw` 阻塞、**`ro→ro` 正常**。错误原文：`IO Error: Could not set lock on file … Conflicting lock is held`。
**v3.2 注记（第四轮实测）**：上述矩阵是**跨进程**语义——同进程双开（rw+rw/rw+ro）不撞锁、
全部成功；§5.5 的夹具按跨进程语义断言。

| 角色 | 行为 |
|---|---|
| **读者**（`status`/E 的查询） | 以 `ro` 打开；锁冲突时**重试**（见下） |
| **写者**（`init`/D 的同步） | 以 `rw` 打开；**撞锁不重试**，立即 `store_locked`（v3 定死——`store init` 是人跑的一次性命令，退避 30s 不合理；D 的 sync 写者撞写者同理，由 D 层重试调度） |

**读者退避（v3 定死参数）**：

- **识别规则**：错误 message 含 **`Conflicting lock`** → 锁冲突（重试）；**其余错误立即
  透出**，不退避（防止「文件不存在」「权限拒绝」被无谓退避 30 秒）。
- **曲线**：**固定间隔 200ms**（v3 修正——设计稿实测「2.6s/13 次成功」换算即 ~200ms 固定
  间隔；v1/v2 写的「指数退避」与该实测证据矛盾，且指数曲线在剩余预算不足时会大幅越过
  `maxMs`）。上限 `readOnlyRetryMs`（默认 30000）；超过 → `kind: 'store_locked'`。
- **可注入**：`retryWithBackoff({ tryOpen, isRetryable, maxMs, intervalMs, sleep, now })`
  —— `sleep`/`now` 注入使单测用假时钟（`vitest.config.ts` 的 `testTimeout` 是 5 秒）。
- hint 分视角（v3）：
  - 读者收到：`kind: 'store_locked'`、`retryable: true`、
    `hint: '数据库被写进程占用，请稍后重试'`
  - 写者收到：`kind: 'store_locked'`、`retryable: true`、
    `hint: '另一个进程持有数据库写锁。若在同步中请等其完成，否则稍后重试'`

- **Agent 不得被无限阻塞** —— 有界重试的硬理由。
- **写操作包事务**：`BEGIN … COMMIT` 避免空档；`kill -9` 后 DuckDB WAL 自动重放
  （实测数据完整），C1 不做额外恢复逻辑。
- **锁释放时机（v3 补，A 组）**：进程自然退出即释放文件锁（实测 `kill -9` 后他人可立即打开）；
  两条命令流程的 `finally` 中**必须** `close()`（§7.1/§7.2），防止活跃句柄拖住事件循环或
  延迟 WAL 刷盘；「未 close 是否阻塞进程退出」列入实施时实测项。

### 5.3 upsert 与批量写入

**列集契约（v2 裁决，消解 Critical 冲突）**：

- `rows` 中**每一行必须提供该表的完整列集**（即 `TableDef.columns` 的全部列名）。
  缺列 → **usage 错误**，消息点名缺的列与表名。
- **同一批次内所有行的键集必须一致**（第一行缺 `color` 即报错，不做逐行分叉）。
- 显式传 `null` = 写空值（该列 nullable 时合法）；**缺列 ≠ 传 null**。
- **非 nullable 列收到 `null` 值 → upsert 入口预检拒绝**（usage，消息点名列）——
  白名单已掌握 nullability，零成本给出可读错误，不让 DuckDB 的英文约束报错透出（v3，A 组）。
- 理由：单一多值 INSERT 无法表达「逐行只更新各自提供的列」。D 的同步场景是整行写入，
  部分更新无真实需求（YAGNI）。

**事务语义（v3 定死，B 组）**：`upsert` 处于活动事务内（`tx.upsert`）则**加入**该事务
（零额外开销）；事务外调用则**自开单次事务**（整批原子）。「有则加入、无则自开」——
接口 JSDoc（§4.1）已写明；验收 29a 钉「tx 内多批 upsert → 回滚后全无」。

**SQL 形态**：

- `INSERT INTO "t" ("c1","c2") VALUES (?,?),(?,?) … ON CONFLICT ("pk") DO UPDATE SET "c2" = excluded."c2"`
  —— **显式列出全部非键列**（实测 `INSERT OR REPLACE` 跨引擎语义不一致：DuckDB 保留未列出列、
  SQLite 置 NULL）。DuckDB 无 UNIQUE 约束时会拒绝 `ON CONFLICT` —— 故建表必须声明主键。
- **多值 INSERT**：按 `batchSize` 切批（首选切批尺寸）。实测逐行 243.6ms/批 vs 多值 10.9ms/批（**22 倍**），
  80 万行不退化。**绝不逐行循环**。
  **参数上限保护（v3，B 组；M2 修订）**：每批行数 = `min(batchSize, floor(65000 / 列数))` ——
  `batchSize` 小于硬顶时生效、65000 绑定参数硬顶**无条件**兜底（该方法按 DuckDB 的绑定参数
  上限实测裁剪），即使 `batchSize` 配置成 100000 也不炸。
- 返回实际写入行数（`number`，见 §5.4 收敛规则）。

### 5.4 类型与序列化（实测约束）

| 约束 | 实现 | C1 适用性 |
|---|---|---|
| 只用 `getRowObjectsJson()` | `getRows()` 返回 `DuckDBDateValue` 包装对象；`getRowsJS()` 含 BigInt/Date → `JSON.stringify` 抛异常 | ✅ 全部查询 |
| **BIGINT → 字符串（v3 新增，A 组 Critical 级对拍）** | **`COUNT(*)` 是 BIGINT，`getRowObjectsJson` 将 BIGINT 映射为 `string`**（`duckdb-node-neo` 官方 type-mappings.test 证实）——`count()`/`upsert` 返回值必须显式 `Number()` 收敛，否则返回 `"1"` 且验收 18 的 `=== 1` 必挂 | ✅ `count()`/`upsert` 返回值 |
| ID 列统一 `VARCHAR` | `BIGINT` 在 DuckDB 读回 bigint、better-sqlite3 静默丢精度、`node:sqlite` 抛 `RangeError` | ✅ `tags.id` 等 |
| 时间值不走本地 getter | `TZ=America/New_York` 下 `DATE '2026-01-01'` 读成 2025-12-31 | ⚠️ **C1 的 4 张表无 DATE/时间类型列**（全 VARCHAR/INTEGER）——本约束**当前无适用对象**，留给 D/E 出现 DuckDB 时间列时验证 |
| `message` 需二次解析 | 报表接口的 `message` 是 JSON 字符串 | ❌ **不属 C1** —— 归 `core/envelope.ts`（信封归一化层），C1 不重复实现、不纳入测试 |

### 5.5 锁行为的可测性（v3.2 修订：撤销降级裁决，改为夹具断言）

**v3.2 实测裁决（第四轮 G 组质疑 + controller 以 1.5.6-r.1 安装包真机探测，macOS/node 24）**：

- **锁只在跨进程成立**：子进程持锁时父进程 `create` 抛 `Conflicting lock is held in … (PID n)`；
  持锁者 SIGKILL 后立即可重开（WAL 无残留问题）。
- **同进程双开不撞锁**：rw+rw、rw+ro 双开全部成功（v3.1 之前「同进程双实例可同时打开」
  的实测记录由此补全归因——那是没有文件锁竞争，不只是「看不到写入」）。
- §5.2 锁矩阵（rw→rw/rw→ro 阻塞、ro→ro 正常）**按跨进程语义成立**；同进程不适用。

**裁决（v3.2，取代 v3.1 的降级裁决）**：

- **跨进程锁在 `npm test` 内断言**：`spawnLockHolder` 测试夹具（spawn 子进程以裸
  `DuckDBInstance` 持锁，打印 `locked` + 空 `setInterval` 保持存活证活，调用方 SIGKILL）
  —— Task 5 的读者/写者撞锁测试、Task 7 的写者撞锁 e2e 均用它。
- **发布前手动 checklist 保留**（验收 60 四项不变）：作为真终端跨进程场景的二次验证，
  不再是锁行为的唯一验证手段。
- 退避逻辑纯函数化裁决不变（`retryWithBackoff` 假时钟注入，不真等 30 秒）。

### 6.1 表范围（C1-D3）

| 表 | 主键 | 列 | 来源 |
|---|---|---|---|
| `sync_state` | `dataset` | `dataset` VARCHAR NOT NULL、`watermark` VARCHAR NULL、`range_status` VARCHAR NULL、`last_error` VARCHAR NULL、`locked_by` VARCHAR NULL、`locked_at` VARCHAR NULL | 设计稿 §6.2 元数据表 + §6.4 单写者锁字段 |

**职责边界（v2 澄清 + v3 补强）**：

- **`sync_state.locked_by`/`locked_at`：C1 只建列，不读写、不检测、不回收陈旧锁。**
  陈旧锁超时的阈值、检测者、竞态处理、恢复动作**全部归 D**（§12 开放问题 2）。
  C1 不实现任何陈旧锁逻辑——不得与 DuckDB 的**文件锁**（§5.2）混为一谈：前者是 D 的

- **`sync_state.watermark` 的编码格式归 D** —— C1 只保证它是 `VARCHAR`。
  设计稿 §7.3 的水位形态不统一（`query_start`/`endTime`/`updateTime`/`staff_id+work_date`，
  且知识库时间有秒/毫秒两种单位），C1 不预设编码（§12 开放问题 2）。
- **⚠️ `sync_state` 单行/数据集也是 C1 假设（v3 补标，A 组）**：设计稿 §7.2 的区间状态
  （`pending`/`complete`）若需**多区间并行**（断点续传），单行不够——由 D 的 spec 裁决，
  不够则 D 经迁移机制改键（同 `sync_gaps` 主键的处理）。
- **`sync_gaps` 主键 `(dataset, range_start)` 是 C1 的假设**，设计稿未给依据。
  若 D 需要「同起点、不同终点」的多条缺口，D 的 spec 通过迁移机制改键（§6.3）。
- **`tags` 的 nullability 按「主键 + 实测 24/24 非空」定为 NOT NULL**；
  但 spec 如实标注：这是**基于单次实测的存储策略**，不是 API 永久契约。
  **违约路径（v3）**：D 写入 null → upsert 入口预检拒绝（§5.3）→ D 把它记为同步错误
  （落 `sync_gaps`/`last_error`），**不是静默丢行**。
- **「他人的合法 DuckDB 库」（v3 新增，A 组）**：`--db` 指向别的应用的 `.duckdb` 时，
  init 会打开并尝试建表——若对方库已有同名异构表（`tags` 是极常见表名），
  `CREATE TABLE IF NOT EXISTS` 静默 no-op、schema_version 记 1，后续 upsert 才在
  DuckDB 层报错。**防线**：打开后先读 `schema_version` 表——**不存在且库中已有其他表**
  → 拒绝（`store_not_initialized`，hint「目标库不是本 CLI 创建的，请换 --db 路径」）。
  空库（无任何表）→ 正常初始化。

### 6.2 声明式表定义与迁移机制（v3 补强）

```ts
interface ColumnDef {
  name: string
  type: 'VARCHAR' | 'INTEGER'   // ⚠️ version 是迁移序号，非 ID 列，故用 INTEGER
  nullable: boolean
  /** ⚠️ E 交付前无运行时读取者，是给 E 的预置位（db describe 消费）。 */
  sensitive?: boolean
}
interface TableDef { name: string; columns: ColumnDef[]; primaryKey: string[] }
export const TABLES: TableDef[] = [ /* schema_version, sync_state, sync_gaps, tags */ ]
export function ddlFor(t: TableDef): string   // 仅 v1 基线（CREATE TABLE IF NOT EXISTS）

/** 迁移条目：函数式，可执行 ALTER TABLE（v3 定死——纯 SQL 串形态无法承载改键）。 */
interface Migration { version: number; up: (db: Store) => Promise<void> }
export const MIGRATIONS: Migration[] = [ /* v1：建 4 表 */ ]
```

- **迁移形态钉死（v3，A 组）**：`{version, up(db)}` 函数式；**任何 `TABLES` 变更必须
  新增迁移条目**（`ddlFor` 只产建表，对已存在的库加不了列——只改 TABLES 不写迁移 =
  schema_version 推进而列缺失的静默 drift）。
- **`schema_version` 一版本一行，当前版 = `MAX(version)`**（v3 定死——主键形态与
  「迁移水位」措辞在 v2 不自洽；一行一版本利于审计）。
- **每条迁移包独立事务**：失败不推进 version，下次 `init()` 重放（v3 补——DuckDB DDL
  可事务化）。
- **`TABLES` 与迁移产物一致性**（v3 防-drift 测试）：对临时库跑 `MIGRATIONS` 到最新版，
  反射 `information_schema`/`duckdb_columns()` 与 `TABLES` 对拍。
- **`sensitive` 标注机制进 C1**（全表 `false`）——E 的 `db describe` 消费；
  按设计稿 §6.5「必须**按表**标注，不能靠跨域名称模式」。
- **`TABLES` 是 E 的部分数据源**：E 的 `db describe` 需要单位、枚举等更丰富元数据，
  C1 的 `ColumnDef` **不含**这些；E 在自己的 spec 里扩展或另建描述层，**不重复定义表结构**。

### 6.3 ID 一律 VARCHAR

所有 ID 列统一 `VARCHAR`（`tags.id` 虽实测为 int）。理由：保持全仓一致性，避免将来
`staff.id`（330 行）等真 ID 列出现时两种类型并存。

## 七、命令（`src/commands/store.ts`）

### 7.1 `store init`

```
用法：qiyu store init [--db <path>] [--profile <name>] [--backend <name>]
```

流程与契约：

1. 解析配置（§3.2）→ 得到 `StoreConfig`。
2. **目录与文件检查（v2 新增；v3 改用 DuckDB 自身校验，修正魔数偏移错误）**：
   - 父目录不存在 → `fs.mkdirSync(dir, { recursive: true })`；失败 → 退出码 **1**、
     `store_not_initialized`、message 含目标路径与底层原因（如权限）。
   - ~~校验前 4 字节为 `DUCK`~~ → **v3 修正（A 组 Critical）**：魔数实际在**偏移 8**
     （前 8 字节是块校验和；`MAGIC_BYTE_OFFSET = DEFAULT_BLOCK_HEADER_SIZE = 8`，
     已从 DuckDB 源码 `storage_info.hpp`/`magic_bytes.cpp` 验证）。**放弃自写魔数检查，
     改为依赖 DuckDB 自身校验**：对非 DuckDB 文件，打开即抛
     `The file "…" exists, but it is not a valid DuckDB database file!` →
     映射为 `store_not_initialized`、hint「该路径已存在且不是 DuckDB 数据库，请换 --db 路径」。
     （DuckDB 打开失败**不会覆盖**目标文件，已由其存储管理器保证。）
   - **目标是符号链接** → 拒绝（`fs.lstatSync` 判定），退出码 1、
     `hint: '--db 目标是符号链接，请给出真实路径'`。
     **威胁模型如实声明（v3）**：这是「防误操作」不是「防对抗」——检查与打开之间存在
     TOCTOU 窗口，本地单用户 CLI 下接受。
3. 以 `rw` 打开（撞锁不重试，§5.2）→ `init()`（含 §6.1 的「他人库」防线）→ 输出：

```json
{"ok":true,"data":{"path":"/Users/x/.qiyu/duckdb/qiyu.duckdb","backend":"duckdb",
 "config_path":"/Users/x/.config/qiyu/config.json","config_exists":false,
 "schema_version":1,"tables":["schema_version","sync_gaps","sync_state","tags"]}}
```

- **幂等**：重复执行 = 成功（表已存在不报错，`schema_version` 不变）。
- 锁冲突 → **立即** `store_locked`（写者不重试）。
- **`config_path` vs `config_exists`（v2；v3.1 改名——本仓 data/meta 载荷惯例是下划线，先例 `registry_complete`/`body_kind`/`has_body_schema`）：`config_path`（预期路径，恒有值）与
  `config_exists`（布尔，真实存在性）拆分，消除 `configFile` 的歧义。
- **`store init` 不创建配置文件**（§3.5）。
- **`finally` 中 `close()`**（v3，§5.2 锁释放时机）。

### 7.2 `store status`

```
用法：qiyu store status [--db <path>] [--profile <name>] [--backend <name>]
```

流程与契约：

1. **先做文件系统检查，再打开**：`fs.statSync(path)` —— 不存在 → 直接
   `store_not_initialized`（hint 含 `store init`）；不是普通文件 → 同错误（**验收 36b**）。
2. 以 `ro` 打开（冲突 → 退避 → `store_locked`）。
3. 输出：

```json
{"ok":true,"data":{"path":"…","backend":"duckdb",
 "config_path":"/Users/x/.config/qiyu/config.json","config_exists":false,
 "schema_version":1,
 "tables":[{"name":"schema_version","rows":1},{"name":"sync_gaps","rows":0},
           {"name":"sync_state","rows":0},{"name":"tags","rows":24}]}}
```

- 库文件不存在 → `kind: 'store_not_initialized'`、退出码 **1**、
  `hint: '数据库尚未初始化。请先运行：qiyu store init'`。
- 表缺失（文件存在但无 `schema_version` 表）→ 同 kind，
  hint 改为 `数据库结构不完整（缺表）。请运行：qiyu store init`。
- **他人库**（有表但无 `schema_version`）→ hint「目标库不是本 CLI 创建的，请换 --db 路径」（§6.1）。
- 锁冲突 → 退避后 `store_locked`、退出码 1（**这就是验收触发器**）。
- **移除 `locked` 字段**（v2）：只读打开成功即代表无写锁阻塞，恒 `false` 无信息量。
- **`finally` 中 `close()`**（v3）。

> **⚠️ 裁决（controller）：hint 指向 `store init`，而非设计稿 §9.5 写的 `sync run`。**
> 设计稿 §9.5 原文是「`kind: "store_not_initialized"` + 指向 `qiyu sync run` 的提示」——
> 那是**站在 D 交付后**的视角。C1 交付时 D 尚不存在，指向一个不存在的命令是「承诺了但
> 不存在的能力」。**C1 指向 `store init`；D 交付时改指 `sync run`**（D 的 spec 负责改，

### 7.3 注册与用法文案（v3 补全 B 惯例）

> **⚠️ 本节第三点已作废（2026-10-30 状态注）**：`--pretty` 已于 **2026-10-24（G1 第二批）实现**
> —— 它现在是**合法 flag**（缩进 JSON，须写在具体子命令之后），`REJECTED_FLAGS` 已清空为
> 空数组（机制保留）。原文说它「承诺过未实现」、验收写「`store init --pretty` → 2」**都不成立**：
> 现行口径是 **`store init --pretty` → 0（缩进 JSON）**、`store --help --pretty` → 0（给帮助）。
> **保留下来的是第三点里与 `--pretty` 无关的部分**：三层 KNOWN 集合、次序（未知参数 → help →
> 位置参数）、带值 flag 的值位置守卫 —— 这些**至今是现行惯例**（见 `src/commands/spec-types.ts`）。
> 下面的原文保留作历史记录。

- `src/cli.ts` 的 `COMMANDS` 加 `store: storeCommand`；

- `store` 自己的 `--help` 中文，**完整移植 B 的次序惯例**（v3——v2 只写了一句，

  - **三层 KNOWN 集合**：`store` 级（子命令分派层）与 `init`/`status` 级各有一份，
    均含 `--help`/`-h`/**`--pretty`（合法 flag、承诺过未实现）**；
  - 次序：未知参数 → help → 位置参数；
  - **带值 flag 的值位置守卫**：`store init --db --profile` 中 `--profile` 是 `--db` 的值，

### 7.4 不暴露 `query()`

C1 **没有任何命令**能执行任意 SQL。`Store.query()` 是给 E 用的内部原语；
在 E 交付三层沙箱之前，暴露它等于把无防护的 SQL 执行面直接交给 Agent
（实测无防护时可 `COPY TO` 写文件、`read_csv('/etc/passwd')`、SSRF）。**这是硬边界。**
**`WriteTx` 不含 `query`**（§4.2.6），事务内同样无任意 SQL 面。

| `store_locked` | `store_locked` | 跨进程锁冲突（读者退避超限 / 写者立即） | `true` | 1 | 分视角，见 §5.2 |

|---|---|---|
| 1 | 库文件不存在 / 非普通文件（`status`） | `数据库尚未初始化。请先运行：qiyu store init` |
| 2 | 库文件存在但缺 `schema_version` 表（且无其他表） | `数据库结构不完整（缺表）。请运行：qiyu store init` |

### 8.2 退出码归类

| 情形 | 退出码 | kind |
|---|---|---|
| 库文件不存在 / 非普通文件（`store status`） | **1** | `store_not_initialized` |
| 库文件存在但缺表 / 他人库 | **1** | `store_not_initialized` |
| `@duckdb/node-api` 未安装 / 平台不支持 | **1** | `store_not_initialized` |
| 锁冲突（读者超限 / 写者立即） | **1** | `store_locked` |
| 目标文件非 DuckDB / 符号链接 / 父目录创建失败（`store init`） | **1** | `store_not_initialized` |
| **DuckDB 执行期错误**（约束违约、类型不匹配等，经入口预检后仍发生） | **1** | `internal`（message 含表名/列名与底层原因，hint 中性——v3.2：「数据库执行期错误。若持续出现，请用 qiyu store status 检查库状态，或换 --db 路径重试」（status 只读路径也会走到，不能说「写入」）） |
| `upsert` 缺列 / 未知表 / 未知列 / null 违约 | **2** | `usage` |
| `--backend` 传未知名 | **2** | `usage` |
| 配置文件含未知键 / 取值非法（§3.2） | **2** | `usage` |
| 配置文件 JSON 畸形 | **2** | `usage`（点名文件路径与解析错误） |
| ro 模式下调 `init()` / `close()` 后再调用任何方法 | **2** | `usage` |

> 「环境/状态问题」归 1，不是 2：换任何参数都不会成功。
> **通道规则（v3 补，B 组）**：退出码 2 的各行**必须经 `usageFail()`**（stderr 纯文本 +
> stdout JSON 双通道）；退出码 1 的各行经 `fail()`（单通道 stdout JSON）——与本仓
> 「用法错误必须双通道」的既有契约对齐。
> **DuckDB 执行期错误（v3 新增，A 组）**：入口预检（白名单 + nullability）已拦截大部分，
  残余的运行期错误归 `internal`，message 含定位信息，不裸透英文原文。
