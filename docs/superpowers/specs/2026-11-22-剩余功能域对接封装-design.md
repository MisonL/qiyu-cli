## 2. P0 · Windows 凭证权限：证据链与裁决

### 2.1 三层失效（【已验证】，静态 + 真机）
- **写入不收紧**：`writeConfigFile`（`src/core/config.ts` 的 `writeConfigFile`）在 win32 上 `mkdir mode:0o700`「Not supported on Windows」、`writeFileSync{mode:0o600}` + `chmodSync(0o600)` 只映射「只读属性」——**NTFS DACL 零改变**。
- **门禁不拦截**：`checkPermissions:371` 首行 `if (process.platform === 'win32') return {ok:true}`，「含凭证过宽即拒绝」在 Windows 上整条蒸发（连警告都没有）。
- **自检恒 ok**：`auth login` 写后自检调 `checkPermissions`（`auth.ts` 的「权限自检」段），win32 短路使它在 Windows 上 **恒返回 ok**——`configured:true` 里的「权限已复核」这层含义在 Windows 上没有发生；而同一函数上方的注释把 「凭证已落盘且可被他人读却报成功」定义为假成功，win32 路径恰好落进自己定义的形态。 · **边界澄清（Codex P1-4）**：自检的 `catch { }` 吞错是**另一件事**——它对全平台一致、注释写明是有意的 （「自检失败不影响已写入这一事实；下一次任何命令都会再查一次」），不是 win32 特有。 spec 此前把两者压成 「自检恒真」一句，读起来像 catch 也是 win32 分支——修法里两者要分开对待。- **影响面（按调用链列，Codex P1-4 要求）**：`writeConfigFile` 的直接写入方只有 `auth login`；`checkPermissions` 直接调用点三处 （login 自检、`loadConfigChecked`、`store/config.ts resolveStoreConfig`），传递覆盖 `auth whoami`、`api call`、 `sync run/status/verify/install/uninstall`、`store/db/query/stats` 全族与限流 fallback 探测；`api list`/`api schema`/ `skill *`/`--version` 不读配置，不在其内。

### 2.2 真机决定性证据（M1 + 我亲自复核 T-8/T-7a）
- **M1（有效证据）**：Windows 上 0600/0644/0666 四种造法的文件，`icacls` 输出**逐字节相同**、`statSync().mode` 全部回读 `666`；把 config.json 显式 `/grant` 给 `Everyone:(R)` + `BUILTIN\Users:(R)`（**RC=0、ACE 在、含凭证**）后 `auth whoami` **RC=0** 照常返回 `configured:true`，不报 `config_insecure`；`icacls /reset` 回纯继承后仍 RC=0。
- **T-8**：git 历史证明两个函数自 `5650cfa`(G1/v0.2.0) 引入、v0.2.1→v0.2.3 函数体哈希相同 ——「非 0.2.2 回归」 **这一半是源码历史可复核的**；另 一 半 「三版产物在 Windows 上 ACL 逐字节相同」只是**本机样本观察** （原始输出见 `private/evidence/2026-11-22-windows-acl/raw-outputs.md`，gitignored），不推广为普遍结论。该缺陷是 **G1（PR #13，v0.2.0 起）的存量**，0.2.2 在权限域反而往诚实方向走（新增 ACL 拒绝的平台分流）。用户「0.2.2 起」是观测时点，不是回归点。
- **T-7a（精确归因）**：M1 环境中那条**测试机特有的某沙箱服务组**的 `(I)(M,DC)` ACE 来自 `%TEMP%` 目录本身（新建任意文件都继承），**不是 qiyu 写入的、也不是全体登录用户可读**。真实暴露面按「NTFS 默认 ACL 可能授予广域主体 + CLI 不检查也不告警」陈述，**不夸大**成「所有登录用户可读」。
- **T-8 附加**：Windows上 `os.homedir()` 只认 `USERPROFILE`（HOME 完全忽略）；OpenSSH 会话里 `USERPROFILE` 指向 Temp——路径契约在 Windows 上比预想复杂。
- **我方探针诚实记录**：我自己跑的一轮「放宽 Everyone 后 whoami rc=0」是**无效探针**（凭证从 env 读、`grant` 静默失败、ACE 没落上）；「门禁不拦」只以 M1 那份有效证据为准。

### 2.3 Linux 正确基线（M2，全实测）
文件 600 / 目录 700 且与 umask 077/022/**000** 无关；644 → whoami rc=1 `config_insecure` + `chmod 600` hint；目录 757/777 → 拦、755 不拦（判据 `&0o022`）；把 login 产物复制成 644 后 `nobody` 真能读出 secret（泄露面真实）；644 下 `login` 静默自愈为 600、777 目录下 login 报「已写入但自检不合格」；符号链接**只写侧拒绝、读侧跟随**。

2. **方案 A（以真机为闸，机制结论见 §2.4a）**：写入侧 win32 显式 `icacls "<tmp 路径>" /inheritance:r /grant:r "*<当前用户 SID>:(R,W,D)"`——数值 SID **必须带 `*` 前缀**（`icacls` 语法要求，实测同此），且按 **SID** 不按本地化 trustee 名（中文 Windows 的 `icacls` 输出是本地化的——同「按错误文本分流」红线）；**写序与 ACL 落点（CodeRabbit #82 major 的追问）**：`writeConfigFile` 是「写 tmp → `renameSync` 换入」。 `rename` 是**换入对象**——换入后目标的 ACL 取 **源文件（tmp）**的，**目标旧 DACL 不保留**（**实测 T-9b**：对已显式放宽过 `Everyone:(R)` 的目标做 `mv` 覆盖，换入后 ACL 变成 tmp 的目录继承态、旧 `Everyone` 授权消失）。所以"保留旧 DACL 再写凭证"这条泄露路径在 **当前 tmp→rename 形态下不成立**。**写序必须拆成各自可验证的步骤（Codex 对 PR #82 的 P1-1——比 rename 语义更早的一处泄露；round 77/79 后又补了 ⓪ 与创建时刻受限，第十一轮再把「创建」与「独占持有」合并，现在共五步）**：win32 上 `writeFileSync(tmp, secret)` 会按父目录继承的 DACL 创建 tmp，**secret 在被收紧之前就已经躺在 tmp 里**（当前代码先写后 `chmod`，而 `chmod` 不落 DACL → 整个写入窗口 tmp 都是继承可读的）。正确顺序：⓪ **建 tmp 之前先校验父目录受信**（清单第 7 条；不可信就直接失败，**不建 tmp、不写 secret**——CodeRabbit round 77：tmp 会继承父目录 ACL，事后收紧救不回来）；① **以受限安全描述符原子地创建空 tmp 并同时独占持有它**（不写 secret；**2026-11-24 十一轮真机探针后的落地形态见 §2.4a「设计据此收敛」——`FileStream(…, FileShare::None, …, FileSecurity)` 一次调用完成创建与独占，产物 `D:P(A;;0x13019f;;;<自己>)`，含 `DELETE` 供换名，见 §6.32**）——CodeRabbit round 79：父目录对他人有**可继承的只读** ACE（第 7 条只拦写面、放行这种）时，tmp 创建瞬间就继承可读，别人可在收紧前打开并**持有句柄**，而 Windows 只在**打开时**检查访问、改 DACL 不撤销已授予的访问；所以「`writeFileSync` 之后补 `icacls`」不满足要求，必须创建时刻就受限。机制选择：**已实测可用**的是 .NET `FileStream` 七参重载 + `FileSecurity`（PowerShell 5.1 上直接可用，见 §2.4a）；`CreateFile` + `SECURITY_ATTRIBUTES`（P/Invoke）是等价备选但**未实测**；「先建目录再 `icacls`」的 staging 目录路线**不可用**（问题递归，且普通创建窗口已证明能被 `WRITE_DAC` 元数据句柄利用）。② 对它 `icacls "<tmp 路径>" /inheritance:r /grant:r "*<SID>:(R,W,D)"` 收紧（**必须带 `D`**，否则抹掉 ① 的 `DELETE`，见 §2.4a ④），并**读回确认收紧成功**；③ 收紧到位后才写 secret，**且必须写进 ① 创建时拿到的同一个句柄**（不得按路径重新打开——round 81：`qiyu` 目录的**祖先**若对他人可替换子项，对方可在 ② 之后把 `qiyu` 目录换掉、在同一路径放另一个 tmp，按路径重开会把 secret 写进攻击者可读的文件；**目录身份必须先钉住**：打开 `qiyu` 目录的句柄并保持到 ④ 完成（Windows 上持有目录句柄可阻止其被删除/改名——**前提是打开时不得带 `FILE_SHARE_DELETE`**：共享标志里给了删除共享，别人照样能删/改名，句柄形同虚设；Codex round 24），或在 ② 与 ③ 两边比对同一路径下对象的 **file ID / 卷序列号**，不一致即中止）；④ 换入（换入前对目标路径再比对一次目录身份）——**执行原语以 §2.4a ⑥ 为准：子进程内 `MoveFileExW` + `MOVEFILE_REPLACE_EXISTING`，不是 Node 的 `renameSync`**（后者只出现在「当前产品代码 `writeConfigFile` 怎么写」这句事实描述里，不是本契约的动作；Codex round 41 P2-1）。**任一步失败的处理一律走 §2.4a 的统一规则，且按 secret 是否已写分两臂**（本例编号 ③（= §2.4a 的 ⑤）写 secret 之前的失败 → 非 0 退出、**不写 secret**、不删除也不移动任何对象；③ 之后（本例 ④ = §2.4a 的 ⑥）的失败发生在 secret 已写之后 → 非 0 退出、**如实报告含 secret 的残留路径**、同样不删除也不移动任何对象；此处原写「就删除 tmp 且不换入」是收敛前的旧语义，与统一规则矛盾，Codex round 33 P2 指出后改掉；把「不写 secret」说成全称则与 ⑥ 的实况矛盾，CodeRabbit round 108 minor 指出后按两臂改写）。换入后目标的 ACL 继承自这个已收紧的 tmp——「换入会把收紧带过去」只有在「先收紧再写入」的前提下才成立，否则只是把带 secret 的宽松 tmp 换进目标位置。**若**将来改成对现有文件 **原地改写**（不走换入），则 `/inheritance:r` 只断继承、`/grant:r <自己>` 不删**他人已显式授予**的 ACE——旧的 `Everyone`会存活，那种形态必须额外 `/remove` 广域主体。**收尾一律对最终路径复核一次 ACL **（见下探测），别假设写序正确。`checkPermissions` win32 分支改**真探测 ACL**——探测不能只看「当前用户可不可达」，必须**枚举现有 ACE 并按「最小允许名单」判**：只有当前用户 SID（以及 `*S-1-5-18` SYSTEM、`*S-1-5-32-544` BUILTIN\Administrators 这两个设计上本就等价全权的内置主体）可以持有允许 ACE，**出现任何其他主体的允许 ACE 即判 `ok:false`，不论它是不是广域主体**。**不得写成广域主体黑名单**（Everyone/Users/Authenticated Users 枚举）——黑名单天然漏一族：`icacls /grant:r <某个具名用户>:(R)` 的显式授权不在名单里，却同样让那个账户读到 `appSecret`，探测却报 `checked:true, ok:true`（CodeRabbit round 74 指出的正是这一形态，与本 spec「凭证可被他人读却报成功」的定义同类）；那个具名用户即使在别处有 deny ACE 也按「先判 allow 名单」处理——宁可误报要求人工 `icacls` 清理，也不放过。**「空名单」不等于「已保护」——必须先把 DACL 本身的存在性与空态判掉（CodeRabbit round 75）**：Windows 的 **null DACL**（安全描述符里 `DACL` 指针为空）表示「无访问控制」——**所有人都拿到完全访问**，它枚举出来的 ACE 列表同样是空的，光按「没有名单外主体的允许 ACE」判会把这种最危险的形态判成 `checked:true, ok:true`。**探测的对象不是「ACE 列表里有没有已知坏形态」，而是整份安全描述符是否处于「受信状态」**——逐轮补黑名单式缺口（round 74 具名用户、round 75 null DACL、round 76 属主）说明这个方向本身会一直漏，所以判据改成封闭清单，**任一条不满足即 `ok:false`**：
1. **DACL 存在**（null DACL = 「无访问控制」，所有人完全访问 → 拒）；
2. **DACL 非空**（空 DACL = 「显式拒绝所有人」，文件连当前用户都读不了，不是本 CLI 写序可能产出的形态 → 拒并提示重建 ACL，不得当成「收紧得好」放行）；
3. **属主（owner SID）∈ {当前用户 SID, `*S-1-5-18` SYSTEM, `*S-1-5-32-544` Administrators}**——非受信账户作属主时，属主隐含 `WRITE_DAC`，可以随时给自己补一条读 ACE，ACE 名单里永远看不出来（CodeRabbit round 76）；
4. **所有允许 ACE 的主体 ∈ 同一受信集合**（出现任何其他主体即拒，不论广域与否——round 74）；
5. **当前用户的允许 ACE 至少含读权限**（否则 CLI 自己读不了配置，「收紧成功」是假的），
   且**不得把 `WRITE_DAC`/`WRITE_OWNER` 授给「当前用户以外的受信主体」**——那是把改回宽松的权力交给了别人，
   等于没收紧成功。
   ⚠️ **当前用户自己持有 `WRITE_DAC`/`WRITE_OWNER`（含 `FullControl`）不构成危险（CR 128 minor）**：
   属主隐含这两项（清单第 3 条已要求属主 ∈ 受信集合），所以「只授当前用户 `FullControl`」的受保护 DACL
   并不比「只授 Read」更宽——拒绝它会让一份合法配置的只读命令直接不可用。
   判据因此是「**除当前用户外，有没有其他主体拿到 `WRITE_DAC`/`WRITE_OWNER`**」；
   旧文写成「当前用户 ACE 不得含 `WRITE_DAC`/`WRITE_OWNER`」，会误拒 `FullControl`，已按此更正
   （同轮连带：夹具 9(c) 用「只含 `Read`」不是因为 `FullControl` 不合法，而是为了隔离 deny 判据，见 §2.5）。
   **「至少含读权限」同样要按有效权利判，不是「Allow 掩码里有 `Read`」（CodeRabbit round 115 minor）**：
   判据必须**按 DACL 顺序模拟 Windows 的访问检查**（微软《How AccessCheck Works》；这是**机制规则**，
   本仓库的真机探针没有单独验证顺序语义，见下）：沿途把**主体命中**当前用户（直接或经所属组、且按
   令牌 SID 属性，见下）的 **allow** ACE 所授的所需权利**累加**起来，**累加到所需权利齐全即通过**
   （此后即使还有 deny ACE 也不再求值）；中途遇到**主体命中、且否定了任一所需权利**的 deny ACE
   → **整个请求被拒**（该权利此前是否已被累加过不影响——Windows 只在「全部已授予」时才提前停止）；
   走到 DACL 末尾仍有权利未获授（含压根没有 allow ACE）→ 隐式拒绝。
   ⚠️ **不是「第一条命中主体的 ACE 决定全部」（CR 133 minor）**：一条只授 `READ_DATA` 的 allow ACE
   并不授予 `READ_ATTRIBUTES`/`READ_CONTROL` 等其余所需权利；必须逐权利累加，任何一项缺失都算未获授。
   ⚠️ **「命中」要按访问令牌的 SID 属性判，不是「是不是这个组的成员」（CR 131 minor + Codex 60 P2）**：
   令牌里的组 SID 可带 `SE_GROUP_USE_FOR_DENY_ONLY`（deny-only，UAC 非提权令牌里的 Administrators
   就是典型），此时 Windows **忽略该 SID 上的 allow ACE、deny ACE 照常生效**（微软《SID Attributes
   in an Access Token》）。所以：**allow ACE 的主体是 deny-only 组 → 不算获授该权利；deny ACE 的主体
   是 deny-only 组 → 仍算拒绝**。不按令牌属性实现时，「受保护 DACL 只授 Administrators 读、其余条件
   全满足」会被判成可读，而实际读取 `0x80070005`——正好是本条要防的假绿。实现须取令牌的组列表与属性
   （`GetTokenInformation(TokenGroups)`）；取不到 → 第 8 条 `checked:false`，不得假定为可用。
   ⚠️ **受限令牌要做第二遍检查（CR 132 minor）**：若进程令牌是 `CreateRestrictedToken` 的产物
   （`TokenRestrictedSids` 非空），Windows 的访问检查**分两遍**——按普通/启用 SID 一遍、按 restricting
   SID 一遍，**两遍都授予才算通过**。只按 `TokenGroups` 求值会把「restricting SID 集在该 DACL 上
   拿不到读」的进程判成可读。实现须取 `TokenRestrictedSids` 并对同一 DACL 做第二次按序求值，
   任一遍拒绝即 `ok:false`；读不出该列表/无法判定 → 第 8 条 `checked:false`。
   （CLI 平常不是受限令牌，但契约不假定运行环境。）
   **探针实测到什么、没测到什么（按原始存档更正，Codex 59 P2）**：探针 39 的 R2 档是
   `D:P(D;;CC;;;<self>)(A;;FR;;;<self>)`——**deny `READ_DATA` 在前、allow 只含 `Read`（`FR`，不是
   `FullControl`）在后**，读取被拒 `0x80070005`；探针 38 的 N2/N3 同样是 deny `DELETE` 在前。
   所以这两组探针证明的是「必须显式解析 deny、不能只看 Allow 掩码」，**不是** allow-在前/deny-在后的
   顺序行为——本 spec 与夹具里那条 allow-在前的档位（9(c)(iii)、9(b) 对照）**尚未真机实测**，0.2.4 必跑。
   ⚠️ **更正（CR 129 minor + Codex 57 P1 + CR 133 minor）**：旧文写「有**任一**覆盖读面的 deny →
   `ok:false`」是**过严**，会把「前面的 allow 已把所需读权利授齐、deny 排在其后」的合法配置误拒、
   让只读命令不可用，而且把上述探针误当成顺序行为的证据。但**也不能**简化成「deny 排在 allow 之后
   一律不生效」（CR 133）——只有前面**已累加到所需权利齐全**时检查才提前结束、后方的 deny 才够不着；
   前面的 allow 只授了**一部分**时，后面覆盖任一所需权利的 deny 仍会终止整个请求。正确判据就是上面的
   **累加算法**：所需权利齐全 → 通过；中途被 deny 否定任一所需权利、或走完 DACL 仍缺权利 → `ok:false`。
   同一规则**同样适用于 `W1`**（写序的有效 `DELETE` 判定）——不能对 deny「一票否决」。
   夹具须补一档**allow 在前、deny 在后**：读面必须 `ok:true`（与 9(c)(i) 的 deny-在前形态成对）。
   （Allow `Read` 且无相关 deny 的配置必须通过——夹具 8 就是这一档。）
   **`DELETE` 是「写序专用」加项，不在读面判据里（CodeRabbit round 114 minor）**：本清单同时被
   `checkPermissions` 用（它服务于只读命令——`api call`/`query`/`sync` 之前都要读配置），
   而 `DELETE` 只影响**删除/覆盖**，与「能不能安全地读」无关。一份属主受信、DACL 受保护、
   当前用户可读、父目录受信、但**不含 `DELETE`** 的配置**应当通过读面检查**。
   所以本清单拆两层：**①–⑧ 是读面判据（`checkPermissions` 用）**；**写序在磁盘上校验自己刚创建的
   tmp 时再附加一条，记为 `W1`**（**不并入上面的编号**——第 8 条是「任一条判不了」，与 `W1` 同名会混淆）
   ——「当前用户对**该 tmp** 的有效 `DELETE` 存在」（否则 ⑥ 的换名只能靠父目录的
   `FILE_DELETE_CHILD`，而受信父目录可能只授 `Modify`——探针 32 E 档实测 `(OI)(CI)M` 不含该位；
   这种配置下 secret 会先写进去、换名才失败，见夹具 13(c)）。**两层不得混用**：把 `DELETE` 塞进
   读面判据会让一份**只读可用**的配置被拒（本 CLI 自己读得了、却报不安全），这正是 round 114 指出的形态。
   **判的是「有效」`DELETE`，不是「Allow 掩码里有 `DELETE`」（Codex round 41 P2-2）**：只看 Allow 掩码会
   漏掉「deny 排在前、把 `DELETE` 挡掉」的配置——随后 ⑤ 写 secret、⑥ 换名才 `0x5`。所以 `W1` 必须
   显式解析 DACL 里作用于当前用户（含所属组、含继承来的）的 ACE，并**按 DACL 顺序求值**：沿顺序找
   **主体命中且覆盖 `DELETE`** 的第一条 ACE，是 allow 即有效、是 deny 即无效（`DELETE` 是**单权利**
   请求，这与第 5 条读面的累加算法等价：allow 覆盖它时所需权利即已「齐全」、检查提前结束）；「命中」
   同样按访问令牌的组 SID 属性判（deny-only 组的 allow ACE 不算数、deny ACE 照算），受限令牌同样做
   第二遍 restricting SID 检查——均见第 5 条读面说明。
   ⚠️ **不得写成「只要有一条覆盖 `DELETE` 的 deny 就判红」（CR 130 major）**：allow 在**前且覆盖
   `DELETE`** 时，这个单权利请求在到达后方 deny 之前就已「全部授予」、检查结束，deny 不生效——
   与读面同一条累加规则，两层不能各用一套判据。
   解析不出（掩码未知、组归属或令牌属性判不了）→ `ok:false`，不冒认收紧成功。**不写「调用某某 API 取有效权利」**：
   `FileSystemSecurity` 没有算有效权利的方法，`GetEffectiveRightsFromAcl`（advapi32）是候选但**本轮未实测**，
   按本 spec 的规矩，未实测的机制只能作为备选并当场标注。夹具 9(b) 造「deny `DELETE` 在前、allow `(R,W,D)` 在后」
   必须红——**这条前提本轮已真机验证**（探针 38：同一用户 `D:P(D;;SD;;;<self>)(A;;0x13019f;;;<self>)` 时，
   覆盖换名 `0x5` 且目标内容原样、单删同文件也 `0x5`；父目录同样不含 `FILE_DELETE_CHILD`）。
6. **继承关闭**（`SE_DACL_PROTECTED` 置位）——继承开着时，父目录 ACL 一变就会把名单外主体重新带进来，当前这份 ACE 列表「碰巧干净」不构成保证；
7. **父目录的写面受信**（不是「所有 ACE 都受信」）：非受信账户对目录没有任何**写类**权限（创建/删除子项、`WRITE_DAC`、改属主）——否则别人可以**整个换掉**这个文件；继承来的**只读** ACE 只暴露文件名、读不到 `appSecret`，与 POSIX 侧「目录 0755 不拦、group/other 有写位才拦」（`checkPermissions` 目录分支的 `& 0o022`）同构；
   **父目录的属主同样必须 ∈ 受信集合（Codex 61 P2，与第 3 条对文件同理）**：属主隐含 `WRITE_DAC`，
   只查显式 ACE 会漏掉「非受信账户作属主、DACL 里没有它的写 ACE」的目录——对方仍可先改写目录 ACL
   再替换整个配置目录。属主判「受信」与 ACE 判「写类」两条并存，任一不满足即 `ok:false`；
8. **任一条判不了**（非 NTFS、PowerShell/icacls 不可用、SDDL 解析失败、令牌的组列表/属性读不出、受限令牌的 restricting SID 列表读不出或两遍检查判不了）→ `checked:false`，不冒认 ok。
候选机制是 PowerShell `Get-Acl` 的 SDDL 形态（null DACL 为 `D:NO_ACCESS_CONTROL`、空 DACL 为 `D:`，两者枚举 ACE 都是空列表，**只有 SDDL 能区分**）。**验证状态分两截（Codex round 40 P2）**：`Get-Acl` 的 `.Sddl` 可读、ACE 可逐条取主体/继承位/掩码，**已真机实测**（§2.4a「已验证可行」）；但**「null DACL 与空 DACL 各自长什么样」尚未实测**——本机用 .NET 造不出空 DACL（设置静默不生效，见 §2.5 夹具 6），所以这两个形态仍须在真机上各造一个（`icacls` 能造空 DACL；null DACL 需 PowerShell/.NET 设置 `SetSecurityDescriptorSddlForm('D:NO_ACCESS_CONTROL')`）并读回确认，实测定稿前不把这两条写成「已验」。判据取 **SID + 访问掩码**，不解析 `icacls` 输出里的本地化权限文本（`(F)/(M)/(RX)/(R)` 一类 token 的中文输出形态**未经实测**，不拿它做判据；取 SID/掩码的候选机制——PowerShell `Get-Acl` 的 `FileSystemRights` 枚举值 + `Translate([SecurityIdentifier])`——需真机验证后再定稿）；按 **SID** 判不按本地化名，规避中文 Windows `icacls` 输出本地化——同「按文本分流」红线；收紧用的是**重建整份 DACL**（断继承 + 删他人显式 ACE + 仅授当前用户），`/grant:r <自己>` 单用**不会删别人的显式授权**，残留即泄露；返回三态的完整取值：**安全 → `{ok:true, checked:true}`；不安全（名单外主体的允许 ACE / null DACL / 非受信属主等，清单第 1–7 条任一不满足）→ `{ok:false, checked:true}`；无法判定（非 NTFS、PowerShell/icacls 不可用、SDDL 解析失败）→ `{ok:false, checked:false}`**——不能把「不安全」与「判定不了」混成一个 `ok:false`（CR 126 minor：旧文写作 `{ok:true, checked:true|false}`，字面漏掉了 `ok:false` 这一整态）；三个调用点（`auth login` 的「权限自检」段、`core/config.ts` 的 `loadConfigChecked`、`store/config.ts` 的 `resolveStoreConfig`）把「判定不了」如实透出；不得复用 `mode & 0o077` 判据（Windows 正常文件回读 666，会把所有人误拒）。非 NTFS / icacls 不可用 → 「判定不了」，不冒认 ok。
3. **同构面裁决**：`store init` 创建的 DuckDB 库文件（含业务数据）同样无权限收紧——要明确「一并收口」还是「明确非目标并声明」，不留下沉默缺口。

十五轮由审查与自查推动：第一轮列机制；第二轮（CR 86）推翻第一轮的「只能引原生依赖」；
第三轮（CR 89）验证独占句柄语义；第四轮（CR 93，探针 6–12）验证「祖先目录被替换」下句柄与路径各自的实况；
第五轮（**CR 93 两条 major 的追问**，探针 13–14）验证「真独占句柄能否钉住祖先目录」——**.NET

探针 14 独立复现 `rmdir` 被挡），而 **Node 的 fd 不能**（libuv 带删除共享）。这决定了 ③⑤ 按路径判据

第七轮（自查，无新实验）发现「句柄是进程内资源」→ ①–⑥ 必须同一长驻子进程这条硬约束；
第八轮（CR 94/95/96，探针 14b–14d、17）把 error 87 查到**信息类号**级（真因是类号写错，
修正后仍闭合不了⑥ 窗口），并收回两处过度声明（并发删除竞态、检测范围全称承诺），
再把独占打开失败按异常类型分成三档；
第九轮（CR 97，探针 19–20）修掉两处**序列缺陷**（③ 漏跑属主校验；删除时机——他人不含删除共享时
删不掉、自己持有时也要先关句柄才删得掉）。
第十轮（CR 98/99/100，无新实验）把九轮累积下来的**互相打架的删除语义收敛成一条统一规则**：失败路径一律
不按路径删除/移动任何对象——路径那一刻无法正名「这是我的对象」（② 失败没有句柄、③ 要删就得先丢句柄、
⑥ 不一致时可能是并发写者刚验收的配置），于是 CR 95「给删除配串行化」与 CR 97「删除分档/先关句柄再删」
**都作为派生要求作废**，只留机制解释；继承关闭也从 ③ 的前置挪到 ④ 之后的读回（否则合法输入被自己拒死）。
第十一轮（CR round 103 major + 探针 21–29）推翻第十轮之前的**主路线本身**：「先建空 tmp 再独占打开」这条
在 CR 103 的追问下被真机证伪——共享检查只作用于**数据**访问，`WRITE_DAC` 一类**元数据**句柄可以和我们的
`FileShare.None` 并存、熬过 ④ 的 `icacls` 重建，然后改写 DACL 把读权限补回去，**secret 被按路径读走**
（探针 26 端到端复现）。修法不是加判据，而是把「创建」和「独占持有」合成一次**带受限 SD 的原子创建**：
`[System.IO.FileStream]::new(CreateNew, …, FileShare.None, …, FileSecurity)` 在 PowerShell 5.1 上实测可用
（探针 25/27/29、30/31、32），产物是 `D:P(A;;0x13019f;;;<自己>)`——从文件首次可被观察的那一刻起就没有任何外部 ACE，
攻击者拿不到 `WRITE_DAC`，也就没有「熬过重建」这回事；顺带把 ①→② 之间的空窗一并消掉。
第十二轮（Codex round 38，探针 32/32b–32d）补上「换名这一步到底怎么执行、依据哪个权限」：
子进程里不能用 Node 的 `renameSync`（P1），`File.Move` 两参重载在目标已存在时失败（`0xB7`），
`File.Replace` **保留被替换文件的 ACL**（会把旧配置的宽松 ACL 带回来，与 ④ 矛盾），只有
`MoveFileExW + MOVEFILE_REPLACE_EXISTING` 既可用、又带过去源文件的 DACL；换名的权限依据从
「父目录的 `FILE_DELETE_CHILD`」改为「文件自身的 `DELETE`」（ACE 由 `Read | Write` 改成
`Read | Write | Delete` → 掩码 `0x13019f`），因为父目录只授 Modify 时前者并不存在。同轮还查出
**探针机的令牌会让这一条无从实测**：ssh 会话是已提权管理员，`GetTokenInformation(TokenPrivileges)`
读出 `SeBackup`/`SeRestore`/`SeTakeOwnership` 均为 `attr=0x3`（已启用，探针 35b）；把这三个特权
在进程内**置 0** 后再跑同一组实验，改名与删除立刻变成 `0x5 ACCESS_DENIED`、而 `DENY READ_DATA`
读仍是 `0x80070005`（探针 36 的受控对照）——特权就是成因，不是猜的。（32d 里那次 `whoami /priv`
实际打到了 Git Bash 的同名工具、报了参数错误，不能当证据；Codex round 39 P2-2 指出后已换掉。）
第十三轮（CodeRabbit round 110 major + Codex round 39，探针 33–36）修的是**上一轮修法自己引入的抵消**：
① 把 `DELETE` 放进 ACE 供换名用，而 ④ 的 `icacls "<tmp 路径>" /grant:r "*<SID>:(R,W)"`（旧形态，现行为 `(R,W,D)`）是**替换**该委托人的显式 ACE，
把 `DELETE` 又抹掉了（探针 33 B 档：掩码 `0x13019f`→`0x12019f`），七条读回只要求「至少含读权限」，
于是整条链能一路通过、secret 写进去、换名才失败。④ 改成 `(R,W,D)`（C 档读回 `0x13019f`）、
清单第 5 条补 `DELETE` 与「不得含 `WRITE_DAC`/`WRITE_OWNER`」、并把「读回通过才写」写成硬门。
同一轮把探针机的特权归因从「whoami 输出」换成 **`GetTokenInformation` + 进程内禁用特权的受控对照**
（探针 35b/36）：禁用后改名/删除立即 `0x5 ACCESS_DENIED`，读的对照仍 `0x80070005`。
第十四轮（CodeRabbit round 111 minor，探针 37）补的是**源/目标两侧**的权限边界：覆盖已有目标要目标
自己的 `DELETE`，源文件的 `DELETE` 不能代替。
同一轮 Codex round 41 P2-2 的追问（探针 38）：**deny 压过 allow**——清单第 5 条只查 Allow 掩码是
真缺口，已改成显式解析 deny。
第十五轮（CodeRabbit round 115 minor，探针 39）把「deny 优先」推到**读面**：deny `READ_DATA` 在前、
allow 含读在后时读取被拒（实测档的 ACE 顺序如此，见 §6.57），所以读面判据同样要看有效权利。
同轮 Codex round 45 P2-1 反过来指出夹具形态本身有缺陷：初稿用 `FullControl` 做「deny 读」夹具，
会被「不得含 WRITE_DAC/WRITE_OWNER」抢先拒绝，**遮蔽**了 deny 判据；探针 40 复现后改成
「只含 `Read` + deny」并配「无 deny 必须通过」的对照。

**已验证可行**
- `Get-Acl` 的 `.Sddl` 可读，ACE 可逐条取类型 / 是否继承 / 主体 SID（`Translate`）/ 权限 ——
  「不解析 `icacls` 本地化文本」这条判据路线成立。
- **原子地以受限 SD 创建文件可行，且不需要额外程序集**：`System.IO.FileStream(path, FileMode, FileSystemRights,
  FileShare, bufferSize, FileOptions, FileSecurity)` 这个构造重载在 **PowerShell 5.1 / .NET Framework** 上
  可用，实测产出的 SDDL 是 `D:P(A;;…;;;<当前用户 SID>)`——受保护 DACL、仅当前用户。
  （第一轮只试了 `System.IO.FileSystem.AccessControl` 的扩展方法，它在 5.1 加载不了，据此下的
  「只能引原生依赖」结论**错误并已撤回**。）
- 该机 `%TEMP%` 下的新文件继承了一条**非受信主体的 Modify ACE**（沙箱服务组）——「父目录对他人有
  可继承权限」有真实可造形态。
- **独占持有期间的行为（第三轮）**：`icacls` 照常可用、`rename` 被拒（须先关句柄）；**数据**读取被拒。
  旧版本把这一步同时写成「探测既有持有者」，**第十一轮更正**：共享检查只管数据访问，
  所以它只挡住「有人要读/写内容」，挡不住「有人持元数据句柄改 ACL」（探针 24 D 档）；
  而主路线改用 `CreateNew` 后连「打开既有对象」这一步都没有了（见下）。
- **受限创建与独占持有可以是一次调用**（第十一轮，探针 25/27/29）：`FileStream(path, FileMode, FileSystemRights,
  FileShare, bufferSize, FileOptions, FileSecurity)` 七参重载在 PowerShell 5.1 上直接可用，产物
  `D:P(A;;0x13019f;;;<自己>)`（ACE 取 `Read | Write | Delete`，见下「设计据此收敛」；
  早期探针里的 `0x1301ff` 是我手写进 SDDL 的字面量，不是这条 ACE 配方的产物，见 CR round 106），
  且该句柄**同时**满足「钉住祖先目录」与「数据读被拒」两项性质
  （探针 27 B 档、29 E 档复核）。这是本设计的落地形态。
  ⚠️ **本轮的验证范围要说准**：全部探针都在**同一个 Windows 账户**下跑——「受限创建后，另一个
  非受信账户也打不开」这一步**没有**跨账户实测（本机只有一个可登账户，尝试第二账户 ssh 被拒）。
  现有证据是 SDDL 形态 + 同账户下「DACL 不含某主体 → 该访问被拒」的内核行为，据此判定
  「首次可见即打不开」是【推断】而非【已验证】。0.2.4 实施时必须用**两个真实账户**跑一次**夹具 13(a)**
  （受限创建路线的那一支；13(b) 测的是被降级的备选路线，别把跨账户验证挂到它上面）。

**已验证不可行 / 需谨慎表述**
- **`[System.IO.File]::Open` 打不开目录**（访问被拒绝）→ 「持有目录句柄（不带 `FILE_SHARE_DELETE`）
  阻止改名」需要 P/Invoke `CreateFile` + `FILE_FLAG_BACKUP_SEMANTICS`，纯 .NET/Node 面不可用。
- **null DACL 的判据只能从 SDDL 形态间接确认**：设 `D:NO_ACCESS_CONTROL` 后 `Get-Acl` 的 SDDL 里
  `D:` 段消失、`icacls` 报「该文件没有 DACL」一类本地化报文，但 .NET 的 `.Access` 仍返回 1 条——
  **没有做原生描述符读回**，不得声称「已用原生 API 验证是 null DACL」。
  ⚠️ **null DACL 与「显式 Everyone ACE」不是同一条判据**（CodeRabbit round 87）：显式 Everyone ACE
  会出现在 ACE 列表里，只走允许名单的实现能拒掉它；**缺失 DACL 时 ACE 列表是空的**，只走允许名单
  的实现会把它判成「干净」。所以夹具 6 只有在实现**先判 DACL 存在（清单第 1 条）**时才算覆盖，
  「两种形态都判 `ok:false`」只对**完整清单**成立，不是允许名单单条判据的等价性。
- **空 DACL `D:` 的设置静默不生效**（SDDL 读回与设置前一致）→ 夹具 7 在本机**造不出来**，
  实施时必须如实标注。

**设计据此收敛（实施以此为准，取代 §2.4 里对应的未实测表述）**

主路线：**以受限安全描述符原子地创建并同时独占持有 tmp，然后判 DACL、收紧、写 secret——secret 全程
只经过这个独占句柄**。写序（① 与旧的「② 独占打开」是**同一次调用**，见下）：

- ⓪ 校验父目录受信（不满足就失败，并点名路径）。
- ① **一次调用同时完成「创建空 tmp」与「独占持有」**：
  `FileStream(path, FileMode.CreateNew, FileSystemRights.Read | FileSystemRights.Write,
  FileShare.None, bufferSize, FileOptions.None, fileSecurity)`，
  其中 `fileSecurity` 为 `SetAccessRuleProtection(true, false)` + **仅当前用户**一条 Allow ACE，
  该 ACE 的权限**也**取 `FileSystemRights.Read | FileSystemRights.Write | FileSystemRights.Delete`。
  ⚠️ **`.NET Framework` 的 `FileSystemRights` 没有 `ReadWrite` 成员**（CR round 106；探针 30 E0 档实测
  `GetMember('ReadWrite').Count == 0`），写 `ReadWrite` 的实现编不过——必须逐项 `-bor`。
  实测产物 SDDL 是 `D:P(A;;0x13019f;;;<自己>)`——受保护、无继承位、无任何他人 ACE（探针 30/31/32）。
  掩码逐位：含 `READ_DATA`/`WRITE_DATA`/`APPEND`/`READ_EA`/`WRITE_EA`/`READ_ATTR`/`WRITE_ATTR`/
  `READ_CONTROL`(0x20000)/`SYNCHRONIZE`(0x100000)/`DELETE`(0x10000)；**不含 `WRITE_DAC`(0x40000)、
  `WRITE_OWNER`(0x80000)**——后两位的缺席正是 round 103 那条攻击路径消失的原因。
  ⚠️ **`DELETE` 必须在场（Codex round 38 P2）**：换名的依据是「文件自身的 `DELETE`」**或**「父目录的
  `FILE_DELETE_CHILD`」二选一（微软 DeleteFile 文档）；只靠父目录那条会把 ⑥ 的成败绑在**我们控制不了的
  父目录 ACL** 上——`icacls` 的 `(OI)(CI)M` 展开成 `0x001301BF`（探针 32 E 档实测：含 `DELETE`，
  **不含** `FILE_DELETE_CHILD`），父目录若只授我们 Modify，tmp 的 `0x12019f` 又不含 `DELETE`，
  换名就会在 **secret 已写之后**失败。把 `DELETE` 放进这条只属于当前用户的 ACE，换名就不再依赖父目录。
  ⚠️ `0x13019f` **不是**早期那个手写的 `0x1301ff`：后者多出 `0x60`（`EXECUTE`/`DELETE_CHILD`），
  这两个位对文件无意义。
  ⚠️ **换名权限这一条在本机无法实测**（探针 32d）：该机 ssh 会话的令牌是**已提权管理员**且
  `SeBackupPrivilege`/`SeRestorePrivilege`/`SeTakeOwnershipPrivilege` 均**已启用**（`GetTokenInformation`
  读出的 `attr=0x3`，探针 35b），这几个特权使 `DeleteFile`/`MoveFileEx` **绕过 ACL 校验**——即使文件上写死
  `DENY DELETE`、父目录写死 `DENY DELETE_CHILD`，改名与删除**照样成功**；把这些特权在进程内禁用后
  立刻变成 `0x5 ACCESS_DENIED`（探针 36 的受控对照，成因已确认而非推断）
  （对照：`DENY READ_DATA` 时读取确实被拒 `0x80070005`，说明 ACL 校验本身是生效的，被绕过的只是
  删除/改名这一侧）。所以「给的权限不够时换名会失败」这一步是**按文档推的**，不是本机实测；
  0.2.4 必须在**不带这两个特权**的普通账户下补一条「父目录只授 Modify/`FILE_ADD_FILE`」的夹具
  （见夹具 13(c)）。这条与「DELETE 必须在场」互为保险：即使文档那条二选一在某个 Windows 版本上不成立，
  我们也不再依赖父目录。
  ⚠️ **`DELETE` 只解决「源文件」这一侧；覆盖已有目标还要目标自己的 `DELETE`（CR round 111 minor）**：
  上面这段依据的是 DeleteFile 文档，管的是**源对象**能不能被移走；`MOVEFILE_REPLACE_EXISTING` 换入时
  Windows 还要**单独**判定被替换的那个目标能否被删除，依据同样是「目标自身的 `DELETE`」**或**「目标父目录的
  `FILE_DELETE_CHILD`」——**源文件带 `DELETE` 不能代替**。探针 37 实测（同一进程内先禁用
  `SeBackup`/`SeRestore`/`SeTakeOwnership`，父目录只授 CreateFiles|Traverse|ReadPermissions|Synchronize，
  即不含 `FILE_DELETE_CHILD`）：目标 `0x12019f`（无 `DELETE`）→ 换名 `0x5 ACCESS_DENIED`、**目标内容原样未动**；
  目标 `0x13019f` → 成功，且目标 SDDL 变成源文件的 `0x13019f`；目标不存在（首次创建）→ 成功。
  所以在这个形态下 ⑥ 的成败仍可能被**目标自己的 ACL** 决定，而目标是我们**将要替换、此刻还不归我们管**的对象。
  合规处理不是「连目标一起收紧」（那要先改别人的文件，⓪ 与统一规则都不允许），而是：
  **把换名失败按「secret 可能已落盘」那一臂处理**——非 0 退出、报告含 secret 的残留路径、不删不移。
  换言之这一档是**可用性损失，不是机密性损失**；夹具 13(c) 必须分别覆盖「目标不存在」与「目标存在且无 `DELETE`」两档。
  **本步不写 secret**。
  ⚠️ **不许拆成「先建空文件、再打开它」两步**（CR round 103 major 推翻的正是这个形态）：共享检查只看
  **数据**访问，`WRITE_DAC`/`READ_CONTROL` 一类**元数据**句柄能与 `FileShare.None` 并存（探针 24 D 档：
  数据读写报 `0x80070020`，`WRITE_DAC` 照开）。于是普通创建出的 tmp 若继承了父目录对他人可继承的
  `WRITE_DAC`（父目录只授**只读** ACE 时 ⓪ 是放行的），对方就能持一个元数据句柄熬过 ④ 的 `icacls` 重建、
  再改写 DACL 把读权限补回去——探针 26 端到端复现：**secret 写完、我方句柄关闭后该文件按路径可读，
  内容逐字等于写入的哨兵**。合并成一次受限创建后攻击者拿不到 `WRITE_DAC`（探针 29 E 档：数据、
  `WRITE_DAC` 都被 DACL 拒），这条路径从源头消失；旧 ①→② 之间「他人可抢先打开**空** tmp」的窗口
  也一并消失。
  ⚠️ **「元数据句柄不受共享检查约束」是一条独立事实**，主路线改了不等于它不存在：它同时说明
  「独占持有」**不等于**「没人在旁边动这个对象的 ACL」，所以 ③ 的清单必须在 ④ **之后**再读回跑一遍。
- ② **① 返回的句柄即本契约所说的独占持有，保持到 ⑤ 之后**。
  ⚠️ **创建失败与独占打开失败是同一处失败**：`CreateNew` 撞上已存在路径报 `IOException`/`0x80070050`
  （探针 27 D 档实测），不得把它归进「有人持有」那一档。
  ⚠️ **硬约束：①–⑥ 的身份比对与换名必须在同一个长驻子进程里连续完成**（第七轮自查，非审查发现）——
  独占句柄只存在于**打开它的那个进程**内：把 ①⑥ 拆成一步一个子进程，会在步间关闭句柄，祖先目录的
  「钉住」随之消失（探针 13 的阻挡力只在持有期间有效）；`fstatSync(fd)` 这类**按句柄**的身份比对
 在父进程里根本没有那个 fd，跨进程只能按路径查，而按路径正是会被换目录劫持的那一侧。
  所以形态是：Node 起**一个** PowerShell 子进程，stdin 喂 secret，子进程内完成
  「受限创建＋独占持有 → 判 DACL → icacls 收紧 → 经句柄写 → 关句柄 → 比 `ino`/`dev` →
  换名（**P/Invoke `MoveFileExW(src, dst, MOVEFILE_REPLACE_EXISTING=0x1)`**，见下）→ 复核」，
  只把结构化结果（成功/失败 + 成因 + 实测到的 ino）交回；父进程事后只按路径复核**最终文件**。
  ⚠️ **子进程里的换名必须是子进程自己能执行的调用**（Codex round 38 P1）：`renameSync` 只存在于 Node 的
  `node:fs`，而这一段要求整条写序都在 PowerShell 子进程内完成——照字面实现会编不出来。实测（探针 32）：
  · `[System.IO.File]::Move(src, dst)` **两参重载在目标已存在时失败**：`0x800700B7`（`ERROR_ALREADY_EXISTS`）
    ——首登（目标不存在）能过，日常更新（目标已存在）必挂；
  · `[System.IO.File]::Replace(src, dst, backup)` 能覆盖，但**换入后目标保留的是被替换文件的 ACL**：
    把目标预先加上 `Everyone:(R)` 再 Replace，结果 SDDL 仍是 `D:AI(A;;FR;;;WD)…`，**源文件的受限 DACL
    没有带过去**（探针 32 F 档；同一现象早先 T-9b 在 `mv` 形态上得到的是相反结论——`mv` 带过去的是**源**的）。
    用 Replace 会让一份宽松的旧 `config.json` 把它的宽松 ACL 保留到新配置上，**与 ④ 的收紧直接矛盾**，
    而且它还会多产出一个备份文件。**不得使用。**
  · `MoveFileExW(src, dst, MOVEFILE_REPLACE_EXISTING)` **可用且带过去的是源文件的 DACL**：换入后
    目标 SDDL 是 `D:P(A;;0x12019f;;;<自己>)`（这一档探针用的 ACE 是 `Read | Write`；加上 `Delete`
    之后是 `0x13019f`，见 §2.4a 写序），内容逐字等于哨兵（探针 32 C 档）；同一调用
    **不带** `MOVEFILE_REPLACE_EXISTING` 时目标已存在即失败（`0xB7`，D 档）。
  · **首次创建（目标不存在）两种调用都能过**：`File.Move` 两参可改名到不存在的名字，换名后 SDDL
    仍是 `D:P(A;;0x12019f;;;自己)`（探针 32 F 档第一次改名）；`MoveFileExW` 不带标志同样成功
    （探针 32b）。所以「首登」与「更新」两条路径都被覆盖，差别只在目标已存在时用不用 REPLACE 标志。
  · 所以 ⑥ 的换名在子进程内用 P/Invoke `MoveFileExW` + `MOVEFILE_REPLACE_EXISTING`；Node 的
    `renameSync` 在 Windows 上应当同样带 `MOVEFILE_REPLACE_EXISTING`（libuv 的实现如此，**本轮未单独实测**
    ——这是现有 `writeConfigFile` 能覆盖旧文件的事实依据，但本条只当**推断**记），它**不能**写进
    「子进程内完成」那一句（那是 PowerShell 侧的执行要求）。
  · 换名前的 `ino`/`dev` 比对用的是子进程自己的句柄/路径信息，这一条不变。
  这一步同时提供两件事（第五轮探针 13 实测），外加一条被第十一轮改掉的旧假设：
  · **钉住祖先目录**（探针 13，探针 14 独立复现 `rmdir` 那一半）——持有期间 `rmdir /s` 与 `ren`
    对 `qiyu` **都失败**（报「a.tmp 正由另一进程使用」/「拒绝访问」），目录原封不动，也就无法在同路径
    重建；于是 ③④⑤ 的**按路径**判据与写入在此期间不可能被换目录劫持
    （CR round 93 第二条 major 要的「替换操作期间目录受保护」由此满足；探针 27 B 档在
    `FileStream::new + FileSecurity` 这个新形态上复核过同一性质）；
  · **阻止第三方读**——其他进程打不开它（探针 6 的 B/C；探针 29 E 档复核新形态）。
  ⚠️ **「独占打开=探测既有持有者」这条旧能力随主路线一起作废**：合并形态是 `CreateNew`，
  **路径已存在就是失败**（`0x80070050`，探针 27 D 档），不存在「打开一个别人也在用的文件」这一步；
  并发 login 的 tmp 名含 `pid`+时间戳，撞名本就极罕见。不要把「有人持有」写成创建失败的成因。
  ⚠️ **失败语义必须按异常类型分档**（探针 17；CR round 96 minor 1 纠正我上一版的过度归因；
  第十一轮按合并形态重新标注了每档是否还可达）：
  我原先把「独占打开失败」一律写成「该文件已有其他持有者」——只有第一类支持这句：
  · `IOException` / HRESULT `0x80070020`（共享冲突）→ 语义是**确有另一持有者**（探针 17 的 A、E 两档）。
    **合并形态下这一档不可达**（`CreateNew` 只创建新对象，没有「打开别人在用的文件」这一步）；
    若 0.2.4 出于任何理由改回「打开既有对象」，它才重新生效——届时必须照原义归因；
  · `IOException` / HRESULT `0x80070050`（文件已存在）→ **路径上已经有对象**（探针 27 D 档实测）。
    语义只有这一句：不等于「有人持有」，也不等于「有人读过」——并发 login 撞名与攻击者预置
    是两种不同成因，报错要分别提示；
  · `UnauthorizedAccessException` / `0x80070005` → **访问被拒**，成因**不止一种**：
    （B：DACL 只授 R 却要 ReadWrite → 是我们自己的收紧把要申请的访问挡在门外；
    D：路径是目录；本形态还多一档——父目录 ACL 不允许在此建子项）。**只有再用一次检查确认是
    ACL 造成的，才报「收紧失败」**（例如读回该路径对象的 DACL：若确实没有我方申请的访问位 →
    收紧没生效；若是目录/别的对象 → 报「路径不是预期的文件」）。
    把 `0x80070005` 一律报成「收紧把我们挡在门外」会把「路径上落着别的东西」这类实现/竞态问题
    误诊成 ACL 问题（CR round 99 minor 1）——同「报错必须点名真正给坏值的来源」红线。
  · `FileNotFoundException` / `0x80070002` → **tmp 已不在该路径上**（C；被删或被换）——也不等于「有人读过」。
    合并形态下这一档同样不可达（创建刚返回），留着是为了实现若把它写成两次调用时当场判红。
  可达各档都必须 fail-closed（非 0 退出、此时文件是空的、中止安全）且**都不写 secret**。
  ⚠️ **失败语义按 secret 是否已写分两臂**（CodeRabbit round 108 minor：旧版把「任一步失败都不写 secret」
  写成全称，与 ⑥ 的实况矛盾——⑤ 写完之后 ⑥ 再失败，secret 已经躺在那个 tmp（或已换入的目标）里）：
  · **⑤ 写 secret 之前**（⓪–④ 任一步失败）：secret 从未写出，**写入次数为 0**、非 0 退出、不删除也不移动；
  · **⑤ 开始写之后**（写 secret 本身失败、⑥ 换名/复核失败）：secret **可能已落盘**，此时只要求两件事——
    非 0 退出（不报 `configured:true`）与**报告含 secret 的残留路径**，让用户自己决定处置；
    同样**不删除也不移动任何对象**（「能正名」这个删除先决条件在这一臂同样不成立）。
    ⚠️ **报路径之前要先确认那个路径上还是我们的对象（Codex round 38 P2）**：句柄关了之后目录可能已被改名、
    目标也可能已被并发写者覆盖——此时按路径报「这里有你的凭证」是在**指控别人的文件**。规则：
    残留路径必须附**核实依据**（同一 `ino`/`dev` 或仍在原目录内可重开且身份一致）；核不出来就
    明确写「**残留位置无法确认**」并列出候选路径（tmp 路径 / 目标路径），不得断言其内容。
  ⚠️ **统一规则：失败路径一律不按路径删除/移动任何对象**（CR round 98 major 2 把 round 97的
  「清理能力分档」进一步合并掉——分档讨论的前提是「有该删的」，而正名问题让「该删」无法安全判定）：
  ② 失败时我们**没有句柄**、③ 失败时若先关句柄再删，删除发生在**已放弃唯一正名手段之后**——
  路径那一刻是谁的对象**无从证明**（并发写者/攻击者的同名对象都可能在场）。所以什么都不删：
  ⑤ 之前的失败**留下空 tmp**（无 secret；名字含 `pid`+时间戳；父目录 0700 下无外部读面），
  ⑤ 之后的失败留下的是**含 secret 的残留**（见上两臂与 ⑥ 的失败报告要求）。
  是否清扫、何时清扫**留给 0.2.4 设计并写明判据**——两个坑先列全：① 崩在 ⑤ 之后的 tmp
  **含 secret**，「只扫空文件」恰好漏掉最该清的；②并发 login 的 tmp 名含 `pid`+时间戳，
  撞名极罕见，但无脑清扫仍会踩到别人正在写的对象。安全候选形态是「能独占打开 + 判 size/年龄」再删，
  但**未验证**，本轮不写进契约。
  原「三档删除能力」的分档（探针 19）在取消删除动作后**只作机制解释、不再派生实现要求**：
  持有方不给删除共享时，按路径的删除与改名都会被 `0x80070020` 拒绝（`DeleteFile`/改名同报错，
  微软 DeleteFile 文档明写「被以不含删除共享的方式打开时删除失败」）；另两档
  （收紧自挡 `0x80070005`、路径消失 `0x80070002`）没有并发持有者，删除技术上可行——
  **但本契约不要求谁去删它**。
  三档**报错仍要各自点名真实成因**，不得共用一句「已有其他持有者」——那会把「我们收紧错了」
  误报成「有人盯着这个文件」，把排障方向带偏（同「报错必须点名真正给坏值的来源」红线）。
  即使是共享冲突档，也只能证明「有人持有句柄」，**不能**推出「内容已被读过」。
  ⚠️ **Node 做不到**：libuv 打开总带 `FILE_SHARE_DELETE`，实测其 `fs.openSync` 句柄**挡不住**
  `rmdir`（目录消失、路径可被重建、`statSync(path)` 已指向攻击者对象）→ ② 必须走 PowerShell/.NET
  或 P/Invoke，**纯 Node 实现不满足本契约**。
- ③ 读 DACL（同一个路径，此时无人能打开它）：出现任何非受信主体的允许 ACE，**或属主不在受信集合**
  → 关闭句柄、**不删除任何东西**、非 0 退出（留下空 tmp，见上统一规则）。
  ⚠️ **为什么干脆不删（探针 20 是直接诱因）**：③ 这一档我们持独占句柄，**持有期间按路径删不掉**
  （`DeleteFile` 报 `0x80070020`），要删就**必须先 `CloseHandle`**——而「关句柄之后再按路径删」正是
  把唯一能证明「这是我的对象」的手段丢在身后。`FileDispositionInfo`（随句柄标记删除、不必先关）
  本次调用方式不对（PS 强转失败）**未验证**，不得当替代方案；即便将来验通，也只是删自己那个空
  tmp 的优化，不改变「失败路径不碰别人对象」的底线。
  ⚠️ **③ 的执行清单与 ④ 之后的读回清单不同**（CodeRabbit round 98 major 1 定了「③ 不判继承位」这条
  原则，第十一轮把 ① 换成受限创建后**它的依据变了、结论不变**）：
  · ③（① 刚返回时）判第 1–5 条，**尤其第 3 条属主 SID**；第 6 条（继承关闭）**仍然不在 ③ 判**——
    受限创建产出的就是 `D:P(...)`（受保护、无继承位，探针 25/27 实测），③ 若要求它反而是在验一个
    已经成立的事实；真正需要判它是 ④ `icacls "<tmp 路径>" /inheritance:r` 的**结果**，所以只放在 ④ 之后的读回里。
  · ④ 之后的读回判**全部七条**（收紧会重建整份 DACL，属主/允许 ACE/继承位都可能被改动）。
  ⚠️ **③ 必须执行属主 SID 校验（第 3 条）**（CodeRabbit round 97 major）：
  只查 allow-ACE 名单**挡不住攻击者预置的文件**——若 ① 不是严格 `CreateNew`（或路径被换后落到攻击者
  预置对象上），③ 的允许 ACE 名单也可通过（攻击者故意只授当前用户），**但属主是攻击者**，
  属主隐含 `WRITE_DAC`，拿到句柄后即可给自己补读、读走 ⑤ 写入的 secret。所以 ③ 要在**写 secret 之前**
  断言 `owner SID ∈ 受信集合`；不满足即**关句柄、不删除任何东西**、非 0 退出、写入次数为 0
  （动作与上文「统一规则」一致——我在 CR97 那一版此处误写成「删除 tmp」，CR 98 取消删除动作时漏改）。
  （**归因要说准**：微软「new object 的 owner」文档说默认 owner 是创建者令牌属主，故**严格 `CreateNew` 成功时
  owner 必是我们自己**——这一档属主校验是**纵深防御 + 对「① 其实走了 Open 而非 CreateNew」这类实现退化的当场拦截**，
  不是「CreateNew 路线下真有攻击者属主文件」。真正的跨进程预置攻击能否造出 owner≠self 且 allow-ACE 干净的对象，
  **留 0.2.4 用夹具验**，不在此声称已复现。）
- ④ `icacls "<tmp 路径>" /inheritance:r /grant:r "*<SID>:(R,W,D)"` 收紧并读回确认（真机实测：**独占句柄持有期间
  `icacls` 照常可用**，E）。**读回确认必须再跑一遍 §2.4 清单全部七条**（收紧后属主/允许 ACE/继承位都可能变），
  再加**写序附加项 `W1`**（不并入上面的清单编号——清单第 8 条是「任一条判不了」，两者同名会混淆）：
  当前用户对该 tmp 的有效 `DELETE` 仍在（`W1` 的判据与理由见 §2.4 清单第 5 条的分层说明；
   **有效**同样是按 DACL 顺序**累加求值**的结果——`DELETE` 这个单权利请求在遇到第一条**主体命中且
   覆盖 `DELETE`** 的 ACE 时定案（allow → 有效、deny → 无效），不能一票否决，见 CR 129/133）。
  ⚠️ **收紧命令必须带 `D`（CodeRabbit round 110 major + Codex round 39 P2-1）**：`/grant:r` 是**替换**该委托人
  已有的显式 ACE，不是合并——写 `(R,W)` 会把 ① 特意加进去的 `DELETE` 抹掉，掩码从 `0x13019f` 掉回
  `0x12019f`（探针 33 B 档实测 SDDL 读回）；改成 `(R,W,D)` 读回就是 `0x13019f`（C 档），且对一份**本来就没有**
  `DELETE` 的文件也自足（E 档）。这不是「少写一个字母」的问题：清单第 5 条旧版只要求「至少含读权限」，
  所以这道抹除**能通过全部七条读回**，随后 secret 已写、换名才因缺 `DELETE` 失败。
  **判据必须盯住收紧后的产物，而不是 ① 的创建产物**——两者在旧配方下恰好不同。
  ⚠️ **命令必须带文件参数（CR 127 minor + Codex 56 P1）**：`icacls` 的语法是 `icacls <文件名> [/选项…]`，文件名在选项**之前**；旧文漏了它、照抄会直接报语法错、tmp 根本没被收紧，而 ⑤ 接着把 secret 写进继承可读的文件。`<tmp 路径>` 是 ① 创建出的**那个具体路径**（不是字面占位符），§2.4 方案 A 的摘要与 ② 步、本条三处必须指向同一个 tmp。
  ⚠️ **读回不通过就不得进入 ⑤**：完整七条的读回必须发生在写 secret **之前**；不得先只查继承、
  把七条拖到 secret 落盘之后再补跑（Codex round 39 P2-3 指出的形态——那等于把完整校验挪到了泄露之后）。
- ⑤ **通过 ② 拿到的句柄写 secret**——不许按路径重开（**这一步是失败语义的分界线**：一旦开始写，任何失败都按「secret 可能已落盘」处理，见上两臂）（CodeRabbit round 89：按路径重开时，攻击者可在
  收紧后把目录换掉再换回来，四条 `ino`/`dev` 比对全部通过而 secret 落进另一份文件）。
- ⑥ 关闭句柄 → 比对 `ino`/`dev`（一致才继续）→ 换名换入（子进程内 `MoveFileExW` +
  `MOVEFILE_REPLACE_EXISTING`，见上）→ **换入后立刻复核目标路径上的对象
  身份仍是我们那个 tmp**；不一致 → **响亮失败（不报 `configured:true`），但绝不删除、也绝不改名移走
  目标文件**。
  ⚠️ **这一档失败时 tmp 已含 secret**（⑤ 已完成），失败报告必须点名该残留路径（见上「按 secret 是否已写分两臂」）；
  「不写 secret」只对 ⑤ 之前的失败成立，不得写成全称。
  ⚠️ **比对与换名之间的窗口：数据完整性风险，当前契约挡不住（CR 127 major + Codex 56 P1）**——
  `ino`/`dev` 比对在换名**之前**、复核在换名**之后**，两者之间祖先目录仍可被替换；此时按路径的
  `MoveFileExW + MOVEFILE_REPLACE_EXISTING` 会落在**替换后的目录**，我们那份已收紧的 tmp 被换进攻击者
  （或任何人）指定的位置，而**目标位上原有的 `config.json`（可能是并发写者 B 刚写好的合法配置）被覆盖**。
  复核随后报「身份不一致」，但覆盖**已经发生、无法撤销**——「失败时不动目标」在这条路径上不适用
  （它只约束复核发现不一致**之后**的动作）。所以：
  - 真正闭合需要**绑定已核实目录对象**的换名原语（`SetFileInformationByHandle` 带 `RootDirectory`
    的相对换名 / `RenameAt` 形态）——**均未实测**，§2.4a 上文已记载按句柄换名在探针 14 系列下
    「调用成功但目标按路径不可见」，不能当作已解决；
  - **在此之前，本契约对此窗口的态度是「显式接受的数据完整性残余」**：它不危及机密性（secret 只进
    我们独占创建的对象，攻击者拿不到），但可能毁掉别人的合法配置。0.2.4 必须二选一并在实现里写明：
    **① 用绑定目录的换名原语彻底关闭**（先补真机探针验证可行），或 **② 显式接受并在实现 PR 中
    记录该风险**（例如失败报告点名「目标可能已被覆盖」）。**不得写成全称「已防护」或省略不提**。
  ⚠️ **⑥ 失败时「不动目标」是硬规定，取代我前两版「删除 / 隔离目标 + 跨进程串行化」**（CodeRabbit
  round 98 major 2 推翻 round 95我加的锁方案）：复核见到身份不一致时，当前 `config.json` 可能是
  ①攻击者留下的冒充文件，也可能是**并发写者 B 刚 `renameSync` 进去的合法新配置**——A **无从区分**，
  任何「删掉/改名移走」都会毁掉 B 的成果。而我上一版想靠「配置目录内锁文件」串行化这段，**锁本身挡不住**：
  A 在旧目录持锁、关句柄后目录被换，B 在**同一路径文本**上拿到的是**新目录里的另一把锁**，两者都自认
  持锁、都会去动目标——**路径式锁的身份被目录替换劫持了**，锁名唯一也没用。要让锁有效必须钉住**目录对象**
  （按句柄的目录锁 / 校验目录 `ino`），而纯 Node 拿不到可阻挡的目录句柄（探针 9/13）。**所以取消这个破坏性
  动作本身**，比给它配一整套原生依赖锁更简单、可验证、且 round 95 的并发删除竞态**以「没有该动作」关闭**。
  正确后果：A 报错退出、**不碰目标**；A 自己那份已 `renameSync` 的对象此时可能已被 B 覆盖（last-writer-wins，
  与今天 `writeConfigFile`的良性并发一致，见下归因），A 无需也无法安全回收。机密性不受影响（A 的 secret
  只写进 A 独占句柄的对象，从未落到攻击者或 B 的文件）；可用性上 A 这次 login 失败、用户重试即可。
  **前置失败（②/③）同样不删**（见上统一规则）：② 失败没有句柄、③ 要删就得先丢句柄——都不具备
  「正名后删除」的条件（空 tmp 的清扫策略见上文统一规则末尾——**留给 0.2.4 设计**，本轮不定）。
  ⚠️归因要说准（差点写错）：**当前 `writeConfigFile` 对并发 `auth login` 确实没有任何串行化**
  （实测 `src/core/config.ts`：无锁文件、无 `O_EXCL`、无互斥），但今天的并发是**良性 last-writer-wins**
  ——tmp 名带 `pid`+`Date.now()`、`renameSync` 原子换入，两个写者各写各的 tmp、后换入的覆盖，不损坏数据。
  **CR 95 指出的删除竞态不是今天就有、而是⑥ 这条「不一致就删目标」的新清理动作引入的**：
  一旦加了删目标的失败清理，没串行化时 A 就会删掉 B 刚验收的配置。所以这是「**别把新问题引进来**」，
  不是「补一个老 bug」。我上一轮的处置是「给删除动作配跨进程串行化」——**本轮（CR 98 major 2）连处置一起推翻**：
  路径式锁挡不住目录替换，正确做法是**取消⑥ 对目标的破坏性动作**（见上「不动目标」硬规定），
  竞态因「没有该动作」而消失，串行化前置要求也随之作废。**「不一致就删/移目标」不再是契约的一部分。**
  ⚠️ **可检测范围收窄**（CodeRabbit round 95 minor，也是对我上一版措辞的收回）：两次身份比对只能发现
  **持续到比对时刻**的替换。对方可以在 ⑥ 前比对之后换入目录、又在**换名那一步（`MoveFileExW`；旧实现写作 `renameSync`）**之前**换回原目录**——
 换名与复核都对着原对象**成功**，而中间那段冒充文件已被第三方读到，本序列**检测不到**。
  所以准确说法是：「持续到比对点的替换 → **可发现、可响亮失败（不碰目标、保留取证现场）**；
  **介入式换了又换回的替换 → 不可检测，且可与成功结果共存**」。上一版把它写成全称承诺（复核对任意替换都成立、
  并且必然不会报成功），**那种写法已被收回**；同一版还说可发现者「可清除」——**「清除」也收回**，
  因为 ⑥ 已规定不动目标（CR 98 major 2），发现后的动作是**报错 + 保留现场**，不是清理。
  第四轮的第 12 个探针按这条顺序实测过两种时序：
  · 替换发生在换名前 → `preCheck=false`，**换名根本不执行**；
  · 替换抢在换名前那一刻（pre-check 已过）→ `postCheck=false` **当场发现**，我们的 secret
    从未出现在这条路径上（⑤ 是经句柄写入，落在我们自己的对象里）。
    ⚠️ 本轮我曾给这条加过一个【待核】推测——「`MoveFileEx` 默认不允许跨目录换名，所以真实失败模式
    可能更安全」。**查官方文档后该推测被推翻并撤回**：MoveFileEx 的 `lpNewFileName` 明确可指向别处
    （只有跨**卷**才需要 `MOVEFILE_COPY_ALLOWED`；「目标须同卷」那条限制针对的是移动**目录**），
    与探针实测的「按路径换名成功、把攻击者文件送进目标位」一致。记这条是为了防止下一个读的人重复

   残余（如实声明，别写成「已彻底防御」）：目录钉住靠 ① 创建时拿到的独占句柄，**换名必须先关句柄**（实测
  `FileShare.None` 持有期间 rename 被拒），所以「关句柄 →换名」之间窗口重新打开：第三方读该路径
  可能读到**冒充文件**（完整性面，不含 secret——我们的 secret 始终在已删除/待换入的原对象里）；
  复核能发现**持续到比对点**的替换、响亮失败且**不碰目标**（换了又换回的介入式替换检测不到，见 ⑥ 的 CR 95/98 注）。
  **另有一条完整性残余（CR 127 major + Codex 56 P1）**：比对在换名前、复核在换名后，两者之间目录被替换时
  按路径换名**会覆盖目标位上别人的配置**，复核发现时已无法撤销——见 ⑥ 的专段，0.2.4 必须或其关闭、或显式接受。
  ⚠️ **元数据句柄能与我们的独占句柄并存**（CR round 103 的核心事实，探针 24 D 档）：在我们持
  `FileShare.None` 的整个期间，他人仍可按 `WRITE_DAC`/`READ_CONTROL` 打开同一个对象（数据读写被
  `0x80070020` 挡住）。所以「独占持有」只能证明「没人能读/写内容」，不能证明「没人在改它的 ACL」——
  这也是 ① 之后的每次 DACL 判据都必须按「此刻的 DACL 可能是别人刚改的」来写的原因。
  ⚠️ 曾设想「用 `SetFileInformationByHandle` **按句柄**换名」连这个窗口一起关掉。探针 14 系列
  （a→d）逐层查成因，也逐层推翻我自己的解释：
  - 探针 14a（naive：`ByValTStr` 定长缓冲 + 信息类号 10）报 **error 87**。我当时归因
    「该结构要卷内相对名」——**那是编造的**（CodeRabbit round 94 质疑后核实：官方文档明确
    `FileName` 接受绝对路径，`RootDirectory` 常见就是 NULL）。
  - **真因在探针 14c 查明**：`FILE_INFO_BY_HANDLE_CLASS` 里 **`FileRenameInfo = 3`，不是 10/11**——
    error 87 是我把**信息类号**传错，与路径形态无关。（教训：实验失败要怀疑到调用方式最底层，
    「相对名说」和「封送布局说」都是只猜对一半的半途解释。）
  - 探针 14c/14d 用正确的类 3 + 自算 x64 布局 + 绝对路径 + 独占句柄持有期间调用：调用**返回成功、

    （**换了又换回的介入式替换仍检测不到**——见 ⑥ 的 CR 95/96 注，别把这句读回全称承诺）；

**为什么这条能同时关掉前面的洞**（第十一轮按合并形态改写）：**受限创建**让「文件首次可被观察时」
就没有任何外部 ACE——攻击者连 `WRITE_DAC` 都拿不到（探针 29 E 档），旧主路线里「元数据句柄熬过

③ 保证这个对象在**我们这一侧的观测里**没有被写过非受信 ACE；⑤ 保证 secret 写进的正是 ① 创建、
③ 验过的那个对象（第四轮实测：目录被换后按**句柄**写仍落在我们自己的对象里，**secret 不会进攻击者的

⓪ 仍然必要（父目录不可信时连 tmp 都不该建）。

**两个残余窗口的内容是什么（实施者必读）**：
- **①→② 之间：合并形态下这个窗口不存在**（创建与独占持有是同一次调用，探针 25/27/29 实测产物

  一起作废**，保留在此只为解释为什么现在没有它。若 0.2.4 因为平台原因退回两次调用形态，
  整套窗口论证与「独占打开=探测持有者」必须一并恢复，不得只恢复一半。
- **⑥ 关句柄→换名之间**：文件已含 secret，但 DACL 在 ④ 已收紧到「仅当前用户（+ SYSTEM/Administrators）」，
  非受信主体此时打不开；`ino`/`dev` 比对再挡住「目录被换过」这一跳。

  **不删除**，留空文件待 0.2.4 的清扫策略处理；我上一版这里写「删除 tmp」，是第十轮 grep 窗口
  只覆盖写序段、漏了这段所致——CR round 99 minor 2）。

**已验证的机制边界（同一台真机，2026-11-24）**
- `FileShare.None` 的独占语义、`icacls` 与独占句柄并存、`renameSync` 需要先关句柄——
  这四条**都有真机输出**（见 gitignored 证据）。
- **载体红线（第六轮自查，探针 15–16）：secret 只能经 stdin 交给那个 PowerShell 子进程**。
  Windows 上任何进程的**完整命令行对同机其他进程可读**（`Get-CimInstance Win32_Process` 与 `wmic`
  两把独立机制都实测读到哨兵），所以把 appSecret 当参数传给子进程 = 直接泄露，违「凭证绝不入外部
  可见面」铁律；探针 16 实测 stdin 交付**不出现在 argv、且字节确实落盘**。环境变量、命名临时明文文件
 同样不许。**①–⑥ 的子进程接口 = stdin 进、结构结果出，argv 只带路径/常量。**
- **① 的受限创建＋独占持有必须有 .NET/PowerShell 或 P/Invoke**：Node 的 `fs` 走 libuv，
  `openSync` 总带 `FILE_SHARE_READ|WRITE|DELETE`，钉不住祖先目录（探针 13 实测 rmdir/ren/重建全部成功）；
  Node 也没有「带受限 SD 创建」的入口（`fs.openSync` 的 mode 在 Windows 上不落 DACL——§2.4 方案 B 的
  出发点）。**纯 Node 实现不满足本契约**；若因故只能纯 Node，必须把 ③④⑥ 标注为**弱保证**
  （「按路径判据可被目录替换劫持、创建瞬间 DACL 不受控」），不得声称已保护。
- PowerShell 不可用 / 非 NTFS → `checked:false`，并且**不写凭证**（fail closed，不冒认 ok）。

**第四轮（CR 93，探针 6–12）实测的句柄/路径语义（决定最终形态）**
- **Node 的句柄挡不住祖先目录被删**：libuv 打开文件带 `FILE_SHARE_READ|WRITE|DELETE`，实测「兄弟钉住」
  （在 `qiyu` 里开一个 `pin.lock` 不放）**并不能**阻止 `qiyu` 被删除；.NET 侧 `FileShare.Delete` 的
  组合也挡不住删除那一侧。→ 「钉住目录」在零原生依赖下**不成立**。
- **按句柄写 secret 是安全的**：祖先目录被替换后，`fs.writeFileSync(fd, secret)` 仍写进**我们自己**
  的对象（实测 SAME_OBJECT=false 时写入照样落在原对象），**secret 不会进入攻击者的文件**。
- **按路径 rename 才是泄露/错置的那一步**：路径被重建后 `fs.renameSync(path, dst)` 会把**攻击者的文件**
  搬进目标位置并返回成功（实测 `final.db content="ATTACKER"`）——破坏的是完整性，不是机密性。
- **真独占才钉得住祖先目录**（第五轮探针 13）：`.NET FileShare.None` 句柄持有期间 `rmdir /s`、`ren`
  均失败、路径也无法重建；**Node 的 fd（libuv 带 delete 共享）三者都挡不住**。
- **更强的一点（同轮探针 11）**：Node 持 fd 期间，**对方连我们这个文件本身都能搬走/删掉**
  （`move` 与 `rmdir /s` 都返回成功）——共享位是 per-handle 且 libuv 给了 delete 共享，
  所以「持有句柄」在纯 Node 下**不带来任何排他性**，只有 `.NET FileShare`不含读写时才能挡住
  **读取**（同轮探针 6：READER BLOCKED），仍挡不住删除。
- **纯 Node 可用的替换检测**：`fs.fstatSync(fd).ino/dev` 与 `fs.statSync(path).ino/dev` 比对，
  替换后立刻不一致（实测 SAME_OBJECT=false）。
- **祖先目录被删而路径消失时，Node 的 `renameSync`/`statSync` 直接 `ENOENT` 失败**（fail-closed，实测）。

### 2.5 回归防线
CI 仅 `ubuntu-latest`（`.github/workflows/ci.yml:18-25`），**无测试钉住 win32 短路本身**。建议最小 windows-latest job（跑不依赖 POSIX 的 auth/config/hint 方言子集）+ 静态守卫钉「win32 短路不得无覆盖静默存在」。ACL 夹具清单（0.2.4 实施时必须齐全，每条都要真机跑）：
1. 纯继承（默认新建）→ 判 `ok:false`（继承 ACE 未收紧）；
2. `/grant Everyone:(R)` → `ok:false`；
3. **`/grant *<另一个具名用户 SID>:(R)`、且无对应 deny ACE** → 必须 `ok:false`——这是防止探测判据退化回「广域黑名单」的最小反例（CodeRabbit round 74）；写成黑名单的实现只有这条会红；
4. 按修法收紧后（`/inheritance:r` + 仅授当前用户）→ `ok:true, checked:true`；
5. icacls/PowerShell 不可用或非 NTFS → `checked:false`，不得冒认 ok；
6. **null DACL**（`D:NO_ACCESS_CONTROL`，等于所有人完全访问）→ 必须 `ok:false`——ACE 列表为空，
   只数 ACE 的实现会把它判成「干净」，这是判据最危险的一种假绿（CodeRabbit round 75）；
7. **空 DACL**（`D:`，显式拒绝所有人的访问）→ 同样 `ok:false` 并提示重建 ACL，不得当成「收紧得好」；
   （**2026-11-24 实测：本机用 .NET 造不出空 DACL——设置静默不生效**；该夹具需另找造法，在造出之前不得声称覆盖。）
8. 正常受限 DACL（夹具 4 的那份）→ 仍须 `ok:true, checked:true`，证明①判空态没有把好形态一起拒掉；
9. **另一个普通账户作属主、DACL 里只授当前用户** → 必须 `ok:false`——属主隐含 `WRITE_DAC`，
   能给自己补读权限，ACE 名单看着干净不代表读不到（CodeRabbit round 76）；夹具 8 是对照组；
9(b). **deny `DELETE` 在前、allow `(R,W,D)` 在后**（同一用户）→ **两条判据方向相反，必须都写**
   （CodeRabbit round 115 minor：本档原先只说「必须 `ok:false`」，会把 §6.37 刚拆掉的读面拒绝又装回去）：
   · **读面**（`checkPermissions`）→ **必须 `ok:true`**：deny 只覆盖 `DELETE`，读权限照旧有效（allow 含读、
     无覆盖读面的 deny）；
   · **写序**（`W1`：对该 tmp 的有效 `DELETE`）→ **必须拒**：deny 排在授予 `DELETE` 的 allow **之前**，
     按序求值时 `DELETE` 未获授（探针 38 实测：`MoveFileExW`/`DeleteFileW` 均 `0x5`，且目标内容原样）。
     判据只看**允许掩码**的实现在这里放行，随后 ⑤ 写 secret、⑥ 才失败；deny 是**继承来的**
     （父目录或更高层）同样算。
   · **对照：allow `(R,W,D)` 在前、deny `DELETE` 在后**（CR 130 major）→ `W1` 必须**通过**：allow
     已覆盖 `DELETE`（单权利请求全部授齐），检查在到达后方 deny 之前结束。这条与上一条成对，
     把「累加/按序求值」与「一票否决」区分开。
9(c). **读面 deny 的隔离夹具（同一用户），两档必须成对出现**（Codex round 45 P2-1：单用
   `FullControl` 会把 deny 判据**遮蔽**掉——不过按 CR 128 更正后的第 5 条，`FullControl` 授给当前用户
   本身是合法的，遮蔽的原因只是它的 allow 掩码已含读、deny 解析的有无不改变结论）：
   · (i) **deny `READ_DATA` 在前、allow 只含 `Read` 在后** → 读面必须 `ok:false`（探针 40 B 档：
     读取 `0x80070005`；顺序是判据的一部分——见 (iii)，(i) 不得涵盖 allow 在前的形态）；
   · (ii) **allow 只含 `Read`、无 deny** → 读面必须 `ok:true`（探针 40 A 档：读取成功）；
   · (iii) **allow 只含 `Read` 在前、deny `READ_DATA` 在后**（CR 129 minor + Codex 57 P1）→ 读面必须
     `ok:true`：allow 只含 `Read` 已把所需读权利**全部授齐**，检查在遇到后方 deny 之前就以「全部授予」
     结束（若 allow 只授了**部分**权利，后方 deny 仍会生效，见第 5 条累加规则）；一票否决的实现会把它
     误判成 `ok:false`。
   前两档证明「deny 解析」在起作用（只有 (i) 时，一个完全不解析 deny 的实现也可能因别的条件拒掉），
   第 (iii) 档钉住**顺序**——只按「有没有 deny」判的实现会在这里被判红。
   （`FullControl` 那一版曾作为初稿写在 9(c)，**已撤换**：它证明不了自己声称的东西。）
9(d). **令牌组属性的 deny-only 档**（CR 131 minor + Codex 60 P2，两路同源）：受保护 DACL、属主与父目录
   均满足第 1–4、6–7 条，但**唯一的读授权是授给 `Administrators` 组**——
   · 当前进程是 UAC **非提权**令牌（Administrators 为 deny-only）→ 读面**必须 `ok:false`**：该组 SID 的
     allow ACE 被 Windows 忽略，按「组成员」实现的判据会误判可读；
   · 对照：同一 DACL 在**提权令牌**下 → 读面必须 `ok:true`（证明不是无条件拒绝该形态）。

   按第 8 条 `checked:false`，不得落到 `ok:true`。
9(e). **受限令牌的两遍检查档**（CR 132 minor，两档成对）：用 `CreateRestrictedToken` 起一个子进程，
   restricting SID 集里**没有**该 DACL 授予读的主体（例如 DACL 只授当前用户 SID、restricting 集只含
   `Everyone`）→ 读面**必须 `ok:false`**（普通 SID 一遍通过、restricting 一遍不通过）；
   · 对照：restricting 集**含**当前用户 SID → 读面必须 `ok:true`。两档都要求 CLI 跑在受限令牌下，
     **本机未实测**，0.2.4 必跑；实现读不到 `TokenRestrictedSids` → 第 8 条 `checked:false`。
10. **继承开启、当前 ACE 恰好只含受信主体** → 必须 `ok:false`（父目录一改就带进名单外 ACE）；
11. **文件本身干净、但父目录对另一个普通账户可写** → 必须 `ok:false`——对方可以删掉再重建，文件 ACL 再紧也没用（与 POSIX 目录判据同构）；
11(b). **父目录属主是非受信账户、DACL 里没有它的显式写 ACE** → 必须 `ok:false`（Codex 61 P2）：属主隐含
   `WRITE_DAC`，对方可先改写目录 ACL 再替换整个配置目录。与 11 成对——11 测 ACE 写面、11(b) 测属主，
   任一漏掉都会让 ⓪ 误判父目录受信；

13. **父目录对他人有可继承的只读 ACE（无写权限）**。主路线是 (a)；(b) 已降级为「平台不支持受限创建时
    的备选」，且必须同时声明 CR round 103 指出的泄漏面（见下），**不得当成等价实现**：
    (a) **受限创建路线**（`FileStream` 七参重载 + `FileSecurity`，**探针 25/27/29 实测可用，本设计采用**）：
        tmp 从创建起就只有当前用户可读，**不继承任何外部 ACE**；并发探针从文件首次可见起就必须
        **全程 Access Denied**（合并形态下没有「创建完还没独占」的窗口可言）。

    (b) **先建后验路线**（**已被 CR round 103 否证为主路线**：元数据句柄不受共享检查约束，
        对方可持 `WRITE_DAC` 熬过 ④ 再改写 DACL——探针 26 复现 secret 被读走）。若实现因平台限制
        退回这条，必须同时给出「元数据句柄如何被挡住」的机制，否则不得声称保护。它的失败判据仍是：
        实现必须在**写入任何 secret 之前**
        以独占打开失败或 DACL/属主自检失败的方式**拒绝退出（不删任何东西）**。判据不能是「文件被删且退出码非 0」
        （删除可能发生在写入之后，CodeRabbit round 93；且**删除本身在持有者不含删除共享时会失败**，
        CodeRabbit round 97——见探针 19），必须是**观测「写 secret 那一步从未被执行」**
        ——测试对写入函数打桩计数：任一前置检查失败时写入次数必须为 0，且 secret 字节不出现在任何文件。
        合法结局是「非 0 退出 + 残留空 tmp 如实报告」；**不删除是规定动作，不是失败降级**。
        ⚠️ **判红条件必须覆盖「调用过写入」这一档（Codex round 38 P2）**：旧版末句写「只接受 secret 已落盘判定
        违规」，于是「提前调用了写入函数、但 I/O 在落盘前失败」这种时序违规会被放行。判红条件改为
        **「写入函数被调用次数非 0」或「发现 secret 字节」任一成立即红**——前置检查失败时这两条都必须不成立。
    (c) **父目录只授当前用户 Modify / `FILE_ADD_FILE`（不含 `FILE_DELETE_CHILD`）**（Codex round 38 P2）：
        `icacls` 的 `(OI)(CI)M` 展开成 `0x001301BF`（探针 32 E 档），**不含 `FILE_DELETE_CHILD`**——若 tmp 的
        ACE 也不含 `DELETE`，换名就会在 secret 已写之后才失败。**两档都要跑（CR round 111 minor）**：
        (i) **目标不存在（首次创建）** → 合规结局是**换名成功**（依据是源文件自身的 `DELETE`，主路线 ACE 取
        `Read | Write | Delete`），换入后目标 SDDL 是 `D:P(…0x13019f…;自己)`；
        (ii) **目标已存在且其 ACL 不含 `DELETE`**（如历史遗留的 `0x12019f`）→ 换名会 `0x5` 失败（探针 37 实测），
        这是**允许的结局**，但必须按「secret 可能已落盘」那一臂：非 0 退出 + 报告含 secret 的残留路径 +
        不删不移；**不得报 `configured:true`**，也**不得**为了让它成功去改目标文件的 ACL。
        ⚠️ **本机造不出干净的判据**：探针机的 ssh 令牌带已启用的 `SeBackup`/`SeRestore`（探针 35b），
        删除与改名会**绕过 ACL**（探针 32d：显式 `DENY DELETE` + 父目录 `DENY DELETE_CHILD` 仍然改名成功；
        探针 36 在禁用这两个特权后立刻 `0x5`，成因已确认），
        所以这一档的「权限不够就失败」**未实测**，0.2.4 必须在普通账户下补跑。
14. **`qiyu` 目录的祖先把「替换子项」权限给了另一个账户**（而 `qiyu` 自身写面受信）：对方在 ① 之后
    尝试把 `qiyu` 换成同名目录 + 另一个 tmp。合规结局按独占持有的实现分档（探针 13 实测，round 93 major 2）：
    (a) **`.NET FileShare.None` 持有期间**：替换**当场失败**（rmdir/ren/重建全被挡）——这就是「替换操作
        期间目录受保护」；换名须先关句柄，⑥ 的「比身份 → 换名 → 复核」继续兜关句柄后的窗口；
    (b) **纯 Node fd（libuv 带 delete 共享）**：替换**会成功**，路径判据随后全指向攻击者对象——
        此档只能声明为弱保证，实现若走这档必须让「按路径重开 tmp」与「把冒充文件换成目标并报成功」都判红。
    判据统一：secret 全程不得进入攻击者可打开的对象；目标路径最终要么是我们的对象、要么响亮失败。

### 6.57 顺序求值更正（CR 129 minor + Codex 57 P1，对 `85df1af`）

### 6.61 访问检查是「累加」不是「首条命中」（CR 133 minor，对 `0e7cf06`）

- **问题**：读面判据写成「Windows 逐条求值，**第一条命中当前用户（直接或经所属组）的 ACE 就决定结果**」。
  微软《How AccessCheck Works》的算法是**累加式**：命中的 allow ACE 授予的权利逐步累加，**直到请求的
  权利全部被授予才通过**；中途遇到「命中且否定任一所需权利」的 deny ACE 即终止并拒绝；走完 DACL 仍缺
  权利则隐式拒绝。所以「第一条命中主体的 ACE」并不决定全部——一条只授 `READ_DATA` 的 allow ACE 不授予
  `READ_ATTRIBUTES`/`READ_CONTROL` 等其余所需权利。反过来，此前为修正 CR 129 写下的「deny 排在 allow
  **之后**一律不生效」也**过宽**：只有前面的 allow 已把所需权利**授齐**时检查才提前结束；只授一部分时，
  后方覆盖任一所需权利的 deny 仍会终止整个请求。

  ③ `W1` 写明「找第一条**主体命中且覆盖 `DELETE`** 的 ACE」并注明单权利请求下与累加算法等价；

  同步；⑥ §6.57/§6.58/§6.59 的历史转述加注指向本节。
