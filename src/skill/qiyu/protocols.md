# 数据可信度协议

本地库与实时 API 是两个数据面，任何「有多少、什么时候、对不对」的回答都要先经过本协议。
核心原则：**下结论之前，证据链必须闭环**——哪个命令、哪个窗口、哪个过滤条件，缺一不可。

## 1. 下结论前先看 meta

`qiyu query` 的输出自带 meta，至少检查这几项再说话：

- `rows` / `limit_applied` / `truncated`：`truncated` 为 true 表示只拿到截断样本——放宽
  `--limit` 或缩小时间窗口重查，不要拿样本当全量。
- `warnings`：非空必须逐条读。它们点名「窗口内部有缺口」「区间天数不足」这类**静默失败**；
  忽略 warnings 的 Agent 会把残缺数据当事实汇报。
- `masked` / `masked_columns` / `mask_warnings`：输出默认脱敏；`mask_warnings` 非空说明
  脱敏可能不完整，含敏感列的结论要额外小心。
- `resolved_range` / `data_coverage`：命令实际生效的时间区间、本地数据的实际覆盖范围。
  报告结论时带上这两个区间，让人类知道你算的是哪段数据。
- `--sql` 通道不判定区间与覆盖：`resolved_range` 与 `data_coverage` **恒为 null**——实际
  区间以你写的 SQL 过滤为准，报告时自己写清。

## 2. 0 行 ≠ 没有数据

0 行是比报错危险的失败模式——错误处理不会触发，你会直接汇报「没有数据」。0 行至少有三种成因：

1. **窗口写错**：相对时间按上海时区解析，而 Agent 常跑在 UTC 容器里——「昨天」可能不是
   人类说的昨天，且不会报任何错。
2. **本地还没同步到这段**：用 `qiyu sync status` 看水位与缺口；`qiyu sync verify` 可以核对
   本地与远端的一致性——但**只有快照任务**与远端行数核对（`expected_from_api`），windowed
   任务不请求远端、只核对本地行数与同步状态记录，**drift 为空不代表与远端一致**（发现
   漂移时以非零退出码明示）。缺口先看 `gaps[].reason`：
   `rate_limit_local` 等到 `detail` 里的时刻再重跑，`fetch_failed`/`write_failed`/
   `count_mismatch` 重跑 `sync run` 覆盖该区间；`knowledge_row_malformed`/
   `filter_matched_no_staff`/`export_*` 是**成功窗上的提示**（数据未必缺，按 `detail` 判断）。
   - ⚠️ **`range_status` 的两个取值字面都在撒谎**（逐值释义见输出的 `meta.field_notes`）：
     `complete` 只表示「水位推进过」——中窗失败时它照样是 `complete`，**不是**「全窗口成功」；
     `pending` 只表示「最近一次运行没推进水位」——首窗失败时后续成功窗照常落库，**不是**
     「库里没数据」；先成功一轮再跑一轮首窗失败同样回到 `pending`（watermark 保留上一轮的
     值），所以也**不是**「从未同步过」；更**不是**「正在同步」。判数据完整不要只看
     `range_status`，也不要只看 `gaps`——
     **空 `gaps` 不等于完整**（`windows.skipped > 0` 时可能没有缺口记录、但请求区间仍有
     未覆盖段）。要同时看覆盖范围（`sync status` 的 `resolved_range`、以及 `sync run` 的
     `windows.skipped` —— status 与 verify 都不输出后者）与历史缺口的新鲜度。
   - ⚠️ **`gaps` 是历史记录，不等于「当前仍缺」**：旧记录与新记录的 `reason` 相同，按
     `reason` 分不出新旧；`range` 也只能说明「相关」——换边界重跑后数据可能已补齐，而旧
     缺口的 `range` 仍与你评估的区间重叠。**没有一次覆盖核对就不能确认新鲜度**：写
     「该区间有历史缺口记录，新鲜度未确认」，不要直接报成当前故障。
   - ⚠️ `sync run` 的 `status: "partial"` **也覆盖「一行都没落」的全窗失败**：两个字段分开
     读——`windows.succeeded` 是成功窗数（空窗也算成功），`rows.written` 才是落库行数。
   - ⚠️ **`sync verify` 的 `drift` 为空 / 退出码 0 不能当完整性证据**：对 windowed 任务
     它只核对同步状态记录（实测中窗失败的库同样给 `drift: []` + 退出码 0），快照任务另有
     上游行数核对。windowed 的完整性要另行核对两处：`sync status` 的 `gaps` 与
     `resolved_range`，以及 `sync run` 的 `windows.skipped`（status/verify 都不输出它）。
   - ⚠️ `locked: true` 是**残留的写者章**（上一轮被强杀），不是「正在同步中」——真持锁的
     写者会让 `sync status` 先退避等待，等到后读到的是那一轮的结果。重跑 `sync run` 即可。
3. **真的没有数据**。

报告 0 行时写「查询窗口 X 到 Y 内 0 行」，并说明排除了哪几种成因；不要写「系统里没有」。

## 3. 单位用 stats fields 核对

- **绝不猜单位**——百分比还是绝对值、按日还是按小时，猜错数字全错。报表字段的声明单位、
  本地观测分布、哨兵值由 `qiyu stats fields <报表表>` 给出。
- **`declared.<字段>.unit` 的每个取值怎么用，看输出的 `meta.field_notes`**（那里逐值给了
  释义与动作）：`ms` 是毫秒；`unknown` 是「判不出单位」而不是「没有单位」（如实写
  「单位未知」，不要猜）。`ratio` 的 0–1 量纲**只有 `assignedRatio` 经设计稿实测**——
  其余 `ratio` 是按名字推断的（`source: name-suffix`，**推断不是实测**）。`observed` 的
  `min`/`max` 只能核对一致性、**不是量纲证据**：全都落在 0–1 时，它与「0–1 小数」和
  「数值恰好都 <1% 的百分数」都相容。量纲不明确就**报告原值并标注不确定**，不要自行
  换算成百分比。
  `source` 就告诉你这条声明是实测（`design-doc`）还是命名推断。
- `declared.<字段>.higher_is_better` **恒为 null**——没有任何上游依据，不要据此判断指标
  好坏方向，也不要一直等它变成 true/false。
- 哨兵值会混进聚合（例如「无处理人」用特殊编号表示，不排除就会凭空多出一个「员工」）。
  先看观测分布，再决定过滤条件。
- 声明了但本地观测不到取值的字段，报告时写「未观测到取值」——声明是契约，不是事实。

## 4. 时间一律用绝对日期

- 结论里写绝对日期（如 2026-10-20），不写「昨天」「上周」——相对词在不同时区下指向不同的日子。
- 命令的 `--since` / `--until` 接受绝对日期与 ISO 8601。**只给 `--since` 时上界是当前时刻**
  （含今天已同步的数据）；今天的日报行通常次日才落库，所以区间尾部常为空——以
  `resolved_range` / `data_coverage` 判断实际覆盖。要把窗口止于某个自然日，显式给 `--until`
  （日期型列含该日全天；时刻型列请写清时刻，裸日期会被当成当天零点）。
- 所有相对时间按上海时区解析；响应里的 `resolved_range` 是实际生效的区间——引用它，不要复述
  你自己的输入。

## 5. 结论要带出处

- 每个数字都能指回一条命令与一个窗口；指不回来的数字不要写进结论。
- 推断与观测分开写：推断要标注「推断」，不要包装成观测结果。
- 不确定就说不确定。对数据任务，一个带不确定性的诚实结论远好过一个干净的错误结论。
