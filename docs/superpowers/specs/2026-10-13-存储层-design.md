## 一、目标与非目标

### 1.1 目标

建立一个**本地数据仓库抽象层**，使：

1. **D（同步引擎）可以开工** —— 它只需要 `Store` 接口与一个可用的 DuckDB 实现；
2. **E（查询/沙箱）/F（Skill）有稳定的读入口** —— 只读查询脱离七鱼限流；
3. **配置可自定义** —— 库路径、后端类型、行为参数都可在配置文件中按 profile 设定，
   且后端类型在**接口层**为多后端预留（C2 接外部库时不改调用方）。

### 1.2 非目标（C1 明确不做）

| 不做 | 归属 | 理由 |
|---|---|---|
| Kysely 外部后端（Postgres/MySQL/SQLite）与连接串配置 | **C2** | 用户裁决「拆 C1/C2，先 DuckDB」：D 只需 DuckDB，外部后端不阻塞关键路径 |
| 三层只读查询沙箱（`--sql`） | **E** | 路线图 §四.E 明列沙箱为 E 的产出；C1 只提供 `query()` 原语且**不暴露任何命令**（见 §7.4） |
| 全部 ~20 张业务表的 DDL | **D 及各业务域** | 设计稿明说「完整 DDL 未给，只有表/主键/实测字段清单」；D2 决策「字段语义以实测为准」，空建 18 张表大概率被 D 推翻（先例：`staff_attendance` 粒度随参数切换、`tickets` 线上 27 键 vs 文档 16 键） |
| `db tables` / `db describe` 命令 | **E** | 路线图 §四.E 已划定；C1 的 `store status` 只输出表名与行数，不输出列元数据 |
| `auth login`（配置文件写入者） | **G1** | `src/commands/auth.ts:57-76` 现状是显式报错「尚未实现」；C1 的配置层只有**读者**，无写入者（见 §三.4） |
| 加密存储 | 范围外（设计稿 §6.5 明确） | 与「Agent 可 `--sql` 直查」冲突；密钥管理超出 CLI 范围 |
| `messages` 明细表 | 设计稿 §2 范围外 | 本阶段不做 |

## 三、配置体系

### 3.1 配置文件位置与形态

**位置**：`~/.config/qiyu/config.json`（设计稿 §4.2 既定；`chmod 600`）。

> **⚠️ 裁决（controller，2026-10-13）：两个根目录并存是接受的，不统一。**
> 设计稿 §4.2 定配置在 `~/.config/qiyu/`，而 C1-D4 定数据库在 `~/.qiyu/duckdb/`。
> 二者语义不同（配置 = 设置；数据 = 仓库，且是百万行级 PII），且 §4.2 已写进设计稿与
> README，改口成本大于收益。**代价若判错**：用户需要记两个路径。缓解：`store init` 的
> 输出与 `store status` 都回显实际使用的配置文件路径与库路径。

**形态**（全部字段可选；缺省走内置默认）：

```json
{
  "defaultProfile": "default",
  "profiles": {
    "default": {
      "appKey": "…",
      "appSecret": "…",
      "store": {
        "backend": "duckdb",
        "path": "~/.qiyu/duckdb/qiyu.duckdb",
        "readOnlyRetryMs": 30000,
        "batchSize": 1000
      }
    },
    "prod": { "store": { "path": "~/.qiyu/duckdb/prod.duckdb" } }
  }
}
```

### 3.2 优先级（与凭证既有三级一致）

**命令行 flag > 环境变量 > 配置文件 > 内置默认**。

| 项 | flag | 环境变量 | 配置文件键 | 默认 |
|---|---|---|---|---|
| 库路径 | `--db <path>` | `QIYU_DB_PATH` | `profiles.<p>.store.path` | `~/.qiyu/duckdb/qiyu.duckdb` |
| 后端 | `--backend <name>` | `QIYU_STORE_BACKEND` | `profiles.<p>.store.backend` | `duckdb` |
| profile | `--profile <name>` | `QIYU_PROFILE` | `defaultProfile` | `default` |
| 读锁重试上限 | — | — | `profiles.<p>.store.readOnlyRetryMs` | `30000` |
| 批量行数 | — | — | `profiles.<p>.store.batchSize` | `1000` |

> 沿用 `src/core/credentials.ts:resolveCredentials` 的既有优先级语义（该函数已实现「命令行 > env > 文件」
> 三级合并），新增的 store 配置项**复用同一套解析顺序**，不另立规则。

### 3.3 未知键 fail-closed

配置文件中出现**未知键** → 明确报错（退出码 2，`kind: 'usage'`），消息点名未知键路径
（如 `配置文件未知键：profiles.default.store.backendd`）。

理由：本仓的契约诚实性原则——「声明了但没人读」的字段是本仓要消灭的形态（路线图 §八 条目 6 的
`category` 先例）。一个拼错的配置键**静默无效**等于让用户以为设置生效了。
**`store` 块缺键不报错**（走默认）—— 只有**多余的**键才报错。

### 3.4 已知缺口：配置文件没有写入者

`auth login`（设计稿 §4.2 承诺的「写入 `~/.config/qiyu/config.json`」）**归 G1，尚未实现**
（`src/commands/auth.ts:57` 现状是显式报错）。因此 C1 的配置层是**只读**的：

- 用户需**手工创建/编辑** `~/.config/qiyu/config.json`；
- 或完全靠 flag/env（`--db` / `QIYU_DB_PATH`）指定库路径；
- `store init` **不写**配置文件（不越界实现 `auth login` 的职责）。

**如实记入**：C1 交付后，「配置文件通道」在 `auth login` 落地前只能手工使用。README 必须写明这一点，
不得暗示 CLI 会替你写配置。

## 四、`Store` 抽象（`src/store/types.ts`）

### 4.1 接口签名

```ts
export type BackendName = 'duckdb'   // C1 唯一实现；C2 扩 'postgres' | 'mysql' | 'sqlite'
export type StoreMode = 'ro' | 'rw'

export interface StoreConfig {
  backend: BackendName
  path: string
  readOnlyRetryMs: number   // 读者拿锁的退避上限，默认 30000
  batchSize: number         // 多值 INSERT 每批行数，默认 1000
}

export interface QueryResult {
  columns: string[]
  rows: Record<string, unknown>[]   // JSON 安全值：无 BigInt、无 Date 包装对象
}

export interface Store {
  /** 幂等建表 + 推进迁移。仅 rw 模式合法。 */
  init(): Promise<void>
  /** 表名清单（含元数据表）。 */
  tables(): Promise<string[]>
  /** 单表行数。 */
  count(table: string): Promise<number>
  /** 批量 upsert；内部构建多值 INSERT，绝不逐行循环。返回写入行数。 */
  upsert(table: string, rows: Record<string, unknown>[]): Promise<number>
  /** 原始查询原语。C1 不通过任何命令暴露它；三层沙箱归 E。 */
  query(sql: string, params?: unknown[]): Promise<QueryResult>
  close(): Promise<void>
}

/** 工厂：按 cfg.backend 查后端注册表；未知后端 → usage 错误。 */
export function openStore(cfg: StoreConfig, mode: StoreMode): Promise<Store>
```

### 4.2 设计约束

1. **接口无 DuckDB 痕迹** —— 无 `DuckDBInstance`、无 `getRowObjectsJson` 等类型泄漏到
   `types.ts`。C2 接外部后端时**只新增 `kysely.ts`，不改 `types.ts` 与调用方**。
2. **`rows` 进出都是 JSON 安全值** —— BigInt/Date 的转换消灭在 `duckdb.ts` 边界内
   （实测：`getRowsJS()` 的 BigInt 会让 `JSON.stringify` 直接抛异常）。
3. **`upsert` 语义由实现保证一致** —— 接口只承诺「按主键冲突时更新非键列」，
   实现按 §五.3 用 `ON CONFLICT … DO UPDATE SET` 显式列全非键列。
4. **后端注册表**（`src/store/index.ts`）：`Record<BackendName, () => Promise<Store>>` 形态的
   惰性映射，使 `openStore` 不必静态 import `duckdb.js`——这是 optionalDependency 惰性加载的落点。

### 4.3 分层约束

- `store/` **可以** import `core/`（用 `core/errors.ts` 的 `ErrorKind`）—— 方向单向，无环。
- `store/` **不得** import `sync/`（设计稿 §3.2 明文）。
- `core/` **不得** import `store/`（既有约束：`core/` 不 import `commands/`，同理不依赖上层）。
- `commands/store.ts` import `store/`（命令层消费，合法）。

## 五、DuckDB 实现（`src/store/duckdb.ts`）

### 5.1 惰性加载与依赖缺失

```ts
const mod = await import('@duckdb/node-api')   // 仅在 openStore 真正被调用时执行
```

- `@duckdb/node-api` 进 **`optionalDependencies`**（约 115MB、8 个平台包、无 node-gyp 回退、
  不支持的平台硬失败）——`api`/`auth` 等命令**完全不加载它**，保持轻量。
- **导入失败**（包未安装 / 平台不支持）→ 抛 `kind: 'store_not_initialized'`，
  message 与 hint 区分两种成因：
  - 未安装：`hint: '未安装 DuckDB 依赖。请运行：npm i @duckdb/node-api'`
  - 平台不支持：`hint: '当前平台无 DuckDB 预编译包（无 node-gyp 回退）。请改用外部后端（C2）或受支持的平台'`
- **裁决（controller）**：不为「依赖缺失」新增第三个 kind。Agent 对这两种成因的处置动作
  都是「解决环境后重试」，`store_not_initialized` 的 `retryable: false` + 明确 hint 已足够；
  新增 kind 会稀释 `ErrorKind` 的语义密度（本仓错误层以 message 承载细分，不以 code/kind 堆叠）。

### 5.2 单写者 + 读者退避（实测约束）

实测矩阵（`@duckdb/node-api@1.5.6-r.1` + Node 24）：`rw→rw` 阻塞、`rw→ro` 阻塞、
`ro→rw` 阻塞、**`ro→ro` 正常**。错误原文：`IO Error: Could not set lock on file … Conflicting lock is held`。

设计：

| 角色 | 行为 |
|---|---|
| 写者（`init`/D 的同步） | 以 `rw` 打开；**单写者**约定；进程退出即释放 |
| 读者（`status`/E 的查询） | 以 `ro` 打开；冲突时**指数退避重试**（实测约 2.6s / 13 次成功） |
| 退避上限 | `readOnlyRetryMs`（默认 30000）；超过 → `kind: 'store_locked'`、`retryable: true`、`hint: '写方持有数据库锁，请稍后重试'` |

- **Agent 不得被无限阻塞** —— 这是有界重试的硬理由。
- **写操作包事务**：`BEGIN … COMMIT` 避免空档；`kill -9` 后 DuckDB WAL 自动重放
  （实测数据完整），C1 不做额外恢复逻辑。

### 5.3 upsert 与批量写入

- **`ON CONFLICT (<pk>) DO UPDATE SET <全部非键列>`** —— 实测 `INSERT OR REPLACE` 跨引擎语义
  不一致（DuckDB 保留未列出列、SQLite 置 NULL）。**显式列出每一个非键列**，不得用 `excluded` 简写
  之外的省略形态。（DuckDB 无 UNIQUE 约束时会拒绝 `ON CONFLICT`——故建表时主键必须声明。）
- **多值 INSERT**：`upsert` 内部按 `batchSize` 切批构建多值语句。实测逐行 243.6ms/批 vs
  多值 10.9ms/批（**22 倍**），80 万行不退化。**绝不逐行循环**。
- 返回值为实际写入行数。

### 5.4 类型与序列化（实测约束）

| 约束 | 实现 |
|---|---|
| 只用 `getRowObjectsJson()` | `getRows()` 返回 `DuckDBDateValue` 包装对象；`getRowsJS()` 含 BigInt/Date → `JSON.stringify` 抛异常。`query()`/`count()` 一律走 `getRowObjectsJson()` |
| ID 列统一 `VARCHAR` | `BIGINT` 在 DuckDB 读回 bigint、better-sqlite3 静默丢精度、`node:sqlite` 抛 `RangeError` |
| 时间值不走本地 getter | 在 `TZ=America/New_York` 下 `DATE '2026-01-01'` 会读成 2025-12-31；一律走 JSON 安全路径（返回字符串） |

### 5.5 锁行为的可测性（降级裁决）

**真跨进程锁无法在 `npm test` 内断言**：`tests/` 无 `spawn`/`child_process` 先例、无 tsx、
`testTimeout: 5_000` 无余量（B 的 spec §十二 第 6 条已记录此缺口，并明确「不在 B 的范围」）。
且**同进程双实例测不了真锁**（实测：同进程多实例可同时打开但互相看不到对方写入）。

**裁决（controller）**：

- **退避逻辑纯函数化** —— 把「尝试获取 → 失败 → 等待 → 重试」抽成接受**注入的 `tryOpen` 函数**的
  纯函数，单测注入假实现验证退避曲线（次数、总耗时上界、超时后抛 `store_locked`）。
- **真跨进程锁行为** → **发布前手动 checklist**（两个终端：写进程持锁时跑 `store status`，
  应看到退避后 `store_locked`；写进程退出后应立即成功）。与 B 的验收 12/24 降级模式一致。
- 该降级**记入 §十 验收判据**并标注「手动」。

## 六、Schema 与迁移（`src/store/schema.ts`）

### 6.1 表范围（C1-D3）

| 表 | 主键 | 列（C1 建表用） | 来源 |
|---|---|---|---|
| `sync_state` | `dataset` | `dataset` VARCHAR PK、`watermark` VARCHAR、`range_status` VARCHAR、`last_error` VARCHAR、`locked_by` VARCHAR、`locked_at` VARCHAR | 设计稿 §6.2 元数据表 + §6.4 单写者锁字段 |
| `sync_gaps` | `(dataset, range_start)` | `dataset` VARCHAR、`range_start` VARCHAR、`range_end` VARCHAR、`reason` VARCHAR、`recorded_at` VARCHAR | 设计稿 §6.2 元数据表 |
| `tags` | `id` | `id` VARCHAR PK、`name` VARCHAR、`color` VARCHAR | 设计稿 §6.2：实测 24 行、每行恰好 3 键、`color` 匹配 `^#[0-9A-F]{6}$` |

外加元数据表 `schema_version`（`version` INTEGER）—— 迁移水位。

**`tags` 作为示范业务表的理由**：字段最少（3 键）、无分页、结构扁平（无层级/parentId）、
24 行小样本 —— 用最小表面打通「建表 → 多值 upsert → 查询 → 幂等再 init」全链路。
它**不是**「顺手做了 D 的表」，D 仍负责 `tags` 的真实同步（含「该接口完全忽略请求 body」这条实测陷阱）。

### 6.2 声明式表定义

表定义写成**声明式结构**（非裸 DDL 字符串），使 C2 能为 SQLite 生成对应 DDL：

```ts
interface ColumnDef { name: string; type: 'VARCHAR' | 'INTEGER'; nullable: boolean; sensitive?: boolean }
interface TableDef { name: string; columns: ColumnDef[]; primaryKey: string[] }
export const TABLES: TableDef[] = [ … ]
export function ddlFor(t: TableDef): string   // 当前仅 DuckDB 方言
```

- **`sensitive` 标注机制进 C1**（`tags` 无敏感列，故均为 `false`）——E 的 `db describe` 直接消费；
  按设计稿 §6.5「必须**按表**标注，不能靠跨域名称模式」（会话导出用 `userPhone`、工单域用
  `crmUserPhone`，两域字段名互不相交）。
- **迁移**：`schema_version` 表 + 有序迁移数组；`init()` 幂等推进到最新版本。
  **不引入迁移框架**（纯数组 + 顺序执行），YAGNI。

### 6.3 ID 一律 VARCHAR

按 §五.4 的实测约束，所有 ID 列（`sync_gaps.dataset` 等）统一 `VARCHAR`。
`tags.id` 亦为 `VARCHAR`（虽实测为 int）—— 保持全仓一致性，避免将来 `staff.id`（330 行）
等真 ID 列出现时两种类型并存。

## 七、命令（`src/commands/store.ts`）

### 7.1 `store init`

```
用法：qiyu store init [--db <path>] [--profile <name>] [--backend <name>]
```

- 创建父目录 → 以 `rw` 打开 → 建表 → 推进迁移 → 输出：

```json
{"ok":true,"data":{"path":"/Users/x/.qiyu/duckdb/qiyu.duckdb","backend":"duckdb",
 "configFile":"/Users/x/.config/qiyu/config.json","schemaVersion":1,
 "tables":["schema_version","sync_state","sync_gaps","tags"]}}
```

- **幂等**：重复执行 = 成功（表已存在不报错，`schemaVersion` 不变）。
- 锁冲突 → 退避 → `store_locked`（退出码 1）。
- 回显 `configFile`（即使文件不存在也回显其**预期路径**）——缓解 §3.1 的「两个根目录」成本。

### 7.2 `store status`

```
用法：qiyu store status [--db <path>] [--profile <name>] [--backend <name>]
```

- 以 `ro` 打开 → 输出：

```json
{"ok":true,"data":{"path":"…","backend":"duckdb","schemaVersion":1,"locked":false,
 "tables":[{"name":"tags","rows":24},{"name":"sync_state","rows":0}, …]}}
```

- 库文件不存在 → `kind: 'store_not_initialized'`、退出码 **1**、
  `hint: '数据库尚未初始化。请先运行：qiyu store init'`。
- 锁冲突 → 退避后 `store_locked`、退出码 1（**这就是验收触发器**）。

> **⚠️ 裁决（controller）：hint 指向 `store init`，而非设计稿 §9.5 写的 `sync run`。**
> 设计稿 §9.5 原文是「`kind: "store_not_initialized"` + 指向 `qiyu sync run` 的提示」——
> 那是**站在 D 交付后**的视角。C1 交付时 D 尚不存在，指向一个不存在的命令是「承诺了但不存在的能力」。
> **C1 指向 `store init`；D 交付时改指 `sync run`（D 的 spec 负责改，C1 在 spec 里记这条交接）。**

### 7.3 注册与用法文案

- `src/cli.ts` 的 `COMMANDS` 加 `store: storeCommand`；
- 顶层 `USAGE` 加两行中文说明；
- `store` 自己的 `--help` 中文（沿用 `api`/`auth` 的次序惯例：未知参数 → help → 位置参数）。

### 7.4 不暴露 `query()`

C1 **没有任何命令**能执行任意 SQL。`Store.query()` 是给 E 用的内部原语；
在 E 交付三层沙箱之前，暴露它等于把无防护的 SQL 执行面直接交给 Agent
（实测无防护时可 `COPY TO` 写文件、`read_csv('/etc/passwd')`、SSRF）。**这是硬边界。**

## 八、错误契约

### 8.1 新增 `ErrorKind`

`src/core/errors.ts:3` 的 union 追加两个成员（含注释说明成因与退出码）：

| kind | 触发 | retryable | 退出码 | hint |
|---|---|---|---|---|
| `store_locked` | DuckDB 跨进程锁冲突，退避至 `readOnlyRetryMs` 仍失败 | `true` | 1 | `写方持有数据库锁，请稍后重试` |
| `store_not_initialized` | 库文件不存在 / 表缺失 / `@duckdb/node-api` 未安装或平台不支持 | `false` | 1 | 见 §5.1 与 §7.2（分三种成因） |

### 8.2 退出码归类

| 情形 | 退出码 | kind |
|---|---|---|
| 库文件不存在（`store status`） | **1** | `store_not_initialized` |
| `@duckdb/node-api` 未安装 / 平台不支持 | **1** | `store_not_initialized` |
| 锁冲突超时 | **1** | `store_locked` |
| `--backend` 传未知名（如 `--backend oracle`） | **2** | `usage` |
| 配置文件含未知键 | **2** | `usage` |
| 配置文件 JSON 畸形 | **2** | `usage`（点名文件路径与解析错误） |

> 「未安装依赖」与「库未初始化」都归 1 而非 2：它们是**环境/状态**问题，不是**调用方式**错误 ——
> 换任何参数都不会成功（与 `auth login` 未实现时归 2 的区别：那是「你调了一个不存在的功能」）。

### 8.3 联动文案（契约诚实性）

以下文件必须同步更新，否则就是「说了假话」：

1. `src/cli.ts` 顶层 `USAGE` —— 加 `store init` / `store status` 两行；
2. `src/cli.ts` 的错误 kind 列举句（现列 `usage / network / internal / auth_missing /
   confirm_required / local_rate_limit / unknown`）—— 加两个新 kind；
3. `README.md` 错误 kind 表 —— 加两行；
4. `README.md` 「零运行时依赖」段 —— **必须改写**：C1 引入 `@duckdb/node-api` 作为
   optionalDependency。原文「`qiyu-cli` 零运行时依赖」在 C1 之后**不再成立**，准确表述是
   「核心命令（`auth`/`api`）零运行时依赖；`store` 命令需 `@duckdb/node-api`（可选依赖，缺失时给出安装指引）」；

### 9.2 手动 checklist（发布前，沿用 B 的验收 12/24 模式）

1. **真跨进程锁**：终端 A 起一个持锁写进程（或直接开 `store init` 后不退出），终端 B 跑
   `store status` → 应退避后返回 `store_locked`（退出码 1、`retryable: true`）；A 退出后 B 立即成功。

## 十、验收判据（spec 级，供实施计划展开为测试）

> 格式：判据 → 断言落点（文件/命令）。标「手动」的不在 `npm test` 内。

**配置**

1. 未设任何配置时，库路径默认为 `~/.qiyu/duckdb/qiyu.duckdb`、后端 `duckdb`、重试 30000ms、批次 1000。
2. `--db /tmp/a.duckdb` 覆盖配置文件中的 `store.path`。
3. `QIYU_DB_PATH=/tmp/b.duckdb` 覆盖配置文件，但被 `--db` 覆盖。
4. `--profile prod` 选中 `profiles.prod` 的 store 块。
5. 配置文件含未知键（如 `store.backendd`）→ 退出码 2、消息点名该键路径。
6. 配置文件 JSON 畸形 → 退出码 2、消息含文件路径。
7. `store` 块缺键（如只有 `path`）→ 不报错，其余项走默认。

**schema**

8. `store init` 后库中存在 `schema_version`/`sync_state`/`sync_gaps`/`tags` 四张表。
9. `tags` 表列为 `id`/`name`/`color`，`id` 为 `VARCHAR` 主键。
10. 全部 ID 列为 `VARCHAR`（无 `BIGINT`）。
11. 重复 `store init` 幂等：退出码 0、`schemaVersion` 不变、行数不变。

**upsert 与序列化**

12. `upsert('tags', [{id:'1',name:'a',color:'#FFFFFF'}])` 后 `count('tags') === 1`。
13. 同一主键二次 upsert → 行数仍为 1，`name` 被更新。
14. upsert 只改**指定**的非键列，不把未提供的列置 NULL（对应实测 `INSERT OR REPLACE` 陷阱）。
15. 1000 行批量 upsert 走多值 INSERT（不逐行循环）—— 断言实现路径或计时上界。
16. 19 位 ID（如 `'1234567890123456789'`）往返后仍是字符串、精度不变。
17. 查询结果 `JSON.stringify` 不抛异常（无 BigInt/Date 泄漏）。

**并发与错误**

18. 退避纯函数：`tryOpen` 恒失败 → 总耗时不超过 `readOnlyRetryMs` 上界，抛 `store_locked`。
19. 退避纯函数：`tryOpen` 第 3 次成功 → 返回 store，重试 2 次。
20. `store status` 对不存在的库 → 退出码 1、`kind: 'store_not_initialized'`、hint 含 `store init`。
21. `@duckdb/node-api` 缺失 → 退出码 1、`kind: 'store_not_initialized'`、hint 含 `npm i @duckdb/node-api`。
22. `--backend oracle` → 退出码 2、`kind: 'usage'`。
23. **手动** 真跨进程锁 → `store_locked`（退出码 1、`retryable: true`）。
24. **手动** 两个 `store status` 并发 → 均成功。

**命令面与契约**

25. `store init` 输出含 `path`/`backend`/`configFile`/`schemaVersion`/`tables`。
26. `store --help` 中文，且未知参数优先于 help（次序与 `api` 一致）。
27. 顶层 `qiyu --help` 含 `store init` 与 `store status` 两行。
28. `ErrorKind` union 含 `store_locked` 与 `store_not_initialized`。
29. `README.md` 的「零运行时依赖」表述已改写为准确形态（`store` 命令需可选依赖）。
30. `README.md` 错误 kind 表含两个新 kind。
31. `package.json` 中 `@duckdb/node-api` 位于 `optionalDependencies`（**不是** `dependencies`）。
32. **无任何命令**可执行任意 SQL（`grep` 命令层无 `query(` 调用面）。
